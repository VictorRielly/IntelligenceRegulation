from a reference run of the prover on a fixed admissible input. This is enforced by the type of
`ShdZKProgWitness.Rc` and checked on `shdP_Rc` (COMPILED). The "_of_view" and "_extract" equalities are about the

### Medium

- **M1. The simulator's reconstruction is built from an honest run on a chosen reference input.**
  - **Where.** ProgInst.lean:2231-2237, 2092, 2109, 2118, 2136, 2152-2165, 890-909.
  - **The statement.** `shdP_Rc … (hne) (verdict) (vf) (FRef : FullRunTrace … (refInput Rp hne verdict) default vf)
    (vw : ShdView …)`. Inside it, the following come from `FRef`, the trace of the real prover on
    `refInput Rp hne verdict` with `default` coins:
    - the claim lists `clRef`: `(FRef.blkT k).acc.claims.a`, `…claims.h ++ [logupSumClaim]`, `crAt … pending ++ …`;
    - the audit proofs `haudA/haudH/haudB`;
    - the host coefficients `hc0 := shdP_hc … FRef`;
    - the slot definitions `(FRef.blkT k).dfs …`;
    - the TE claim `c0 := (incTeClaim_of_trace … FRef.incT).choose`.
  - **What holds.** The reconstruction never sees the real input or the real coins: `Rc` takes only
    `verdict, v, hg, view` (COMPILED `#check @ShdZKProgWitness.Rc`, `#check @shdP_Rc`). `hout` proves equality for
    every admissible `y` and every `c`. So, formally, these reference values are proved to equal the real run's
    values, as far as the output uses them, and the zero-knowledge part loses nothing.
  - **The limit (not in the author's summary).** The Lean simulator is a choice-built function (`refInput`, `FRef`
    via `Classical.choice`; first read, L6), not an explicit witness-free simulator. A runnable one would need an
    admissible input with the given verdict, or a public derivation of the claim parts, permutations, host
    coefficients and slot definitions. For statistical zero knowledge in the ROM, with no bound on the simulator's
    work, this costs nothing; but do not call it "a simulator from the view alone".
  - **Checked:** READ (ProgInst lines above) and COMPILED (signatures). I did NOT read whether the approved
    `ZeroKnowledge` (Statements.lean) bounds the simulator's work. INFERRED that it does not, from the first read's
    description.

  single-salt updater `shdCoinsSetLeaf` on `ShdCoins`, and proves three counting bounds through generic
  injection lemmas (386-482).

**E. SaltSplit.**
- **Probability space.**
  - `freshLeafSalt_card` and `coll_pair_twoLeafSalts_card` are over uniform `ShdCoins × (Fin k → Dig)`.
  - `cond_freshLeafSalt_card` is over uniform `ShdCoins` with `v` fixed. This matches the field `hcond_hid`

  (FixedLib:187-191); pairs from `hleaf_inj` (342).

  appear in `δp`, `ωp`, `δh`, `ωh` (ZKBase.lean:43-65).
- **The `shdCoinsSetLeaf_{te,bnd,ah,l2}_poly` lemmas** (339-379) say that overwriting one leaf salt leaves every
  polynomial/mask component of `ShdCoins` unchanged: TE `c.1.1.1`, boundary `(c.1.2.1 k).1`, A/H `(c.1.2.2 s).1`,
  L2 `(c.2 s).1`. `shdLeafSalt_setLeaf_ne` (169) says other salts are unchanged.
