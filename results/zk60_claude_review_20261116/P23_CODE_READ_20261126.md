## Findings

### High (answer before the merge)

**H1. The serve-loop panic guard reaches the verifier server, and its refusal line is not the verifier's refusal form. READ.**
`classify_serve.rs:389-401` wraps `serve(...)` in `catch_unwind` inside `serve_lines_with`. `serve_lines` (`:231-236`) is
`serve_lines_with(lanes, threads, 0, 1, ...)`, and the verifier server `check_serve_inner` calls `serve_lines` (`:810`), so
`zk60_classify check-serve` gets the guard too. The author's entries describe it as a guard for `classify_serve` (the prover).
- What a verifier accepts does not change: a caught panic returns `good = false` and status `internal-error`, never `checked`.
  I traced `check_one` (`:728-801`): `Busy` (`:654-661`) is released by Drop on unwind; a verifier statement is published only
  after `verify_classify_run_with` returned Ok (`:743-755`), so a later panic cannot leave a statement for an unverified run.
- What changes is the verifier's external output on a panic: before, the process died (no result line, non-zero exit). Now the
  stream continues and emits
  `{"event":"served","request":q,"status":"internal-error","error":"internal-error","lane":i,...}`: no `"command"`, no `"id"`,
  and no `FAIL_CLOSED_LINE`, which the verifier's own refusal path always appends (`:826-830`, D45(4)). The request's `log`
  file is not written either (`write_log` runs only inside `serve`). A client that matches results by `id`, or that reads the
  log file or the fail-closed line, cannot handle it.
- Needed: a ruling on whether check-serve should keep the guard. If it does, the line should carry `command` and `id` (both
  public framing, already parsed before any proof work), and for check-serve, the fail-closed line.

### Medium

**M1. On gpu-metal builds, one recovered device error now makes stack-serve refuse every later request until restart. Partly INFERRED.**
`gpu::declines()` is a process-wide counter that only ever goes up (`gpu/mod.rs`, `DECLINES`). The stack-serve
`write_statement` (`trained_block.rs:4259-4264`) refuses when `check_prover_reported(backend, declines)` fails. On a gpu-metal
build, `backend_of_this_process()` is `BACKEND_CPU_BUILD` (the author's own note, `trained_block.rs:3227-3247`), which allows
0 declines. So after one recovered CB error in `run_slot`, every later request of that process is refused.
Before the branch, a CB error inside `round`/`fold`/`masked_prove` panicked (`.expect`) without counting a decline.
`run_fork.rs:1756` and `:2223` catch panics per job (I did not read those contexts), so only the faulting request failed. The
fallback works for the classifier (its statement has no `gpu_declines`) and for single-shot CLIs. For stack-serve it turns a
transient fault into a server that stays up but refuses everything. Both outcomes fail closed. Ask the author to confirm, and to
choose between a per-request decline count and the BACKEND_METAL ruling they deferred.

**M2. Device faults that M6 or A12 detect are no longer refusals; with HL_GPU_REQUIRED=0 they become a silent CPU fallback. READ.**
Before: an M6 replay mismatch (the device's s(1) or challenge differs from the host's) and an A12 "base-field table has an
extension word" both `panic!`/`assert!`ed "the attempt is refused", whatever HL_GPU_REQUIRED said (metal.rs diff lines 263-266,
365, 520-521, 703, 824-827). Now each returns `Err`, then `declined` runs, then the slot runs on the CPU (`argument.rs:2098-2103`,
`2155-2159`). The published bytes are still the CPU's, so the proof stays correct. But the classifier app runs with
HL_GPU_REQUIRED=0 (author's note, `shieldstral_fast_runtime.py:139`) and carries no decline count. So a device that computes
wrong values degrades to CPU speed on every slot, and the only signal is a stderr line. This changes the fail-closed ruling
behind M6 (`metal.rs` doc at diff 714-736). Needs an explicit acceptance, or at least a decline count in the classifier's
timing/event line. Note: the old `fail` closure's unconditional panic on a failed deferred flush is likewise gone (now
`Err((None, Some(_)))`).

**M3. What a panicked request leaves behind is not covered. INFERRED.**
After a caught panic (`classify_serve.rs:389`):
- EVENT_CAPTURE is restored (`classify_cli.rs:168-188`, READ).
- `run_gate` locks are poison-tolerant (`classify_cli.rs:958`, `1109`, READ).
- `Busy` and `DispatchGuard` are released (READ).
- Not checked: the prover's partial `--out` run directory (the module doc says "a refused request creates nothing",
  `classify_serve.rs:47`, but a panic skips that path), the witness-cache budget accounting (`wcache`), and the resident
  `blocks` caches.
- Non-tolerant `lock().unwrap()` sites that a panic inside the lock would poison for the rest of the process:
  `zk.rs:3199,3220` (POOL), `layer.rs:363,380`, `wcache.rs:92,95`, `metal.rs:1809,1862,2545` (FOLD_CAPTURE). The critical
  sections look tiny, so I rate this unlikely.
- The default panic hook still prints the panic message to stderr. That is not the external stdout line, but it is now
  repeated per request instead of once at death. Hidden data could reach it only through a production `assert_eq!` on witness
  values, which is pre-existing and not introduced here.

### Low

- **L1 (READ).** The "queue reset" exists only in `HL_METAL_QUEUES=thread` mode. `reset_own_queue` (`metal.rs:1316-1320`) clears

  `if queue_mode() != Q_THREAD`), nothing is reset and the next CB goes to the same shared queue. The author's text ("Metal
  resets OWN_QUEUE") is accurate only for thread mode.
- **L2 (READ).** Recovery covers only `run_slot`'s slot sumcheck. Other device paths still panic on a device error:

  of the branch, but "recovery from Metal command-buffer errors" should name its scope.
- **L3 (READ).** `try_finals` adds a check that `self.prelude` is None (diff 454-456). On a healthy run the prelude is taken by
  the first round or by `try_into_host`, so this should be unreachable. If it ever fires, it is now a decline, where the old
  code silently read unbuilt tables.
- **L4 (INFERRED).** The `lookup_digest` cache is not invalidated by a direct field write. `attention.exp`, `feed_forward.act`

  production write exists today (grep: only `run_fork_tests.rs:5549`).
- **L5 (READ).** `lookup_tables_digest` makes one `h.update` per i16 element and copies `accuracy.encode()` (`private_block.rs`

- **L6 (READ).** `with_queue` in thread mode now does a RefCell borrow plus a CommandQueue clone (objc retain/release) per CB.
- **L7 (READ).** `Transcript::clone_state` asserts `masker.is_none()` (`transcript.rs:190`) and is now on the production prover

## Q2. Default path: same bytes, small new per-call costs

The transcript and receipt bytes are the same, and so is the work. I compared the old and new `masked_prove` against
`zk::masked_prove_rounds` and `sumcheck::prove_rounds` (`zk.rs:1688-1698`, `rounds.rs:33-48`). The inline nd<2 loop absorbs
the same `sc-round` values, draws the same challenges, and returns the masker's rounds. The nd>=2 replay is identical except
that it returns where it used to assert. On success, `*tr = tr_dev` moves a transcript with the same state, counter and key,
an empty masker and empty masked_rounds, which is exactly what the old in-place call left behind.

New work on every call:
- (a) one `Transcript::clone_state` (about 72 bytes) and one move per device slot (`argument.rs:2091/2094`, `2148/2151`);
- (b) `Result` matching in try_round/try_fold/try_finals;
- (c) thread mode only: a RefCell borrow plus CommandQueue retain/release per CB (L6);
- (d) per serve request: `catch_unwind`, which costs nothing unless something panics, and DispatchGuard;
- (e) per captured-events call: one Restore guard;
- (f) with HL_HOST_FAST_W2 unset: one empty `OnceLock` per BlockPublic (construction, clone, with_accuracy) and no hashing;
- (g) with HL_HOST_FAST_W2 set: one digest per BlockPublic object, replacing the old pointer fingerprint (L5).

No extra buffer copy or lock on the success path. Test builds add thread-local reads (BATCH_TL, QUEUES_TL, DEVICE_TABLES_TL,
INJECT_*), compiled out of production.

## Q3. Error paths

- **a. Transcript. No problem found (READ).** The device attempt runs on `tr_dev = clone_state(tr)` (`argument.rs:2091`,
  `2148`). On Err, `tr_dev` is dropped and `tr` is untouched. The CPU fallback (`:2173-2182`) starts from the same state.
  `try_masked_prove` takes the masker back on both arms (diff 764-766, 865-866). `c` was drawn once before the slot
  (`:1891`); nothing from the failed attempt is absorbed twice or used.
- **b. Tables and buffers. No problem found (READ).**
  - Branch 1 (device-resident tables): after a mid-sumcheck Err, `ev` is dropped and the tables are rebuilt on the host from
    `def.tabs`, `pd` and `pub_gens` (`:2101`, `:2113`). `def.tabs` was only borrowed by the device/into builds (`:1955`,
    `:1964`), so `Tab::Pub` payloads are still present.
  - FoldCache entries are inserted only from host-computed values (`:1190-1199`, `:1271-1281`), so the cache is the same
    whichever path ran.
  - `metal_rounds_owned` returns `(Some(t), _)` only from checks made before any kernel touches the tables
    (`metal.rs:3873-3910`).
  - Branch 2 passes host `tables` by reference to `metal_rounds` (`:2122`), so the CPU folds its own untouched copy.
  - Device buffers go back to the pool through Drop. `run_tagged` waits for every CB before returning, even on error
    (`:1195-1212`), so no in-flight CB still uses them.
- **c. Queue reset. No cross-thread hazard (READ).** OWN_QUEUE is thread-local, and `with_queue` clones the handle before
  calling `f` (`:1331-1352`), so a reset inside `f` drops only the thread-local reference. CBs are always waited for, so none
  is in flight on the old queue. In shared mode nothing is reset at all (L1).
- **d. Zero knowledge. No leak found (READ).**
  - The error strings contain only a status enum, a round index, n_vars, sizes and fixed text (diff 334-338, 449-456,
    804-815, 854-855). `declined` prints `site` plus that string to stderr.
  - The masks are `pd.masks[s]`, precomputed and not redrawn. The failed attempt's masked rounds exist only in `tr_dev` and
    device memory and are discarded, so only one masked transcript is ever published. Reusing the same mask is therefore
    harmless.
  - No partial receipt is written: `out.push` happens only after the slot completes (`:2246`).
- **e. Panic guard.** See H1 and M3. The client receives one constant line with public framing only. The payload is never
  downcast or echoed (`classify_serve.rs:391-400`); the panic message goes to stderr through the default hook, not to stdout.
- **f. HL_GPU_REQUIRED=1. No fallback found (READ).** Every new Err path calls `crate::gpu::declined` (`argument.rs:2100`,
  `2109`, `2157`, `2163`), which panics when required. `Err((None, None))` cannot occur: a failed flush always returns
  `Some(msg)`. The remaining silent CPU paths (`note_cpu_slot` at `:2108`/`:2138`, the base-typing decline, and
  `MetalTables::new` failing at `:1936`) predate the branch and are not error paths.

## Q4. The binding branch

- **What is hashed (READ, `private_block.rs` diff).** BLAKE3 over: domain `hashline/sealed-hist-lookup-tables/1` (36 bytes,
  counted); len(exp) and each exp element; len(act) and each act element; a tag 0/1 for accuracy; then `accuracy.encode()` with
  its length, and every `scaled_tables()` table with its length. The old fingerprint also had `wq`/`wg` pointers, which are
  dropped. Not an issue: `scan_lookup_misses` (`protocol.rs:753-805`) reads only exp, act/accuracy and the dd column, and
  `dd_cap > 0` forces the fallback (`:3121`). Shape-determined tables are covered by `self.sh == *sh`.
- **Can two different table sets share an entry?** Only by a BLAKE3 collision, or by a direct field write after the cache is
  warm (L4).
- **Never computed with HL_HOST_FAST_W2 unset? Yes (READ).** All three production callers of `check_lookup_misses_sealed`
  are behind `host_fast_w2_on()` (`trained_block.rs:3088`, `classify_cli.rs:619`, `745`), and `matches_block` needs
  `Some(sealed_hists)`.
- **How often per request? (INFERRED)** Once per BlockPublic object. Resident classifier blocks keep the digest warm across
  requests; reloaded or cloned blocks pay again.
- **Does it enter a transcript, commitment, statement or receipt?** No (grep: used only at `protocol.rs:799`, `2595` and in
  tests).
