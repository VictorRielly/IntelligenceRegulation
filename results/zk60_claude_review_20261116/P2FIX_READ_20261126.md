# Independent read: the check-server panic-guard fix (9ee0ba37b on 932915a9e)

The fix does what it claims in unwind builds. With `catch_panics = false` the check server's loop matches HEAD-version on every path a viewer could see, and the prover path matches 932915a9e exactly. The new test is deterministic and cannot hang.
One High finding predates the fix and the fix does not address it: `panic = "abort"` in `[profile.release]` (hashline `Cargo.toml:63`) means the prover-side `catch_unwind` never fires in the release binary the app runs. That guard, and the earlier H1, therefore exist only in test and debug builds.
Three Low findings: doc comments describe unwind-only behaviour, a reachable hang is not documented, and the panic payload still reaches stderr. All three are wording or pre-existing; none is a regression made by the fix.

Read: diffs `932915a9e..9ee0ba37b` and `99c4fad7f..9ee0ba37b` (classify_serve.rs); the fix tree under the scratchpad `p2-fix/`; HEAD-version under the repository. No build or test was run. Line numbers marked "fix" refer to the fix tree; "HEAD" refers to the current checkout.

## Findings

### High

**H-A (predates the fix, in 932915a9e / 0360766fc): in release builds the prover-server guard does nothing.**
- READ: `ops/zkp-mvp/gpu-metal/hashline/Cargo.toml:59-63` sets `[profile.release] ... panic = "abort"`. No ancestor `Cargo.toml` or `.cargo/config` overrides it. The binary that serves both commands is `examples/zk60_classify.rs` (`main` at :69, `check-serve` dispatch at :79). It installs no panic hook and has no `catch_unwind`. Recent app drivers run `target/release/examples/zk60_classify` (`results/zk60_p23_app_20261125/t1_driver.py:24`). The project already records "release builds abort on panic" (ZK60_DECISIONS.md D60 F8; R18-1 at :1624).
- INFER: under `panic = "abort"`, `std::panic::catch_unwind` (fix :411) never returns `Err`, because the process aborts after the hook prints. The prover server's "internal-error line, the lane goes on" (fix doc :278-279, :287-288) therefore happens only in test and debug builds. In the release binary a prover panic aborts the whole server (SIGABRT): every in-flight request on every lane is lost, and no serve-end line is printed.
- Consequences:
  - The fix's claim "the prover server behaves exactly as on 932915a9e" holds, but in release 932915a9e already behaved like HEAD-version.
  - The earlier read's H1 (the check server emitting the fixed line) could happen only in unwind builds, so the shipped check server never emitted it.
  - The fix is still correct and keeps test and release semantics aligned on the check side. The prover-side guard's value in production is nil until the release profile unwinds, or the guard is replaced by something that works under abort (e.g. a supervising process).
- Rated High because the brief defines "the prover-side guard is broken" as High. It is not a regression introduced by 9ee0ba37b.

### Medium
None.

### Low

**L-1: the fix's doc comments describe unwind-build behaviour as if it were the server's.**
- Fix :230-233 (`serve_lines`): "It unwinds its lane's thread and ends the process with the stream." The test doc at tests :1280-1284 says the same.
- In release (H-A) the process aborts at the panic, not "with the stream".
- In unwind builds the process does not always end: see L-2.
- Fix :278-279 (`serve_lines_with`): "the lane goes on to its next request". This is true only in unwind builds.

**L-2: an unwind-build hang exists that the doc does not mention.** It also existed on HEAD-version (see Q5) and is restored as is.
- READ: the reader blocks in `req_tx.send` on `sync_channel(lanes)` (fix :314, :343). The receiver is held in `req_rx`, a `Mutex` in the function's own frame (fix :315), so it stays alive after every lane thread has died. The scope joins the reader (fix :333-438).
- INFER: if every lane has panicked and at least `lanes` further non-blank lines arrive, the reader blocks forever and the process hangs, even after stdin EOF. With `--lanes 1` (allowed: `uint_flag(f, "--lanes", 2, 1, 8)`, fix :828), one panic followed by enough further lines is enough.
- Release builds abort first, so the hang cannot occur there.

**L-3 (pre-existing, in 932915a9e; outside the fix's purpose): the K-2 / D65(2) comment's "never ... echo the panic payload" covers stdout only.**
- READ: fix :414-415 says this. No custom hook is installed anywhere in the non-test sources: `set_hook` occurs only at `run_capture_tests.rs:1979`, and the example binary installs none.
- INFER: the default hook runs before unwinding starts, so with or without `catch_unwind` it writes `thread '<a24-laneI-T>' panicked at <file:line>: <payload>` to stderr. Whether that matters depends on where the app sends stderr. The app runs keep `.err` files (e.g. `results/zk60_p23_app_20261125/raw/p23_ab8/*.log.err`).

**L-4 (cosmetic):**
- Fix :228 still heads `serve_lines`'s doc with "**The stream** (both servers)" and then says "This entry is the check server's". Both are right, about different things.
- `serve_lines_with`'s first line, "[`serve_lines`] with a minimum interval…" (fix :276), is no longer the whole difference. The parenthetical added at :278-279 covers it.
- `#[allow(clippy::too_many_arguments)]` (fix :292) is for 8 parameters (clippy's limit is 7). It hides nothing else.

## Q1. Check-server path (`catch_panics = false`) against HEAD-version's `serve_lines_with`

READ: `serve_lines` passes `stagger_ms = 0`, `per_lane = 1`, `catch_panics = false` (fix :238). HEAD passed `0, 1` (HEAD :232-235). The only differences in the loop are these:

1. **`DispatchGuard` (fix :365-382, built at :391, dropped at :426).**
   - Its `at` is `dispatched`. `dispatched` is `Some` only when the reader routes through `lane_tx` (fix :345-357). `lane_tx` is non-empty only when `per_lane > 1` (fix :319-328). With `per_lane = 1` the reader sends `None` (fix :342-343). So on the check path `at` is always `None`.
   - `Drop` begins `if let Some(at) = self.at.take()` (fix :373), so on the check path it does nothing: no lock and no `notify_all`, both on normal exit and when it is dropped during unwinding after a panic in `serve`.
   - On HEAD the equivalent block, `if let Some(at) = dispatched`, likewise never ran on this path (HEAD :370-377).
   - No effect on output, exit or hangs.
2. **`let req_t0 = Instant::now();` (fix :406).** One extra clock read. It is not used on the check path. No effect.
3. **The `if !catch_panics` branch (fix :407-409).** It calls `pool.install(|| serve(q, &line, queued, i))`, the same expression as HEAD :369.
4. **The load release moved into the guard.** On HEAD it ran after `serve`, before `out_tx.send`; it now runs at `drop(dispatch_guard)`, also before the send (fix :426-427). It does nothing on this path anyway.
5. **Outside the loop, also on the check path: the `Restore` guard in `with_captured_events`** (classify_cli.rs fix :171-188; the head-to-fix diff confirms it is the only change in that file). The check closure calls it at classify_serve.rs fix :846.
   - Normal return: `guard.0.take().flatten()` yields the saved value, so `EVENT_CAPTURE` is restored exactly as on HEAD, and `Drop` then sees `None` and does nothing.
   - Panic, unwind build: `Drop` restores `EVENT_CAPTURE` on the rayon worker that ran the closure. On HEAD that worker kept `Some(partial)`. The worker belongs to the dead lane's own pool and runs no further requests, so the difference cannot be observed.
   - Release: `Drop` never runs (abort).
   - No effect on output, exit or hangs.

Normal result, refusal and bad request: these are ordinary `(bool, String)` returns from the closure (fix :839-863), carried unchanged through the same channel and `emit`. They are identical.

Panic inside `serve`: identical. See Q5 for what happens.

## Q4. The new test (tests :1280-1329)

It tests what its doc says, in unwind builds:
- a panic through `serve_lines` comes out as `Err` from `catch_unwind`;
- exactly one line is emitted, for request 1, with `"checked"`;
- no `internal-error` line appears and the payload is not echoed;
- the same closure through `serve_lines_with` gives `(2, 1)` and one `internal-error` line.

On 932915a9e the first half would fail, because `serve_lines` returned `Ok` with two lines. So the test does detect a regression of the fix.

Hang and flake analysis (INFER from the code):
- **Reader:** two non-blank lines go into a `sync_channel(2)` and the reader never blocks. It then drops `req_tx` (end of the closure).
- **Which lane takes what:** the channel is FIFO and the lanes share `req_rx` under a mutex. The lock is a statement temporary, released when `recv` returns, before `serve` (fix :387-390). Whichever lane takes request 0 panics, so it cannot take request 1. The other lane eventually receives request 1, serves it and sends its line, then gets `Err` (channel closed and empty) and exits. No schedule loses request 1 or blocks.
- **Lane death:** rayon's `install` catches the panic at the job boundary on the pool worker and resumes it on the lane thread. The worker survives; the lane thread ends and drops its `out_tx` clone. The main thread's `for … in out_rx` emits request 1's line and ends when the last sender drops.
- **`std::thread::scope`:** after joining all threads it panics ("a scoped thread panicked"). The panic unwinds out of `serve_lines_core`, dropping the pools (rayon pools terminate their threads asynchronously; nothing is leaked or blocked). The test's `catch_unwind` catches it.
- **Other tests:**
  - No thread-local is touched: the closure does not use `EVENT_CAPTURE`.
  - No global state is set and no environment variable is read. `a28_*` are not on this path.
  - The default hook prints two panic messages. Rayon threads are spawned via `std::thread::Builder` and inherit libtest's output capture, so the messages go to the test's captured output.
  - The concurrent hook swap in `run_capture_tests.rs:1978-1983` can at most silence these messages.
  - Each half creates two single-thread pools, which is negligible at `--test-threads=8`.

I see no way for the test to hang or fail spuriously. `cargo test` forces unwinding regardless of the release profile, so the test passes under `--release` too. That is why it cannot see H-A.

## Q5. HEAD-version: a panic in the check server's `serve`

**Release binary (`panic = "abort"`, the one the app runs):**
- At the first panic, on any lane, the default hook writes the message, payload included, to stderr, and the process aborts (SIGABRT; a shell reports 134).
- No served line is printed for that request. Lines already printed stay. Requests in flight on other lanes are lost.
- No serve-end line is printed (`end_line`, fix :867, is never reached), and `refused`/`FAIL_CLOSED_LINE` is not printed either.
- It cannot hang. The number of lanes and the position in the stream make no difference.

**Unwind builds (test, debug):**
- **One lane panics, mid-stream:**
  - The panic propagates out of `pool.install` (HEAD :369) and unwinds the lane thread, which drops its `out_tx`. Its request gets no line.
  - The shared `req_rx` mutex is not poisoned (held only during `recv`), so the other lanes keep taking requests and printing lines.
  - At stdin EOF the reader ends and the lanes drain and exit. The main loop ends, then the scope joins and panics.
  - `serve_lines` never returns, so `check_serve_inner` prints no serve-end line. The panic reaches `main`, and the process exits with status 101 after the hook's stderr message.
- **Panic on the last request:** the same. Exit 101 at EOF after the other lanes finish, no serve-end line.
- **Several lanes, not all:** the same. The scope panics once.
- **All lanes panicked:** nothing consumes requests. Two cases:
  - If, before EOF, the stream holds at most as many further non-blank lines as there is room in the `sync_channel(lanes)` buffer, the reader finishes, the scope panics and the process exits 101.
  - Otherwise the reader blocks forever in `send` (the receiver is alive in the function's frame). The main thread has finished its loop but the scope waits on the reader, so the process **hangs** with no further output, even after EOF. (L-2)
