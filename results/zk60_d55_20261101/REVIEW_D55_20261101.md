## Summary verdict

**SOUND AS BUILT, within the prototype's scope (blocks-only D12a statements, test builds only). Nothing is
broken, and no soundness defect was found.** It is **not ready for use**: one Medium evidence finding (F1) and
four Low findings (F2–F5) must be closed first.

- **Binding order holds, and is stronger than D12a's.** Every boundary root is in S0 before any fork exists.
  Every claim, both its point and its value, is in S1 before any opening challenge.
- **Domain separation holds.** Forks are separated from each other, from the run transcript and from D12a, short
  of a BLAKE3 collision. One structural caveat: D55 shares its base profile's transcript constructor and
  Fiat-Shamir key, and is separated only by its first absorb (F3).
- **Mix-and-match moves no project figure.** The bound for a W16 8B T128 run at L = 32 is about **2^-97.3**
  (union bound), with exactly D12a's terms. On the per-query Fiat-Shamir reading it is about 102.9 bits, also
  unchanged.
  - The note's [UNSURE] item is right: the proof work of the opening-term attack collapses (c·L proofs buy c^L
    tries).
  - But that term is not the binding one, and no project figure counts attempts in proofs.
- **The joined openings are right.** Each boundary is opened once, with both sites and the verifier's own
  claims. No claim can escape the join.
- **Randomness.** L + 1 independent `from_os` generators are neither a soundness nor a privacy problem, and the
  privacy statements' assumption E-1 already covers them. They break W-8 assertions 5 and 7 as written, and the
  census does not scan this module (F4).
- **Privacy.** No new value is published, the openings are the same, and only their order changes. The joint-law
  gate has never seen a D55 capture, and today's capture tooling cannot record one (F5).
- **The verifier.** Every D12a verifier check has a counterpart, and the two profiles do not cross. The four
  controls are real tests that can fail. Control 1, however, does not show that the fork index is in the
  derivation (F2), and no control has a false statement (F1).

## 1. Binding order — SOUND

| step | prover (`run_fork.rs`) | verifier (`run_fork.rs`) |
|---|---|---|
| header: base constructor, `run-construction`, then D12a's six absorbs | `transcript` 302-318, called at 581 | 779 |
| every root `B_0..B_{L-2}`, in order (`pb-fork-commit-root` = k, then `B`, `rows`, `log-cols`), then `pb-fork-s0` = L: this is S0 | commitments 593-601 (one generator, 591), absorbs 604 via `absorb_commit` 343-355 | head decoded 782, absorbed 783, S0 tag compared 784-786 |
| `fork(S0, k)`: S0 rebuilt (`s0` 329-333), then `pb-run-fork` = k and `pb-run-fork-block` = digest_k (364-369) | 535, then `prove_core` 545 | 746, then `verify_core` 758 |
| join on the run transcript from S0, in block order (`pb-join-fork`, `pb-join-state` = 32-byte state and counter, in-claims, out-claims), then `pb-fork-s1` = L: this is S1 | 687-698 | 822-825, with the verifier's own end states and claims |
| openings, all after S1: `B_0..B_{L-2}`, then the input endpoint, then the output endpoint | 710-726 | tail decoded against S1 at 827, checks 834-851 |

- **Phase 1 against the forks.** Every fork's first state is a function of S0, and S0 contains every root.
  - So every challenge of every fork comes after every root: LogUp β/γ/α, every sumcheck challenge, the
    terminal mask challenges and the IO claim points.
  - The external endpoints are in `expected-IO`, inside the header.
  - In D12a, B_k's root is absorbed after blocks 0..k-1 (`run.rs:1188-1200`), so a D12a prover can pick B_k
    after seeing their challenges. D55 forbids that. The note's "kept and strengthened" is correct.
- **Phase 1 against the join.** The IO claims' points come from fork challenges, and their values are slot
  terms absorbed as `pb-term` on the fork (`argument.rs:1129`). The claims are built from those
  (`argument.rs:1131-1137`).
  - So a fork's end state binds its claims. The join binds them again, explicitly (`claim_bytes`, 373-390,
    which is length-prefixed and injective).
  - The PCS opening assumes "claims already absorbed by the caller" (`zkp-core/src/pcs.rs:377-380`), and on the
    run transcript the join is what makes that true. The join is therefore load-bearing. It is correct as
    built.
- **The position tags** (S0, S1, fork start and end) are squeezed from discarded clones (`run.rs:896-903`).
  They are compared and never adopted. None of them advances a transcript.

## 2. Fork domain separation — SOUND (with caveat F3)

- **Fork against fork.** The first fork absorb hashes S0 ‖ 11 ‖ `pb-run-fork` ‖ 8 ‖ k_le. That is 67 bytes, and
  it differs in k (`transcript.rs:59-72`: label and data are both length-prefixed; `absorb_u64` is a fixed
  8-byte LE).
  - The digest absorb comes second. So two forks that carry the same block are separated by the index alone.
    That is the A/B's situation: `RepeatBlock`, every digest equal. It holds by the code, but no test isolates
    it (F2).
- **Fork against the run transcript.** After S0 the run absorbs `pb-join-fork` (a 12-byte label), and a fork
  absorbs `pb-run-fork` (11 bytes). Their first inputs differ.
  - A tag squeeze input is 47 bytes (`transcript.rs:101-111`), and every absorb input is at least 48 bytes. So
    a published tag can never be some fork's absorb.
- **Against D12a.** Both use the same constructor input, `tagged_transcript(sh, base run profile)`
  (`run_fork.rs:305`; `run.rs:798`). Both use the same Fiat-Shamir key, the block shape's tag
  (`protocol.rs:96-101`).
  - They diverge at the first absorb: `run-construction` (16-byte label, data = the fork profile) against
    `run-shape` (9-byte label).
  - No other transcript on the path absorbs `run-construction`; I searched the source.
  - After that every state differs, short of a BLAKE3 collision. The bindings differ (tested,
    `run_fork_tests.rs:198`).
  - The parameter line and the schedule digest also differ, under their own domain
    (`run_fork.rs:261-293`). That separation is redundant but harmless.
- **Against a single block, a token-I/O or classifier run, or a D55 run on another base.** Each has a
  different constructor domain (`protocol.rs:119` for a single block). The token-I/O and classifier bases are
  refused at the door (`run_fork.rs:196-198`).
- **The digest.** Each fork absorbs the statement's `block_digests[idx]`. The verifier's preflight checks the
  handed blocks against those digests (CS-6, `run_fork.rs:492-496`). `RepeatBlock` caches the digest of an
  immutable borrow, so the cache cannot drift.
- **The profile tag.** See F3: the separation is sound in the random-oracle model, but it is outside the D17 /
  T-1 rule that a new construction gets its own profile string. The W-2 check (`census`, 221-257) covers only
  this module's absorbs against the base constructor.

## 3. Mix-and-match grinding — the note's argument is correct; no project figure moves

**What a cheater controls.** The only prover-chosen inputs to S1 are the fork frames.
- The join reads the verifier's own replayed end states and claims (822-825), never a frame field.
- Every fork frame field is either absorbed in the fork or Merkle-bound to a fork root. The columns, salts and
  paths after the last squeeze are bound by their roots. The tags, binding, L and k are compared.
- An honest opening is deterministic: `pcs::open_zk` takes no generator (`pcs.rs:1016-1045`).
- So the S1 values reachable are exactly the combinations of valid fork candidates.

**Interactive (union-bound) reading, D15 / D27.**
- The interactive analogue is: commit every boundary, run the L block sub-protocols in parallel with
  independent coins, then the openings.
- Suppose the statement is false relative to the committed planes. Then some fork's sub-statement is false, and
  either:
  - that fork accepts with true IO claims (ε_k, the per-block term); or
  - one of its IO claims is false and its opening accepts (ε_open).
- Each fork's error holds against any prover that also sees other forks' coins, since those are independent of
  its own. The union bound needs no independence across forks anyway.
- So Pr ≤ Σ_k ε_k + Σ_{L+1} ε_open, the same terms as D12a. The join adds hash inputs, not rounds.

**Fiat-Shamir per-query reading.**
- The doomed-state argument composes. The joint state is doomed while some component (a fork, or the opening
  phase once a false claim exists) is doomed.
- Each oracle query is a challenge of exactly one round of one component, because the states are
  domain-separated (section 2). It un-dooms that component with probability at most that round's error.
- So Pr[forge] ≤ Q · max_round ε + (state collisions). The set of round types is D12a's, so the maximum is
  D12a's: one fork's LogUp α event, 2^-102.92 at W16 T128 (REVIEW_W16).

**Proof-work reading** (the note's [UNSURE] item). The note is right, and the effect is somewhat stronger than
it says.
- With c valid candidates per fork, a cheater gets c^L distinct S1 values for c·L fork proofs.
- It can put its one false claim on B_0, the first opening after S1. Then each try costs:
  - the join suffix, a few absorbs with a mixed-radix Gray-code order;
  - B_0's λ/ρ draws;
  - one boundary fold: about 1.9 M Fp2 multiply-adds, plus about 0.8 MB of BLAKE3 over the absorbed vectors,
    at 38 rows × (2^14 + 256) [MODEL: about 1 ms].
- For a one-half chance against one false claim it needs 2^104.6 tries. At L = 32, c = 10 already gives
  2^106.3 S1 values, from 320 fork proofs (ten runs' worth).
- So proof work stops being the limit on the opening term. In D12a the same term costs at least a partial block
  re-proof per try: the cheapest fresh prefix for B_{k-1}'s opening is a re-commit of block k's H, then its 23
  slots and three openings.
- **No project figure moves:**
  - D27 quotes the work reading as "a generous one-hash-per-try estimate";
  - the D15 note of 20:10 says "all figures are interactive, and Fiat–Shamir grinding over the A randomness
    makes the per-block figure a per-try rate";
  - MEMO_G02 §3.4 says the Fiat-Shamir multi-round loss "is not quantified anywhere".

  None of them counts attempts in proofs. I confirm the note's belief.
- **And the cheapened term is not the binding one.**
  - Per try, an opening is ≤ 2^-105.61. The lookup round is 2^-102.92.
  - The lookup round is ground in both constructions at about one boundary re-commit per try:
    - in D12a, B_k is absorbed before block k's A and M roots and β/γ/α (`run.rs:1188-1220`);
    - in D55, any root in S0 re-randomises every fork.
  - So the cheapest attack on either construction is unchanged.
- **One caveat for the future.** If a security tier (D27's "selectable standards") is ever stated in proof-work
  terms, D55 must be re-derived for it.

**Hosted-claim batching** stays inside one block. The `hosted` lists name slots of the same `acc`
(`argument_accuracy.rs:66, 106, 143, 194, 266`; `argument.rs:936, 1101, 1147`), with ν drawn on that fork.
None of them names an IO slot.

## 4. The joined openings — SOUND

- **Each B_k is opened once.**
  - Prover: `bounds.into_iter()` (711-718). `PreparedBoundary::into_opening` consumes the owner
    (`boundary.rs:275-281`), so a second opening does not type-check.
  - Verifier: one pass, `k = 0..L-2` (834-843).
  - The tail carries exactly L − 1 + 2 openings, by counted length (`run_fork_wire.rs:278-305`).
- **Its claims come from both sides, in D12a's site order.**
  - Site 0 is fork k's slot-22 list; site 1 is fork k+1's slot-21 list. Prover 714-716, verifier 837-838.
  - D12a does the same: `pending` then `ic` (`run.rs:1226-1228`).
  - The layouts point the IO tabs at `mask_row(0)` and `mask_row(1)` (`run.rs:757-771, 883-885`).
- **"One reserved pair per claim site, opened exactly once" is kept.** `check_opening` (`boundary.rs:287-289`)
  runs `audit_claims` (`protocol.rs:240-284`) on both sides. Every reserved row is used by exactly one claim,
  every evaluation claim carries exactly its own pair, and there are exactly two column-weight groups.
  - The endpoints go through `check_endpoint_opening` (`protocol.rs:365-379`), once each (719-726; 844-851).
- **No claim can escape the join.** The verifier's claim lists are the ones `verify_core` computes
  (`protocol.rs:1891-1895, 2009`). The frame carries no claim. Each of the 2L lists is used exactly once:
  - fork k's in-list at B_{k-1}, or at the input endpoint when k = 0;
  - its out-list at B_k, or at the output endpoint when k = L − 1.

  Every list is absorbed at the join before any opening challenge. A claim the cheater leaves out of its own
  join only changes the cheater's S1, and the openings then fail (control 4).

## 5. Randomness — no soundness or privacy problem; a departure from W-8 (F4)

- **The construction.**
  - Commit phase: one generator, `commit_seed_domain` (`run_fork.rs:105-110, 591`).
  - Forks: one each, `fork_seed_domain(profile, k)` (112-118), built inside the worker (538).
  - Each is `ZkRng::from_os`: 32 fresh bytes of `/dev/urandom` key a keyed BLAKE3 over
    `hashline-zk-os-rng/v1/` ‖ domain (`zkp-core/src/rng.rs:44-63`).
- **Soundness.** Prover randomness never enters a soundness argument; a cheater chooses it freely.
- **Privacy.**
  - Every mask, pad and salt is drawn from a key of 256 fresh bits, and no two streams are related.
  - A domain-split single stream would have needed a derived or forked key, which is exactly what W-8 assertion
    5 forbids. So independent keys are the conservative choice.
  - The accepted statements' assumption E-1 is "separate OS entropy reads are independent and uniform"
    (`ZK60_PRIVACY_STATEMENT_TRAINED_TINYLLAMA_T32.md` §6). It already spans several reads per run (the endpoint
    generators plus the run stream). So L + 1 reads change no assumption.
- **The census.**
  - `s25_tests.rs:2764-2817` (W-8(5): "each prover constructs exactly one generator") and `:2637-2721` (W-8(7):
    "`ZkRng::new` appears nowhere on the path") read `production_sources` (`:1627`). That list follows only
    non-`#[cfg(test)]` modules (`:1616-1626`).
  - `run.rs:1680-1682` declares the fork module `#[cfg(test)]`, and `s25_tests.rs:2526` lists the three files as
    test-only. So both scans are silent on D55.
  - Read against this module, assertion 5 is false (L + 1 constructions), and so is assertion 7: `ZkRng::new`
    sits in `ForkRandomness::FixtureSeed` (`run_fork.rs:100`).
  - That seeded arm is dead code: every caller passes `Os`, and the cheating prover hard-codes it (567). It is
    still a seeded constructor in a prover body.

## 6. Privacy (D1)

No new leak was found by reading. This is not a privacy acceptance.

1. **Published values.**
   - Head: the binding, L, the L − 1 roots and the S0 tag.
   - Fork frames: the binding, L, k, the start tag, A/H/M roots, the slots, the M/A/H openings and the end tag.
   - Tail: the binding, L, the S1 tag, the boundary openings, two endpoint openings and the end tag.
   - These are D12a's values, regrouped. Each tag is a squeeze from a public transcript state. The S1 tag, for
     example, equals the first two λ of B_0's opening, which the verifier draws anyway.
   - **No new value is published.**
2. **The opened vectors** are the same function of (the committed matrix and its masks, the claim structure,
   λ, ρ, the column indices) as in D12a. Those challenges are uniform in the random-oracle model in both orders.
   The audit enforces the same reserved pairs, one claim each, at every opening (section 4). So the
   block-triangular argument stated at `protocol.rs:230-239` carries over.
3. **Order.**
   - In D12a, block k+1's challenges follow B_{k-1}'s opening messages. In D55, no fork challenge depends on
     any opening. In the random-oracle model that changes no distribution.
   - But the run-wide joint law and the three-commitment joint rank (`A_k` out rows, `B_k`, `A_{k+1}` in rows)
     have only been gated in D12a order.
4. **Concurrent reads.**
   - Forks k and k+1 share `bounds[k].1.data()` as `&[Fp]` (612-613), read-only, with no data race.
   - Each fork's terminal uses only its own reserved pair: the layout's IO rows, with the audit refusing a
     shared or unused pair.
   - Nothing about the concurrency enters a receipt. `ForkStats` timings are test output only.
   - Per-fork timing is a side channel outside D1's artifact scope. A deployment should not publish it.
5. **The refusal fact.**
   - The refusal events are D12a's: challenge-only refusals at slots and openings, and the CS-3 data refusal
     before any challenge of its fork.
   - D55 emits nothing before the end, because the prover holds every frame. So a data refusal in fork k cannot
     follow published frames 0..k-1, which a streaming D12a run (M-9 aside) could allow. That is neutral or
     better.
6. **Owed.**
   - A capture at the fork profile, then a gate pass (rank lemma, NL-1, joint passes), with W16's 16-bit
     histograms on the list.
   - Today it cannot be done without new wiring: the run capture's recorder is thread-local
     (`run_capture.rs:873-874`), and the D55 verifier runs every fork on a spawned thread (790-808). Even
     `workers = 1` spawns one. So `verify_core`'s capture hooks (`protocol.rs:1936-1945, 1950-1977`) would
     record nothing (F5).

## 8. Anything else

- **Labels and hash inputs.** All transcript inputs are length-prefixed (`transcript.rs:59-68`). The schedule
  digest is a fixed domain followed by length-prefixed lines (`run_fork.rs:271-293`). `claim_bytes` is
  injective (373-390).
  - The one input that is not length-prefixed is the `FixtureSeed` derivation, `ZkRng::new`'s
    domain ‖ seed (`rng.rs:34-40`). It is dead, and test-only.
  - No wrong label was found. The schedule text's ranges are inconsistent (F6).
- **Frame fields.** Every head, fork and tail field is compared, absorbed or Merkle-bound. Field words are
  canonical-checked (`wire.rs:198-204`). Column indices are bounded (`wire.rs:211-215`). No count comes from a
  frame.
- **Test hooks are thread-local.** `CheatingProver` (`protocol.rs:630-660`), the injection hooks
  (`protocol.rs:577, 1089, 1111`; `argument.rs:85`) and the run capture are all per thread.
  - `prove_core` runs on scoped workers, so a hook set by a test is inert inside every fork. Only CS-6's switch
    is read on the calling thread (577).
  - Any ported negative test must propagate the hooks into the workers (F5).
- **The frame binding is the header state**, the same for every D55 run of one statement. It localises
  "another statement", not "another run". A foreign frame from a second run of the same statement is caught by
  the S0-dependent start tag, and then by the chain. That is untested (F7).
- **Prototype limits, fine at this scope.** The verifier holds the whole receipt (no M-3 streaming). The prover
  holds every frame. There is no `finish`-style regression guard.

## 9. Soundness bound for an L = 32 run (W16 8B T128, the A/B's geometry)

**Union bound** (the D15 / D27 reading, interactive). The same terms as D12a.

| term | per unit | count | run total |
|---|---:|---:|---:|
| LogUp, (N + 4·T_d − 1)/p² (REVIEW_W16) | 2^-102.92 | 32 forks | 2^-97.92 |
| M openings | 2^-106.25 | 32 | |
| A and H openings, row width 2^14 | 2^-105.61 | 64 | |
| 31 boundaries + 2 endpoints, row width 2^14 (2^12) | 2^-105.61 (2^-103.69) | 33 | |
| all 129 openings | | | 2^-98.73 (2^-97.90) |
| sumchecks; commitment field terms (MEMO_G02 run totals at 8B T512, carried as upper bounds) | | | 2^-112.2; 2^-106.4 |
| **whole run** | | | **2^-97.27 (2^-96.91)** |

- **The bound.** Pr[a false W16 8B T128 D55 run with L = 32 accepts] ≤ about **2^-97.3**. It is 2^-96.9 if
  the boundary and endpoint rows are 2^12 wide; I did not read that profile's `endpoint_log_n`.
- **Against D27.** That is 1.9 to 2.3 bits above D27's floor of about 95.
- **At D27's named workload** (8B T512), D55 inherits the base profile's figure and changes nothing. That figure
  is 94.48 at R13 per the D24 review, a pre-existing N-r13-1 item.
- **Fiat-Shamir per query.** Pr ≤ Q·2^-102.92 + Q²·2^-256, i.e. about 102.9 bits of oracle work, as in D12a.
- **Proof work.** Mix-and-match removes proof work from the opening-term attack: 320 fork proofs buy
  2^106 > 2^104.6 tries. The lookup term stays the cheapest per try, in both constructions. No project figure
  changes (section 3).
