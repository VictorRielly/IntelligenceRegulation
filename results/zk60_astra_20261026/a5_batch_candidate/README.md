## Implemented

`native.patch` is a source-pinned delta against frozen-r16b/hashline.
`stage_native.py` reproduces the five staged files without editing that tree.
It adds `zk60_classify prove-batch --export DIR --tables DIR --content-file FILE
--batch-file FILE [--label L]`. The request is owner-only, bounded to 64 KiB,
and contains no content on the command line. Its exact schema is generated by
`batch_request.py`.

The native command accepts the complete, ordered sexual/violence/hate moderate
T128 plan for one whole post, at most eight chunks per category and 336 content
tokens. It refuses missing/repeated/reordered jobs, a changed expected model or
whole-post count, existing output/sidecar/owner paths, aliases, overlapping
paths and private owners under any receipt parent. It checks every policy's
tied parameters before proving.

One `ExportPublic` owns the initial checkpoint/tied derivation and public layer
digests. One `BoundClassifierTables` owns the derived embedding/margin tables;
the embedding is borrowed, never cloned for each category. Each proof still
creates a fresh seal, endpoint randomness, witness source and block reader.
Every block reload retains the existing digest check. Proofs execute
sequentially; no batch of witnesses or all-layer weights is retained in RAM.

This removes repeated **initial** checkpoint/model/table loading. It does not
remove per-proof sealing, witness construction or streamed layer reloads.
The existing writer already loads each numerical layer once for every request;
the candidate supplies all category/chunk requests to that writer together.

`batch_request.py` prepares the private whole-content file and complete writer
and native requests from the app's pinned encoder and reserved plan/context.
It constructs explicit candidate-prover commands and the reviewed r16b
fresh-process verify/input-owner/label commands. Its strict event router returns
only `status: unverified`, even after a successful complete batch. It rejects
partial completion, hidden refusals, swapped jobs, missing segments, duplicate
JSON keys, a false verification claim and a changed total/model.

## Failure and acceptance

A failure stops the native batch. The app candidate's terminal boundary is
`collect_batch_result`, not the pure log splitter. It requires confirmed child
termination, the complete success event, and a guard record with clean exit and
no kill/refusal/error/drain failure. On any failure it quarantines every requested
receipt, `.incomplete`, `.unverified-statement` and owner directory (including
`input.dec`), with publication always disabled. Paths come from an immutable
request scope derived from the trusted roots, not from prover stdout. Private
quarantine is restartable; conflicts block publication while remaining paths are
still quarantined. A live child is never cleaned up. Native batch-level cleanup
and fixed-entropy equivalence belong to the token owner's r18 adoption.
There is no implicit restart, re-proving or partial publication.
The app must independently verify each receipt from bytes, check its input
opening against the original whole post, and run category aggregation with
`--expect-total` from the pinned encoding. No verifier, statement encoding or
proof relation is changed by this patch. The single-prove path shares the
refactored body; its full native regression tests are still required.

Queue adoption remains an integration step: atomically claim the post's whole
reserved plan, route the shared guard/log evidence without counting its time
once per receipt, finish all required checks, then use existing publication
validation. The candidate is intentionally not selected by the app factory.
Its preparation helper alone is not a database reservation or a native proof.

The coordinator's approximately 110 seconds per extra category is an estimate,
not an A5 measurement. Existing R16 prove `total_seconds - prove_seconds`
includes initial loading **and sealing**; it cannot be used as the saved model
load time. The new `batch-loaded.load_seconds` measures model plus table loading
directly. Initial-load saving is modeled as `(number_of_proofs - 1) * load_time`;
end-to-end savings and memory behavior still need measurement.
