# First-user workflow on the installed Mac

The W16R2 development profile screens short, already-public text for sexual content, graphic violence and hate or harassment. Each receipt identifies the model, fixed category policy and verdict. The model can make classification errors. Human authorship would require independent provenance evidence. The default app configuration runs the separately labelled demo stub. [App guide](../../../apps/proven-media/README.md#try-the-installed-w16r2-text-classifier) · [Classifier profile](../../../apps/proven-media/deploy.json)

| Participant | Actions available |
| --- | --- |
| Invited author | Use the key supplied by the operator to sign in. Submit text and see it pending under **Your submissions**. Once all three model checks and input bindings pass, read the published labels. **Re-verify now** checks the saved receipts against the post again. |
| Guest | Read the feed, choose an audience filter, inspect a published item's three labels and check its manifest and ledger inclusion. Download the manifest, record and proof bundle without signing in. A separately trusted publisher key lets the guest authenticate the signed labels offline. |
| Independent verifier | With the named verifier binary and matching public model export, run each category command in the bundle's `VERIFY.md`. With a copy of the public store, also replay ledger inclusion and verify every segment digest. The publisher retains the private input opening used for the platform's post-binding check. |

## Measured first use, November 24

Two separate HTTP clients exercised the invited-author and guest roles over localhost on the installed Mac. The app prepared its public model export from an empty store in 3.08 seconds. The author submitted a 14-token public fixture. Publication took 152.88 seconds, including 81.5 seconds waiting for another guarded job. All three labels were “no,” so the minor filter also returned the text. The guest could not see the pending post, and the author could not force the ledger batch. The local ledger closed automatically with a 30-second test interval. The normal default is 600 seconds. These are observations from one automated run. An outside participant has yet to try the workflow. ## Prover switches and GPU faults

At six lanes and eight threads, the paired gains from the sixth switch were 6.248% and 0.018%. The second gain fell below the coordinator's threshold, so the outside-user pilot keeps the five settings on its qualified prover. [Decision and measurements](REVIEW.md#wave-2-decision-for-the-installed-app-november-24)

The installed prover runs six lanes with eight threads per lane. Both the resident and standalone verifier remove all five prover-only settings from their environments. The A30/A31 verifier checks the resulting receipts. [Release and benchmark evidence](REVIEW.md#five-switch-classifier-release-november-24)

The app reaches the native `serve` path implicated in the reported GPU fault. If the process remains alive and gives no reply to a submitted proof request, the service's 900-second deadline kills that process and waiting requests fail. A regression exercises the silent-process case with a shortened deadline, checks the failed job and released lock, and sends a job to a replacement service. The replacement's scripted refusal confirms it handled the request. The native Metal driver fault itself has not been reproduced in this app test. ## A guest download for whole-post verification

After a published W16R2 post's local batch closes, the guest can select **Download offline verification store**. The archive contains the signed post manifest, its public statements and receipt objects, its anchors and batch files, and the local block history through its last anchor. A guest can verify this post without arranging a copy of the operator's public store. The packaged reader checks the public artifacts against a separately trusted publisher key. The operator retains the private openings used to bind the submitted text. [Participant instructions](../../../apps/proven-media/README.md#full-w16r2-verification-on-another-mac)

A seven-chunk regression split one post across three local batches and added a later, unrelated post. The downloaded archive contained each shared receipt object once and excluded the later block and the other post's anchor. In a fresh directory the command in the download recovered the signed verdicts, including a positive last chunk. Changing a segment made the same command fail. Pending posts and batches were refused. [Guest download tests](../../../apps/proven-media/tests/test_w16r2_post_coverage.py)

The guest downloaded a fresh 14-token public post over loopback HTTP. Its verification store contained 97 files and 2,008,826,368 bytes. With the operator checkout removed from its configuration, an extracted reader authenticated the signature, all 84 public segments, three labels and their ledger inclusion. Three separate native verifier processes then used the packaged Python tools, the relocated 611-file kit and the downloaded store. They accepted each category at a 97-bit floor and confirmed the signed post length. Native checking used the installed Mac's shared resource guard and lane hold settings. The author's three private input-binding rechecks also passed. The test used automated clients on one Mac. ## Resuming an interrupted guest download, November 25

The public verification-store URL now serves byte ranges. A HEAD request returns the full length and a strong ETag. A reader can keep that ETag with the partial file and use it as an HTTP precondition when resuming. The server seeks directly to the requested portions of the archive. Readers who receive HTTP 412 can start a new file for the changed version. The signed manifest and native checks still authenticate the contents after transfer. [Reader commands](../../../apps/proven-media/README.md#resume-an-offline-verification-store-download)

The in-process HTTP test split the retained 14-token post's 2,008,826,368-byte store into 121 responses, starting with a break after the first 511 bytes of a TAR header. Reassembly matched an independent Python USTAR writer across all 97 members. Two runs returned the same SHA-256. Regression tests also cover a changed archive of the same size, unsatisfiable ranges, and skipping a preceding file when fetching a later member. This exercised the application endpoint on the installed Mac. Transfer through an outside participant's browser or proxy remains untested.
