## Summary verdict

**SOUND AS BUILT, with findings.** No soundness defect was found. Every verifier site takes the rate, `Q`, pad
count and Merkle depth from the profile's own shape, never from a receipt or a caller flag. A W16R2 string cannot
be carried by a shape at any other geometry. `M` is on its own constants on every wire. Existing profiles' bytes
do not move, by the code and not only by the logs. The implementation is **not ready for registration**: one
Medium evidence finding (F1) and three Low findings (F2 to F4) should be closed first.

- **Parameters (Q1): sound.** `Shape::build` refuses a W16R2 string at any rate, row width or endpoint geometry
  but (1/2, 2^14, endpoints equal) (`shape.rs:1014-1023`).
  - CS-9 pins the rest of the geometry to the registered entry (`shape.rs:902-934`, `640-647`).
  - CS-8's rebuild runs inside every `verify_core` (`protocol.rs:1982`).
  - Every PCS parameter at every verifier site is a function of that shape (§1).
- **Sampling and weights (Q2): what the lemma counts.** There are Q = 260 independent uniform indices, with
  replacement, over all N = 2^15 columns, drawn after every vector is absorbed. The proximity weights are `rows`
  independent `challenge_fp2` squeezes drawn after the root.
  - **But the counted bound is attained.** I built an explicit close-case attack. It is accepted with
    probability exactly (1 − (e+1)/N)^Q: 0.3723 measured against 0.3725 at the toy geometry, and 2^-105.946 at
    the profile.
  - No control exercises that case, and control (d) is vacuous (F1).
  - The tightness also qualifies "no soundness given up" (F2).
- **Domain separation (Q3): sound.** There are three new block strings and two test-only run strings. They are
  distinct, none is a prefix of another, each has its own four `derive_key` keys, and each is its own
  constructor domain.
  - A W16 proof cannot replay as W16R2, or the reverse. Three things stop it independently: the Merkle keys,
    the Fiat–Shamir key and domain, and the geometry.
  - Control (e) demonstrates only the geometry (F7).
  - One equal-length hash-input pair is newly created: the W16R2 rung's 63-byte constructor input against a
    63-byte `pb-slot` absorb. It is separated, and s33's lemma covers it, but it is recorded only under the W16
    rung's name. "No new hash input length" is also not literally true (F5).
- **`MASK_CHECKS` (Q4): complete.** `M`'s prover, verifier, wires, byte count and capture writer all use
  `zk::MASK_Q`. No remaining site reads `M`'s count from the shape, or the block's count from `M`'s (§4).
- **Controls (Q5).** They are real: each runs the production `verify_zk_tagged`, or `verify_core` on a real
  W16R2 proof, and asserts the rejection site. Gaps:
  - the lemma's case (b) is not controlled, and (d) is vacuous (F1);
  - nothing is controlled at run level (F3);
  - some assertions are loose (F4).
- **Existing bytes (Q6): unchanged.** Every changed expression evaluates to its old value at every non-W16R2
  profile (§6).
- **Other (Q7).** Metal is prover-only and gives CPU = Metal bytes. The path depth is 15 at every site. The NTT
  table (2^15) covers `M`'s 2^12. The endpoint row width is 2^14. The receipt counts check by hand, but no test
  ties them to the codec at a W16R2 shape (F4).

## 1. The verifier's PCS geometry comes from the profile — SOUND

**Where the shape comes from.**
- `Shape::build` fixes the geometry: a W16R2 string with `inv_rate ≠ 2`, `log_cols ≠ 14`, or an endpoint rate or
  width different from the core's is an `Err` naming D59 (`shape.rs:1014-1023`). Otherwise
  `opened_cols = W16R2_OPENED_COLS = 260`, and every other profile keeps `COL_CHECKS = 256`.
- `trained_geometry` builds the registered entry at rate 1/2 with `endpoint_inv_rate: None` (`shape.rs:645-646`).
  The `None` default makes the endpoint follow the core rate, and the guard requires that equality anyway.
- CS-9 (`shape.rs:902-934`) compares a `Shape::new` result with that entry, in every field. So tokens, width,
  `endpoint_rows` and `f_e` are pinned too.
- CS-8 (`check_constructed`, `shape.rs:1995-2041`) rebuilds from the fields. A field write to `inv_rate` or
  `opened_cols` is therefore refused. This is tested, `w16r2_tests.rs:219-237`.
- `verify_core` calls CS-8 first (`protocol.rs:1982`). `with_layer_calibration` clones the shape and re-runs CS-8
  (`shape.rs:1928-1947`).
- No production code writes `opened_cols`, `inv_rate`, `endpoint_inv_rate`, `endpoint_log_n` or `log_cols`. I
  grepped every non-test file.

## 2. Column sampling and row weights — what the lemma counts

| lemma premise (handoff §4) | code | holds |
|---|---|---|
| U is fixed before every challenge | A's root at `protocol.rs:2003` and H's at `:2011`, both before their claims; B_k's at `run.rs:1349`, in stage k before block k's slots (D55: in S0); endpoints in the header's `expected-IO` | yes |
| the claims are absorbed before λ | slot terms `pb-term`; the PCS assumes the caller absorbed them (REVIEW_D55 §1) | yes |
| r ∈ Fp2^m uniform and independent, every row weighted, not powers | `zk_rhos`: λ per group, then `prox_rho = tr.challenge_fp2_vec(rows)` (`zkp-core/pcs.rs:936-957`); one 32-byte squeeze per element, each half reduced mod p (`transcript.rs:120-133`) | yes (the 1 + 2^-51.6 bias is the handoff's) |
| Q independent uniform indices over [0, N), drawn after all G + 1 vectors | `absorb pcs-vec` × G, `pcs-prox`, then `challenge_indices(num_col_checks, nn)` (`zkp-core/pcs.rs:1204-1211`); a u64 masked to a power-of-two bound, with replacement (`transcript.rs:136-148`) | yes, exactly uniform and with replacement, as (1 − (e+1)/N)^Q counts |
| every vector checked at every sampled column | `zkp-core/pcs.rs:1245-1255` | yes |
| the code is RS[D, n + q_pad] on a coset disjoint from G_n | `encode_row_zk` (`zkp-core/pcs.rs:658-677`), a bijection; `coset_powers` asserts 7^N ≠ 1 (`:645-654`) | yes |
| K = n + Q, i.e. q_pad = Q exactly | `ZkOpts::standard`; pinned at equality for W16R2 (`w16r2_tests.rs:172`) | yes |

- The verifier's `check_opening` replays the same draws on a clone and refuses λ = 0 or a dependent proximity
  pair (`protocol.rs:292-317`). That conditions r on a negligible set. It can only lower acceptance.
- **The bound is tight.** This is the observation that matters for a white-hat.
  - Take a matrix U within the unique-decoding radius: row 0 is corrupted on e columns S by a codeword D0 that
    vanishes on K − 1 other columns Z.
  - The cheater shifts the group vector by λ·dec(D0) and the proximity vector by ρ_0·dec(D0).
  - Then it passes every check on Z ∪ S, and fails only on the remaining e + 1 columns. A false claim
    (value + ⟨dec(D0), c⟩) is accepted with probability exactly (1 − (e+1)/N)^Q.
  - Measured in exact field arithmetic (`review_logs/close_case_attack.log`): 7,445 of 20,000 = 0.3723 at the
    toy (n = 16, N = 32, Q = 4, e = 6), against 0.3725. At the profile it is 2^-105.946.
  - So the δ/2 count has no slack (F1, F2).

## 3. Domain separation — SOUND (records: F5, F7)

**Strings.** A scan of every `"hashline…"` literal in `hashline/src` finds five W16R2 strings, each defined once:

| string | length | sibling |
|---|---|---|
| `…/private-block-rung-lh-t32-w16r2-d/1` | 51 | W16 rung, 51 |
| `…/private-block-shieldstral-3b-t128-lh24-w16r2/1` | 62 | 62 |
| `…/private-block-llama-3-8b-t128-lh-w16r2/1` | 56 | 56 |
| `…/private-run-rung-lh-t32-w16r2-t/1` (test only) | 49 | 49 |
| `…/private-run-llama-3-8b-t128-lh-w16r2-tst/1` (test only) | 58 | 58 |

- None equals another string or is a prefix of one, other than the shared `hashline-zk-mr1/` stem.
- Each block string gets four keys: `derive_key` over the string, under four contexts (`zkp-core/hashtag.rs:92-101`;
  `shape.rs:2311-2325`).
- Each block string is the transcript constructor's domain under its own Fiat–Shamir key (`protocol.rs:96-101`).
  A run uses its run string. A D55 run uses `D55_PROFILE_PREFIX ‖ base` (`run_fork.rs:82-84, 328`).

**Replay, W16 ↔ W16R2.** Three independent mechanisms reject it:
1. **Merkle keys.** Column, leaf and node digests are recomputed under the verifier's own profile keys
   (`zkp-core/pcs.rs:1241-1243`), so every W16 column fails.
2. **Fiat–Shamir.** The verifier rebuilds the transcript under the W16R2 key and domain, so every challenge
   differs.
3. **Geometry.** W16 has path depth 16 against 15, vectors of n + 256 against n + 260, and Q = 256 against 260.

Control (e) (`w16r2_tests.rs:700-742`) demonstrates only mechanism 3, because T-4 fires first. Its PCS-level half
re-proves the other geometries under the W16R2 keys, which isolates geometry from keys. No control isolates keys
from geometry (F7). They are separated by construction.

**Equal-length hash inputs.**
- Under a tag, coincidences of input length between different functions separate nothing and matter for nothing
  (`hash_domain.rs` `imposed_at_shape_with` returns the empty set). Within the transcript function, inputs are
  length-prefixed.
- **One new same-function pair exists (F5).** The W16R2 rung's constructor input is 12 + 51 = 63 bytes, the same
  length as an absorb of `pb-slot` with 8 bytes of data, under the same Fiat–Shamir key.
  - It is separated, like M26's W16-rung pair: 14 positions in the two `le64` length fields are forced to NUL,
    where the constructor carries ASCII.
  - s33's J-7a lemma covers it, because `registry_profiles` reads `shape.rs`.
  - The census accepts it through the W16 row's generic match strings (`s25_tests.rs:708-721`).
  - But the row's text and the 63-byte pin test (`s33_tests.rs:382-415`) name only the W16 rung.
- **A new absorb length.** `pcs-vec` / `pcs-prox` now absorb 266,304 data bytes, where W16 absorbs 266,240
  (census `logs/chain/g_scans_print.log:11964`). So "no new hash input length appears on the block path"
  (`shape.rs:270-272`) is inaccurate, though harmless.

## 4. `MASK_CHECKS` / `MASK_Q` — complete

- **M's verifier** draws `MASK_Q` indices over its own 2^12 domain and checks the count against them. It never
  reads a shape field (`zk.rs:648-685`; indices at `:661`, count at `:662`). The prover uses the same constant
  (`zk.rs:594`). T-4 for M uses `wire::MASK_PATH_LEN` (`hash_domain.rs:701-713`).
- **Wire, at all nine sites, uses `MASK_CHECKS = zk::MASK_Q`:**
  - `wire.rs:131, 151, 259` (single block);
  - `wire.rs:351, 386, 475` (run segment);
  - `run_fork_wire.rs:77, 155, 231` (D55 fork frame).
- **Byte count:** `receipt_bytes` uses `MASK_PADS` (`shape.rs:2802`), which is `zk::MASK_Q` (`shape.rs:580`).
- **Capture writers:** `run_capture.rs:3271, 3608, 3886`.
- **No remaining site reads M's count from `Dim::checks` or `opened_cols`.** The only place a non-M count is tied
  to `MASK_Q` is the token-I/O tier's TR-2 check (`token_io.rs:226`), which no W16-family shape reaches.
- **A residual inconsistency, harmless.** `wire.rs:17-19` keeps `MASK_VEC`, `MASK_DOM` and `MASK_PATH` as
  literals, while `MASK_CHECKS` now reads `zk.rs`. `token_io.rs:1280` already derives its `MASK_PATH` from
  `zk::MASK_LOG_DOM`. Tie the three to `zk.rs` too (F5).
- **The value is 256 at every profile,** so no frame length moved. The D12a/D55 W16R2 runs verify, which they
  could not with the old `bd.checks` (README).

## 7. Anything else

- **Metal.**
  - Prover only. The verifier re-encodes every vector and re-hashes every opened column on the CPU.
  - `metal_commit_zk` derives q from `pads.len() / rows` (`gpu/metal.rs:1099-1107`). `metal.rs` has no `inv_rate`
    literal.
  - CPU = Metal digests at the rung (golden `334e168f`), 8B (`5343008a`) and Shieldstral (`e0bb5917`). The
    rung's is pinned; the trained ones are not (F4).
  - A device bug could cost completeness or privacy, never soundness.
- **Path depth 15.**
  - Consistent at `Dim` (`wire.rs:89`), `path_len`, `verify_zk_tagged` (`:1183`), `receipt_bytes` (`clog2(n · 2)`),
    `MerkleTree` over 2^15 leaves, and `decode_tail`.
  - M stays at 12. There is no hard-coded 16 on a W16R2 path (grep).
- **NTT.**
  - `ntt_log_at` = max(14 + 1, 12) = 15 (`protocol.rs:40-42`); the run's `ntt_log` = 15 (`run.rs:447-449`).
  - The tables are stride-based (`zkp-core/ntt.rs:68-101`), so M's 2^12 transforms are correct on a 2^15 table.
- **Endpoint geometry.**
  - `endpoint_log_n` = 14, which answers REVIEW_D55's open question for W16-family T128: 2^14, not 2^12.
  - Endpoint rows: 37 at 8B and Shieldstral, 6 at the rung. Boundary rows: 38.
  - Endpoint specs carry the shape's rate and pads (`endpoint_g.rs:142-170`), and `policy_fits_the_shape` holds
    them to the shape (`run.rs:1306`).
- **Receipt bytes, checked by hand.**
  - One endpoint opening: 2·16,644·16 + 260·(8 + 37·8 + 32 + 15·32) = 744,768 at W16R2, against 749,568 at W16.
  - This matches the README.
  - Block: the counted 25,160,664 B against 25,016,184 B (+0.58 %) is consistent with +4 columns × ~20.5 KB at A
    and H, less 32 B per column of path.
  - No test asserts `receipt_bytes().total == wire::encoded_len` at a W16R2 shape (F4).
- **Hiding (for condition 5, not reviewed here).** q_pad = 260 is at least the number of distinct opened columns
  (at most 260). Z_n ≠ 0 on h·G_N at rate 1/2, because h^N ≠ 1. Each regular commitment is opened once in D12a
  and D55. The frozen privacy-gate scripts under `ops/zkp-mvp/gate-tinyllama/frozen_v22/` read
  `mask_domain` / `num_col_checks`; condition (5) should run them against a W16R2 capture.
