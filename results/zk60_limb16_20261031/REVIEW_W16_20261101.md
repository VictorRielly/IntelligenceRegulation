Reviewer: Claude (independent D24-class review, read-only), 2026-11-01.

Scope: the W16 delta in `ops/zkp-mvp/gpu-metal/hashline/src/private_block/`, on both the prover and the verifier side. Files: `range16.rs`, `range16_tests.rs`, `accuracy_layout.rs`, `layout.rs`, `pad.rs`, `protocol.rs`, `argument.rs`, `argument_accuracy.rs`, `shape.rs`, plus the windows they rely on (`accuracy_precision.rs`, `accuracy_aligned.rs`).

Method:

## Summary verdict

**The W16 range argument is SOUND as built for the registered non-DD LowH24 profiles. Nothing is BROKEN.**

- **Range checks.** Each W16 lookup proves the same set as R13's byte limbs, and every recomposition is wrap-free. No constraint R13 enforced was dropped.
- **Family separation.** Separation by tag holds. The tags are bound identically on the query side and the table side, by one function that both the prover and the verifier call.
- **Padded table entries.** They cannot admit an out-of-range value: the verifier builds every table column, padded copies included.
- **LogUp bound.** The recount confirms DESIGN.md's claim. The per-block lookup term *improves*, from 2^-102.00 (R13) to 2^-102.92 (W16) at T128, because the query count halves. The larger tables add only about 1.3% to the numerator.

One **CONCERN (Medium)** is not part of the range argument itself. The R2-a / R2-4 guards key on the profile string list `TRAINED_CALIBRATION_PROFILES`, which does not contain the W16 profiles. A W16-profile shape built outside the trained door is therefore not refused by name: `layout.rs:1311` and `protocol.rs:1313` let it through. This must be closed before any W16 receipt is registered.

The other findings are Low or Info:
- a missing runtime cross-check of helper counts;
- missing malicious controls that DESIGN.md plans;
- a hard-coded tag list in a test;
- DD paths that no test exercises;
- a hard-coded `Rh` width.

## 1. LogUp soundness bound for the larger tables — SOUND (DESIGN.md's claim confirmed)

**The accounting.** I used the R13/R14 review accounting (`results/zk60_d24_review_20261017/REVIEW_R13.md:210-216`, `REVIEW_R14.md:124-160`). Per block it is (N + 4·T_d − 1)/|Fp2|, with |Fp2| = p² ≈ 2^128. The terms are:
- **B1:** a bad query collides with a table tuple under the (β, γ) fold, at most 2/p² per distinct table tuple.
- **B2:** α lands on a table pole with m = 0, or on an equal-pair query pole.
- **B3:** the α identity, by Schwartz-Zippel, with |V| + |PP| ≤ N.

W16 changes only T_d, which gains the range families, and N.

**Why the accounting still applies.**
- All of A is absorbed before the three challenges are drawn: every looked-up plane and every multiplicity, including the new `R{w}_{s}` planes. The challenges are `beta`, `gamma`, `alpha` (prover `protocol.rs:1556, 1574-1576`; verifier `protocol.rs:1863, 1865-1867`).
- H comes after α.
- The new table helpers enter the single value-0 sum claim with sign −1. `HIds::is_table` covers `gu8 .. gu8 + 3 + n_range` (`layout.rs:704-706`), and `logup_sum_claim` sums every H plane (`protocol.rs:177-186`).

**The counts.** The per-position counts come from `lookups_w16` (`accuracy_layout.rs:289-344`): L 2, D 7+8+2+2 = 19, Q 6, Kv 6, S 2+2+1+2 = 7, F 2+1+1+2+1 = 7.
- These reproduce the logged 32,276,480 range-or-byte query words at both trained T128 shapes exactly (`logs/…: W16 W16_8B_T128_H24 … lookups 32276480`).
- The logged families are `[(2,1),(4,1),(5,1),(7,1),(12,1),(13,1),(15,2),(16,4)]`, so the distinct range entries are Σ 2^w = 110,772.

**The sub-terms.**
- **B1 (γ/β tag-fold collision):** 2·T_d/p² = 2^-110.04.
- **B2 (table pole):** T_d/p² = 2^-111.04.
- **DESIGN.md's estimate:** "≤ N_tab/p², N_tab ≈ 2^17" (DESIGN.md:199-202) is about 2^-111. It agrees with B1 to within the factor 2 that the R14 convention charges for degree-2 tuples. The range tuples themselves are degree 1 in γ, so 2·T_d is conservative.

**T256 (estimate).** I assumed f_e = 9, so wrho_s = 17, which adds a width-1 family and two-limb SR/SG. I took G = 4.
- W16: N = 82,378,752, per block 2^-101.70, 32 blocks 2^-96.70.

**Not recounted.** I did not recount the sumcheck, column and PCS terms. W16 changes no slot's rounds or degree: `slots()` is unchanged, and the W16 IR test asserts degree ≤ the declared degree. It also adds no opening. For a whole-run figure, those terms are carried from the R13/R14 accounting.

**Characteristic condition.** The per-value residue argument needs N < p, which holds (2^25 ≪ 2^64). Multiplicities are free field elements, as in R13.

## 2. Family separation — SOUND

**Tags.**
- `TAG_RANGE0 = 200` and `tag_value(w) = 200 + w` give 201..=224 for w in 1..=24 (`range16.rs:27-32`).
- The other block tags are 1 and 2 (`layer.rs:33-34`), 128..=134 (`tables_attn.rs:47-77`) and 141 (`TAG_DD`, `layout.rs:1011`).
- `TAG_EMB = 135` (`token_io.rs:306`) is outside the range as well.
- No two widths share a tag, and no range tag equals another family's tag.

**The byte width keeps the U8 family.** `lk_tag(8) = LkTag::U8` (`range16.rs:36-42`), and `widths()` drops 8 (`range16.rs:138`). So no `Range(8)` family exists that could alias the U8 table.

**The fold.** `g_range(g_u8, w) = g_u8 · tag(w) / TAG_U8`, which is γ·tag(w) (`range16.rs:47-49`). It needs no new transcript draw: it reuses R13's γ, and `g_u8 = gamma · TAG_U8` on both sides (`protocol.rs:1577` and `:1868`).

**Collision argument.** Fix the committed A, then draw γ.
- A query with linear form q (in Fp) and tag w folds to q + γ·tag(w).
- A range or U8 table entry of tag w′ is v + γ·tag(w′).
- The two are equal only when γ = (q − v)/(tag(w′) − tag(w)), which is one γ per entry. When w′ = w, equality means q = v, which is in range.
- For the exp, ACT and DD tuples, the difference is a nonzero polynomial of degree ≤ 2 in (β, γ), nonzero through the γ coefficient (tag(w) − 129/134/141 ≠ 0).
- Acceptance with any bad query needs that bad query to collide, so the probability is ≤ 2·T_d/p² (B1 above).
- The same argument covers the reverse direction: an exp, ACT or DD query landing on a range entry.

**Bound identically on the prover and the verifier, query side and table side.**

| | Prover | Verifier |
|---|---|---|
| Query side | `tagged_column` picks `(w, g_range(g_u8, w), inverses)` from the shape's families (`protocol.rs:1588-1610`, `:778-786`), and `helper_one_any` inverts `alpha − (v + g)` (`:790-802`) | `lk_tables` folds `cst + g_of(l.tag, g_u8)` (`argument.rs:1395-1402`), consumed by `helper_sum` (`argument.rs:1410-1426`) in every `*_w16` zero-check |
| Table side | `range16::table_column(f, s, log_cols, g_range(g_u8, f.width))` (`protocol.rs:1723`) | the same call in `tab_w16`, as a public table (`argument_accuracy.rs:752`) |

- Both sides take each lookup's tag from the same `Layout::lookups` (`layout.rs:1467-1469`, which calls `lookups_at`, then `AccuracyIds::lookups_w16`).
- The verifier's layout comes from its own shape, and the profile string is the transcript domain (`protocol.rs:119`).
- `define` is the one slot definition both sides run (`argument.rs:1654-1657`, then `argument_accuracy.rs:17-29`).
- The verifier evaluates every public table, the range table columns included, itself (`argument.rs:1112`).
- The Metal IR (`slot_ir.rs:882`) is prover-only; the verifier always evaluates the closure (`argument.rs:1119`).

## 3. Decompositions — SOUND

Notation: R_w is the width-w range family. A two-limb value is (lo, t) = (low 16-bit limb, top limb), recomposed as `limbs16` = lo + 2^16·t (`argument.rs:1405-1407`).

| Value | Lookups | Recomposition, where enforced | Admitted set | Wrap |
|---|---|---|---|---|
| 16-bit word (X, Y, AO, X1, YM, Z16, X2, Q8, QR8, O8, K8, V8, KR8, U16) | R16 on `word + 32768` (`range16.rs:80-82`, `accuracy_layout.rs:297`) | none needed: the lookup's linear form *is* the word | [−32768, 32767] | the field element equals k − 32768 with k < 2^16 |
| H16 at LowH24 | R16 on `h − 2^16·t + 0` and U8 on `t + 128` (`range16.rs:91-93`, call site `accuracy_layout.rs:322`) | implicit: h = lo + 2^16·t, where lo is a linear form in h and t | lo ∈ [0, 2^16), t ∈ [−128, 127], so h + 2^23 ∈ [0, 2^24) | lo + 2^16·(t + 128) < 2^24 ≪ p, and t is unique given h |
| Remainder ≤ 16 bits (RQL/RKL 15, RO 12, RVL 16, RU 12, RH 16, rope 7, SR/SG at wrho_s ≤ 16) | one R_b query (`range16.rs:72-73`) | the limb itself in its relation | [0, 2^b) | trivial |
| Remainder of 17-24 bits (NR/NS/MR/MS 24, RAL 21, RDL 20, RGL 20, RSL 18) | R16 on lo, and R_{b−16} (U8 when b = 24) on t (`range16.rs:74-75`) | `limbs16` inside the relation that uses it (list below) | [0, 2^b) | < 2^24 ≪ p |
| Softmax quotient P (P_dict under DD) | one R13 query (`range16.rs:101-104`, `accuracy_layout.rs:334-335`) | none needed | [0, 2^13) | trivial |

Each remainder is recomposed inside a zero-check:
- NR, NS, MR, MS: `dzc_w16` clauses (`argument_accuracy.rs:484-487`).
- RAL, RDL: `host_o` and `host_d` (`:490-491`).
- RGL, RU, RH: `host_g`, `host_u` and `f0` (`:520, :524-525`).
- RQ/RO and RK/RV: `host1`/`host2` (`:557-558`); the rope remainders: the `rope` clause (`:554-555`).
- RSL: `host_s` (`:614`, `:675`).
- SR, SG: `c2`/`c3` (`:619-624`, `:720-722`).

The limb order is low-first everywhere: `role()` in `argument_accuracy.rs:5-9`, `planes()` in `accuracy_layout.rs:203`, `rem_lookups` in `range16.rs:70-77`, and the witness at `witness_accuracy.rs:545`.

**The windows match the relations' shifts.**
- `accuracy_precision.rs:84-90` forces q, k, v, pv, up into 9..=16, so they have one limb; this is what makes the shape's hard-coded 6 Q/Kv lookups and 1 RU plane correct.
- It forces score and ao into 17..=24 (two limbs), and down into 17..=24 at H24.
- The gate shift is 17..=24 (`accuracy_layout.rs:115`).
- The product fold shift is fixed at 16 (LowH24) or 24 (Low) by `accuracy_aligned.rs:25-29`, and equals the hard-coded RH width (`range16.rs:133`, `accuracy_layout.rs:324`).

**The signed top limb.** Its range [−128, 127] (U8 on t + 128) gives exactly h ∈ [−2^23, 2^23). That is R13's three-byte set (R13 `fzc`, clause `f2 = h + 2^23 − limbs(hl)`, `argument_accuracy.rs:111`). So the admitted set, and with it R13's accepted no-wrap analysis of `f0` and the down matmul, is unchanged.

The sign is needed for completeness only. At a padded F position the pad rule zeroes both h and t (`pad.rs:294-315`: HT is a ZERO-rule F plane), giving lo = 0 and t + 128 = 128, both in range (asserted in `range16_tests.rs:151-160`). An unsigned top would be held at zero by the pad rule, which would put lo at 2^23, outside R16.

`word24` with a general bias is consistent: word + bias = (word − 2^16·t + (bias & 0xffff)) + 2^16·(t + (bias >> 16)). The only call site uses bias 2^23.

## 4. Was any R13 constraint dropped or weakened? — SOUND (none)

Slot by slot against R13 (`argument_accuracy.rs:42-438` against `:455-776`):

- **D.** R13 has 13 clauses. The 7 word decompositions (x, y, ao, x1, ym, z, x2 + 32768 − limbs) are removed, and each word is now looked up directly. The other 6 are kept verbatim: the two norm-a clauses, x1 − x − ao, the two norm-m clauses, and x2 − x1 − z (`:484-487`). `host_o` and `host_d` are kept, with 2^16 weights.
- **Q/Kv.** The 3 word decompositions are replaced by word lookups. `rope`, `host1` and `host2` are kept.
- **F.** `f1` (u) and `f2` (h) are replaced by `word16(U16)` and `word24(H16, HT)`. `f0`, `fa`, `host_g` and `host_u` are kept.
- **S.** `c4` (p = Σ PL) is replaced by the direct R13 lookup on P. `c0`-`c3`, `cx`, `host_rs` and `host_s` are kept. The symmetric S8 pair is kept as is, in the same order: `accuracy_layout.rs:328-329` against `:270-271`.
- **DD.** `c4` (P_dict = Σ PL) is replaced by `direct(pdict, 13)`. `c2`, `c3` and `ctab` are kept.
- **L.** LIMB and LIMBM stay U8.
- **TAB.** The three triples stay, and one triple is added per range sub-plane.

Every R13 byte-limb lookup corresponds to a W16 lookup with the same admitted window. Where R13 used a "top pin" (a scaled byte), W16 uses the exact-width family. W16 is strictly *stronger* at padded positions: the words themselves are now looked up at every position (helpers are not gated), whereas R13's word-to-limb clauses were gated by the support indicator. This stays complete because the pad rule zeroes the words there, and 0 + 32768 is in R16.

`new_w16` refuses an allocation in which any legacy limb id is mapped or any word id is lost (`accuracy_layout.rs:164-169`). The legacy `SC_DZC`/`SC_FZC` bodies that read `A_XL0`, `A_HL0` and so on (`argument.rs:2105-2183`) are never reached on an accuracy stack (`argument.rs:1655-1656`).

## 5. Pad rule and table-side support — SOUND

**Padded entries are in-range repeats.** A padded position of a narrow family holds `value = i % 2^w` of the same family, plus that family's γ·tag (`range16.rs:175-182`). The verifier itself builds this column as a `Tab::Pub` (`argument_accuracy.rs:752`). A nonzero multiplicity at a padded copy would therefore count an in-range value of the right width. Padding cannot, by itself, admit an out-of-range value, whatever the pad term says.

**The support term is enforced and verifier-built.** In `tab_w16` (`argument_accuracy.rs:755-771`) each narrow family's multiplicity and helper are added to the pad-zero term under `support_column(f, log_cols)` (`range16.rs:185-188`). That column is a public table built by the verifier: 1 on the 2^w true rows, 0 on the copies.
- The declared zero groups are checked against `pad.rs`'s lists by `tab_group_is_declared` (`argument.rs:1356-1364`).
- Those lists come from `a_rule`/`h_rule` (`pad.rs:299-305`, `:334-340`): narrow families are ZERO and full families EXEMPT. A full family has no copies, since `support == 2^log_cols` (`range16.rs:163-170`).
- The honest prover writes m and h only on true rows (`protocol.rs:1521-1524`, `:1725-1726`).
- The support term is therefore a canonical-form and privacy condition, not one the range soundness depends on.

**S-1.** `log(Dom::Tab)` is `domain_log_at(8, true, log_cols) = log_cols` (`layout.rs:175-181`). The sub-planes are 2^log_cols long (`range16.rs:180-188`). A length mismatch would be refused on both sides at `argument.rs:854-856`.

**Multiplicities are committed before every LogUp challenge.** The `R{w}_{s}` planes are A planes (`accuracy_layout.rs:182-183`) and are filled before A is committed (`protocol.rs:1517-1526`, then the commit at `:1552-1556`).

## 6. Anything the prover relies on that the verifier does not check — CONCERN (one Medium, one Low)

- **Medium: the R2-a / R2-4 string guards do not name W16.** See finding F1. They decide whether a profile string is a trained-calibration profile using `TRAINED_CALIBRATION_PROFILES`, and W16 is deliberately kept out of that list (`shape.rs:143-171`, `:1679-1681`, `:1728-1730`).
- **Low: the helper count is trusted from the shape.** The verifier never re-checks that a lookup domain's helper count equals ⌈lookups/2⌉ (finding F2). The relation constrains only `lks.len().div_ceil(2)` helpers (`argument.rs:1413`). Meanwhile `b.h` registers `sh.helpers(dom)` of them (for example `argument_accuracy.rs:470`), and `logup_sum_claim` sums all of them. A surplus helper would be an unconstrained term in the value-0 sum.
  - Today the two counts are equal by construction. The shape formula (`shape.rs:2318-2326`) and `lookups_w16` agree term by term, and the precision class pins the one-limb windows.
  - An honest prover would panic at `cols[2*k]` (`protocol.rs:1606`) rather than produce such a proof.
  - Nothing refuses it at verify time.
- **Everything else is rebuilt by the verifier.** Families, widths, sub-planes, tags, table columns, support columns, zero groups, the sum claim and the claim sites are all rebuilt from the verifier's shape. The family list is stated twice independently and cross-checked on both sides (`accuracy_layout.rs:178-180`; `layout.rs:367-368`, `:371`; `HIds::new`, `layout.rs:647-652`).
- **Prover-only checks the verifier does not need:**
  - the miss refusal (`w16_histograms`, `protocol.rs:710-760`, then `:1498`);
  - the helper-job overlap checks (`protocol.rs:807-822`);
  - the device IR.

## Privacy-relevant changes (brief; the D54 privacy re-check is still owed)

- **New committed planes.** The new planes are below; R13's word-limb planes and their helpers go away.
  - A: one multiplicity plane per range sub-plane. That is 12 at T128 and 13 at the rung; I estimate 10 at T256 (`R{w}_{s}`, `accuracy_layout.rs:183`).
  - H: one table helper per sub-plane (`layout.rs:647-648`).
- **Openings.** No new opening kind. Each new plane has one `SC_TAB` claim site (`shape.rs:2423-2426`), and the H ones also enter the single sum claim, exactly as `MU8`/`gu8` do.
- **What the histograms reveal.** The 16-bit histograms are a much finer statistic of the hidden activations than the byte histograms: R16 counts every looked-up 16-bit word and low limb. They are committed with hiding and opened only through masked claims, but the privacy statement must list them as new private planes.
- **Lift condition.** It is kept: every sub-plane is exactly one row wide.
- **Zero-denominator refusal.** It is data-independent. The prover inverts every table position of every family, unused entries and padded copies included (`protocol.rs:1724`), and every honest query value is a table value. So a query-side refusal (`helper_one_any`) always implies the same table-side refusal, with the same string, before H.
