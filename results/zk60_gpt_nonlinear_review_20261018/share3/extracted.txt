**Yes—this is a fruitful direction, particularly because quotient lookups could absorb the expensive rounding and range checks.** The important distinction is between a table of exact quotients and one of rounded fixed-point quotients.

Our division audit supports your intuition: for 16,384 outputs, the arithmetic-only diagnostic used **32,800 constraints**; including all normalization bounds brought it to **525,746**. Those are constraint counts, not proof timings, but they identify the opportunity.

**1. The outer-product structure is excellent—before rounding.**

For numerator values \(a_i\) and nonzero denominator values \(b_j\),

\[
T_{ij}=\frac{a_i}{b_j}=a_i\,r_j,\qquad r_j=\frac1{b_j}.
\]

This is a rank-one matrix. Taking “16k” as 16,384:

| Representation | Entries stored | Payload at 32 bytes/entry |
|---|---:|---:|
| Entire quotient matrix | 268,435,456 | 8 GiB |
| Two factor vectors | 32,768 | 1 MiB |

These figures exclude proof overhead and additional columns needed to bind values to indices.

Structured lookup arguments such as TaSSLE provide a framework for exploiting decomposable tables without constructing or committing the entire large table. That supports the architectural direction; it does not establish a speedup in our current prover. genui{"citation":{"ref":"turn11search1"}}

The complication is that our softmax statement is

\[
y=\left\lfloor\frac{Q a}{b}\right\rfloor,
\]

where \(Q\) is the fixed-point scale. This rounded table need not remain rank one. For example,

\[
\left[\left\lfloor\frac{16a}{b}\right\rfloor\right]_
{a\in\{1,3\},\,b\in\{3,5\}}
=
\begin{pmatrix}5&3\\16&9\end{pmatrix},
\]

whose determinant is \(-3\).

Consequently, factorizing the reciprocal computation still leaves a rounding obligation. A modular field inverse also does not, by itself, produce the required integer quotient.

**2. There is an exact reciprocal construction worth testing.**

We can preserve the original floor result using a sufficiently precise, rounded-up reciprocal.

Assume

\[
0\le a\le A_{\max},\qquad 1\le b\le B_{\max}.
\]

Choose a power of two \(L\ge Q A_{\max}B_{\max}\), and define

\[
z_b=\left\lceil\frac{L}{b}\right\rceil.
\]

Then

\[
\boxed{\left\lfloor\frac{Qaz_b}{L}\right\rfloor
=\left\lfloor\frac{Qa}{b}\right\rfloor.}
\]

The reciprocal approximation increases the unrounded result by less than \(1/b\), which is too little to cross the next integer boundary.

This gives us a concrete construction:

- Certify \(z_b\) **once per distinct denominator**, using \(0\le bz_b-L<b\).
- Bind each query’s denominator to its certified reciprocal.
- Multiply by the numerator and prove a power-of-two truncation.

The numerator can remain its existing authenticated circuit value; a separate numerator lookup is optional.

**I checked this arithmetic:** 65,792 exhaustive small-domain pairs, 100,020 random/boundary pairs with 14-bit values, and 100,020 with wide softmax-like bounds. Every result matched exact integer division. These are correctness checks, **not proof-runtime benchmarks**.

The remaining tradeoff is precision:

| Tested bounds, \(Q=2^{32}\) | Required \(L\) | Truncation bits after cancelling \(Q\) |
|---|---:|---:|
| 14-bit numerators and denominators | \(2^{60}\) | 28 |
| 135-bit numerators, 144-bit denominators | \(2^{311}\) | 279 |

This matters for us: **16k distinct values does not mean 14-bit values.** Our wide softmax weights can require multi-limb arithmetic for this exact construction, potentially consuming the savings. Our existing lower-precision reciprocal modes avoid some of that cost but have a different rounding contract.

**3. Your table-sizing optimization applies most strongly to the pairs actually used.**

Let:

- \(N\): total quotient requests;
- \(U_a,U_b\): distinct numerators and denominators;
- \(K\): distinct **numerator–denominator pairs**.

There are two useful approaches:

| Approach | Work certified once | Work remaining across requests |
|---|---|---|
| Denominator dictionary | \(U_b\) reciprocals | \(N\) bindings, multiplications and truncations |
| Observed-pair dictionary | \(K\) exact quotient relations | \(N\) lookups of complete \((a,b,y)\) tuples |

The second approach can eliminate repeated rounding checks entirely: prove each occupied quotient-table entry once, then reuse it. Its approximate cost is

\[
T_{\text{binding}}(N,K)+K\,C_{\text{exact division}}.
\]

That can be excellent when \(K\ll N\). But small marginal dictionaries do not guarantee small \(K\): 16k numerator values and 16k denominator values can still generate almost entirely distinct pairs.

For softmax, denominators already repeat within each row. At one million outputs with 512-element rows, there are only about 2,048 row denominators before any further deduplication. Conversely, 16k possible exponential outputs does **not** imply only 16k possible row sums.

The previous optimizations therefore transfer as follows:

- **Adaptive table sizing:** size reciprocal tables by \(U_b\), and quotient dictionaries by \(K\).
- **Separate certification from assignment:** certify dictionary entries once, then bind all requests to them. Private dictionaries still need sound commitment and binding.
- **Repeated-scalar aggregation:** potentially useful again, but savings depend on repeated scalars in the resulting proof—not merely repeated numerator values.
- **Batching:** amortizes dictionary certification across many requests sharing the same numerical specification.

**My recommendation is to compare the exact reciprocal dictionary and the observed-pair dictionary against our exact division baseline.** Measure total certification, binding and proving time while varying \(U_b\), \(K\), and value bit widths independently.

Your proposal targets the expensive part of division. The decisive question is whether we can share the **rounding certification** as effectively as we can share the reciprocal table.

The implementation uses the exact identity

\[
\sum_i s_i B_i
=
\sum_u s_u\left(\sum_{i:s_i=s_u}B_i\right).
\]

We group actual equal field scalars, then perform the smaller MSM. The circuit, keys, verification, proof size, and integer exponential outputs remain unchanged.

For your **16k-distinct-value case**, this reduces the complete G2 MSM from **1,453,639 terms to 37,832**. Its median duration falls from **2.94 s to 1.05 s**, including aggregation overhead. The remaining terms come from other circuit work, so the total does not fall exactly to 16k.

The whole-proof improvement is smaller because G1 MSMs, FFTs, and witness construction remain. This successfully exploits repetition, while retaining an \(O(N)\) scan and base-aggregation step.

I also tested a control that removes only zero scalars. Grouping outperformed it in all million-evaluation comparisons, confirming an additional benefit from repeated **nonzero** scalars.

There is a crossover: at 262,144 evaluations and 200,000 distinct inputs, the improvement was only **0.4%—effectively a tie**. The smaller 32,768-evaluation/16,384-distinct pilot regressed by 1.1%. The new path is therefore opt-in.

**1. Batch inversion: implemented and tested**

For each lookup, we need a quotient such as

\[
q_i=\frac{1}{z-X_i-\alpha Y_i}.
\]

We now compute inverses in batches of 4,096. At \(N=1,048,576\) requests and a 200,000-entry table, this reduces **1,248,576 individual inversions to 305 batch inversions**, with additional field multiplications.

Every quotient remains checked inside the circuit. The hint is untrusted, and the constraint count is unchanged.

The qualification: implementing this also changed constraint orientation. Consequently, we cannot credit the measured runtime improvement entirely to batch inversion. The structural investigation below explains an important part of the gain.

**2. The \(3N \to N\) optimization: implemented and validated**

These equations enforce the same relation:

q_i(z-X_i-t_i)=1

(z-X_i-t_i)q_i=1.

But their placement in the R1CS matrices can change Groth16’s expensive G2 multiscalar multiplication.

Putting the quotient on the appropriate side reduces the activation-dependent contribution from approximately **\(3N\) columns to \(N\)**.

**3. Tables sized to distinct values: implemented, with certification costs included**

Your observation is correct: **a batch containing 16,384 distinct inputs needs only 16,384 distinct input/output pairs for its membership proof.**

The remaining question is how we establish that those pairs contain correct exponential outputs.

| Situation | Required treatment |
|---|---|
| A fixed, known 16,384-value allowed domain | Compile that smaller table directly |
| A batch-selected dictionary | Prove that its entries implement the exponential function |
| An identical dictionary already certified | Reuse its certificate |

We implemented two ways to certify a batch-selected dictionary:

- **Within the same proof:** validate each distinct pair using the factorized exponential gadget.
- **Separate certificate:** certify the dictionary against the full function, then prove the requests use that dictionary.

For the separate-certificate implementation, the verifier binds both proofs to the **same ordered dictionary**. Tests explicitly reject a valid membership proof containing consistently false exponential outputs.

With \(U=16,384\):

| Requests \(N\) | Optimized full table | Compact table, fresh certificate included | Compact usage, certificate already available |
|---:|---:|---:|---:|
| 262,144 | 2.92 s | 3.56 s | 2.67 s |
| 1,028,096 | 9.73 s | **7.67 s** | 6.82 s |
| 1,048,576 | 10.13 s | 10.05 s | 9.24 s |

This reveals two important effects:

- **At 1,048,576 requests, fresh certification is effectively a tie.** The difference is too small to call a reliable improvement.
- **At 1,028,096 requests, the smaller table halves the FFT domain**, from \(2^{22}\) to \(2^{21}\). That produces the **21.2% improvement**, even after paying for a fresh certificate.

Thus, table capacity and batch size should be optimized together. Choosing a power-of-two request count alone can be inefficient because table and circuit overhead push the actual constraint count into the next FFT domain.

This also applies to the factorized approach, with an important distinction: its constant factor tables contain only **\(50+50+80=180\) entries**. Our 16,384-value samples occupied all 180, so those tables could not shrink. We did shrink the dictionary of complete input/output pairs.

That factor-certified dictionary took **10.65 s** at one million requests and 16,384 distinct inputs—slower than the optimized full table. With only 64 distinct inputs, grouped methods were better: approximately **9.52–9.64 s**. Smaller dictionaries help, but their validation cost determines the crossover.

**4. GKR for the lookup sum: implemented and evaluated**

We implemented a fractional-sum tree, combining fractions through

\[
\frac{a}{b}+\frac{c}{d}=\frac{ad+bc}{bd},
\]

and verifying its GKR proof inside Groth16.

Small proof round trips and adversarial tests passed. However, the large-table compile screen already required **1,710,544 constraints for just 1,024 requests** against the 200,000-entry table.

The generic embedding carries substantial costs for binding the intermediate values into the outer proof. **This version is not a promising replacement for the optimized direct lookup.** We did not run or claim a large-table GKR latency benchmark.

That result concerns this implementation; it does not establish that a native lookup/GKR backend sharing commitments with the surrounding model would perform poorly.

For very large LLM workloads, I would use the findings as follows:

- Keep the inversion batching and measured constraint-orientation improvements.
- Select dictionary capacity from actual distinct quantized inputs, using reusable circuit shapes.
- Choose request chunk sizes from **compiled constraint counts and FFT boundaries**.
- Count fresh dictionary certification unless identical-dictionary reuse is actually established.
- Measure real activation traces before choosing between full-table and grouped approaches.

The numerical function stayed unchanged: the same 200,000-point input grid, the same integer outputs, and 40 fractional output bits. A 16,384-entry dictionary does **not** reduce input precision.

All reported timings are three-trial medians on eight CPU threads, including witness construction, proving, and verification, with setup excluded. They use synthetic repeated inputs and public input/output statements. Private wrappers were tested, but **private compact-table composition and complete LLM proof latency remain unmeasured**.

Finally, while multiple lookup input columns can be batched for a single lookup table in LogUp, batching multiple lookup types (range bounds in this case) is impossible with LogUp, afaik.On the contrary, one can batch many lookup types and verify them via a single primary (collation) sum check and two grand product argument GKRs.
