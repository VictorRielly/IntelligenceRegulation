**Yes—grouping the repeated values first is sensible, and it could replace our current two-lookups-per-request design.** My earlier wording was too strong: we need to account for all \(N\) original entries, but we do **not** inherently need \(N\) separate cryptographic lookup checks.

Your proposed \(O(N\log m)\) grouping is reasonable. With hashing, we can even construct the groups in expected \(O(N)\), then sort the \(m\) distinct keys in \(O(m\log m)\). The question is how to prove that those groups faithfully represent the original inputs and outputs.

Suppose we want to prove

\[
y_i=F(x_i),\qquad i=1,\ldots,N,
\]

where \(F\) is our precisely specified quantized exponential.

We can construct a dictionary of distinct inputs, their outputs, and occurrence counts:

\[
(u_j,v_j,n_j),\qquad j=1,\ldots,m.
\]

Then prove just two things:

1. **Dictionary correctness:** \(v_j=F(u_j)\) for the \(m\) dictionary entries.
2. **Batch consistency:** the original pairs \((x_i,y_i)\) are exactly the dictionary pairs \((u_j,v_j)\), repeated according to the counts \(n_j\).

The second step can be **one batched multiset/permutation argument**. Permutation arguments and batched lookups are established ways to express this kind of consistency. genui{"citation":{"refs":["turn73view1","turn73view0"]}}

For example, schematically, compress each pair using a random challenge \(\alpha\):

\[
a_i=x_i+\alpha y_i,\qquad b_j=u_j+\alpha v_j.
\]

Then check, at another random challenge \(z\),

\[
\boxed{
\prod_{i=1}^{N}(z-a_i)
=
\prod_{j=1}^{m}(z-b_j)^{n_j}.
}
\]

Along with nonnegative integer counts satisfying \(\sum_j n_j=N\), this expresses the desired multiset equality.

The vectors, dictionary, and counts must be committed **before** the challenges are chosen, and the product claims must be proved against those commitments. This equation is the algebraic idea, not by itself a complete ZK protocol.

**Crucially, we group input/output pairs together.** Checking the input histogram and output histogram independently would allow a prover to attach correct output values to the wrong inputs.

The original tensors can remain in their original order for the surrounding model. Sorting is an auxiliary witness operation; we do not have to reorder the actual neural-network computation.

**What does this buy us?**

It separates the work into

\[
\underbrace{m\,C_F}_{\text{expensive function checks}}
+
\underbrace{\text{one batch-consistency argument}}_{\text{processes the original }N\text{ entries}}.
\]

For the product formulation:

- The left side has \(N\) factors.
- The compressed right side can use roughly \(O(m\log N)\) multiplications through repeated squaring, with additional count constraints.
- We avoid separately looking up both the dictionary input and dictionary output for every request.

An alternative is the logarithmic-derivative identity

\[
\sum_{i=1}^{N}\frac{1}{z-a_i}
=
\sum_{j=1}^{m}\frac{n_j}{z-b_j}.
\]

This is particularly attractive for a GKR/sumcheck implementation: it gives a linear-size algebraic representation and supports reducing auxiliary commitment work. The Papini–Haböck construction specifically develops GKR-based fractional sumchecks for this purpose. genui{"citation":{"ref":"turn73view2"}}

**So your objection identifies a real optimization opportunity.** Our current cost of approximately \(6N+\text{dictionary work}\) is an implementation cost, not a lower bound.

What sorting cannot do is establish consistency by examining only the \(m\) representatives: a dishonest prover could construct a correct small dictionary and omit an incorrect original entry. Some authenticated check must still involve the original vector. But that check can be a cheap batched computation, rather than our current pair of lookup arguments per request.

Also, \(O(N\log m)\) is still linear in \(N\) when \(m\) is fixed. Its advantage would be reducing expensive proof operations, rather than making total processing sublinear in the input length.

**I would now prioritize comparing a joint-pair multiplicity argument and a sorted/permutation argument against our existing cache.** Your idea targets exactly the remaining bottleneck. We have not measured those formulations yet, so the previous latency results should not be interpreted as the best achievable performance for repeated values.

**My strongest recommendation is a GPU-native tensor proof system that proves complete activations through shared lookup arguments, reuses the surrounding model’s commitments, and fuses normalization with the operations that consume it.** I would keep your factored exponential construction for domains too large to tabulate directly.

That is the best direction I can justify from our measurements and the literature. **Making nonlinearities less than 5% of total proving time is a useful target, but we have not established that it is achievable.** Matrix multiplication proofs can themselves be extremely efficient, so the fact that matrix multiplication dominates inference FLOPs does not mean it will dominate proof time.

I would build the system as follows.

**1. Make the unit of optimization a complete activation, rather than an exponential.**

| Operation | My preferred proof representation |
|---|---|
| Sigmoid, SiLU, GELU | One lookup for the complete quantized input/output relation |
| SwiGLU | One SiLU lookup, followed by a multiplication integrated into the surrounding tensor proof |
| Softmax attention | Exponential-weight lookups, weighted reduction, and normalization of the resulting outputs |
| RMSNorm | One scalar inverse-square-root relation per token, followed by batched vector multiplication |

For example, prove

\[
(x,y)\in\mathcal T_{\mathrm{SiLU}},
\qquad
\mathcal T_{\mathrm{SiLU}}
=\{(u,\operatorname{Quantize}(\mathrm{SiLU}(u)))\},
\]

instead of separately proving an exponential, addition, division, multiplication, and their intermediate roundings.

With a **16-bit activation input encoding**, this table has at most 65,536 entries—even if its outputs require more bits. The important qualification is that reducing the preceding matrix accumulator to that encoding must also be proved. We cannot move an expensive rounding operation outside the statement and call it eliminated.

Our latest experiment supports prioritizing this approach: the direct table beat cached factors **3.48 seconds versus 6.12 seconds** at 262,144 evaluations. That measured exponentials, not complete SiLU, but it identifies the direction worth testing.

**2. Pay for connecting activations to the model only once.**

This is probably the most important architectural change.

The matrix multiplication proof already needs to bind its output tensor. The activation proof should consume that same committed tensor, and its output should become the next operator’s input. We should avoid separate activation-vector hashes, duplicate commitments, and independently proved copies.

For the lookup layer, my first implementation choice would be **a GKR-LogUp-style argument integrated with the tensor sumchecks**. Its appeal is reduced auxiliary commitment work: the underlying construction can reduce additional committed lookup data to the table multiplicities. This is a concrete reason to investigate it, not a guarantee that it beats every alternative. genui{"citation":{"ref":"turn72view0"}}

Queries would include the function and numerical-contract identifier:

\[
(\text{function/scale identifier},\,x_i,\,y_i).
\]

Compatible queries could then share lookup arguments and table preprocessing across layers and chunks. The protocol must still connect every query to the correct tensor position; grouping them does not remove that obligation.

Tensor-level sumchecks, batching, and avoiding unnecessary committed intermediates are also central to Jolt Atlas’s design. genui{"citation":{"ref":"turn70view1"}}

**3. Use repetition through lookup multiplicities, without adding an expensive second dictionary layer by default.**

A fixed public activation table already contains every permissible result. A multiplicity vector records how often each entry is used.

That gives us the useful part of repetition:

- Table-side work depends on the domain and occupied entries.
- Repeated transcendental calculations disappear.
- All requests share the same authenticated function definition.

The request side still has to process \(N\) inputs. Our current private cache adds another selection layer, which explains why it can lose to a direct table despite enormous repetition.

Your factorization remains valuable when the precision makes the full domain enormous. In that case I would use it **inside a structured-table lookup construction**, rather than expanding digit selection, products, and rounding into a generic circuit for every request. TaSSLE specifically targets decomposable tables while minimizing commitment costs. genui{"citation":{"ref":"turn70view4"}}

There is also a relevant recent preprint: for **Shout-style one-hot lookups**, it argues that the per-query proving work depends on the access pattern, rather than the activation table’s values. That is a result about a particular protocol family, but it reinforces our experimental finding that cheaper table construction alone does not solve the dominant request cost. genui{"citation":{"ref":"turn70view0"}}

**4. Fuse softmax into attention, if the numerical specification permits it.**

The relation I would target is

\[
E_{ij}=\exp(S_{ij}-m_i),\qquad
D_i=\sum_jE_{ij},\qquad
Z_{ic}=\sum_jE_{ij}V_{jc},
\qquad
O_{ic}=Z_{ic}/D_i.
\]

This avoids producing and normalizing every intermediate attention probability when the model only consumes the weighted result.

The normalization count changes from approximately

\[
O(T^2)\quad\text{to}\quad O(Td_v)
\]

per head. That is a structural improvement whose benefit grows with sequence length. Exponential membership and the weighted matrix product still remain.

However, moving normalization past a sum **changes finite-precision rounding**. I would adopt this only as an explicitly specified, accuracy-validated model implementation. If we require identical outputs to an existing sequence of rounded operations, we must preserve those operations or prove their exact equivalent.

The broader principle has precedent: zkLLM integrates rescaling with activation lookups and designs a specialized attention argument instead of treating all nonlinear steps as independent generic circuits. genui{"citation":{"ref":"turn71view4"}}

**5. Spend precision where the model needs it, and measure the entire block.**

I would optimize the activation *input address width*, intermediate rounding rules, and normalization precision separately. A blanket “use fewer bits everywhere” policy is unlikely to be best.

The next decisive benchmark should be **one complete transformer block at the actual 8B dimensions**, with private tensors, matrix proofs, commitments, range checks, and normalization included. It should compare:

- Complete-function tables.
- Your factored tables.
- Low-degree or piecewise-polynomial approximations at matched model accuracy.

The polynomial comparator matters: multiplication is cheap in a tensor proof, so a sufficiently low-degree approximation could beat lookup selection. Its interval checks and rescaling must be included in the comparison.

I would define “insignificant” concretely as

\[
\frac{T_{\mathrm{nonlinear}}}
     {T_{\mathrm{other}}+T_{\mathrm{nonlinear}}}<5\%,
\qquad\text{equivalently}\qquad
T_{\mathrm{nonlinear}}<\frac{T_{\mathrm{other}}}{19}.
\]

For illustration, if everything else takes 300 seconds, nonlinear processing gets **15.8 seconds**. For the approximately 369 million activation sites in our 8B/512-token workload, that corresponds to roughly **23 million sites per second**, including their associated proof overhead. This is a design requirement, not a performance prediction.

**My first engineering investment would therefore be the shared tensor/lookup backend and a complete SiLU proof integrated into one transformer block.** That experiment will tell us whether lookup binding, commitments, rounding, or arithmetic remains dominant. Your exponential factorization should be an adaptive option within that system; making it the organizing principle of every activation proof is unlikely to deliver the smallest total runtime.

**Problem:** Computing the exponentiation requires a bit-decomposition of $m_i$ --- ## Logarithmic Derivative $$ \prod_{i = 1}^n (X - a_i) = \prod_{i = 1}^n(X - b_i)^{m_i} $$ Apply $\log()$ on both sides: $$ \sum_{i = 1}^n \log(X - a_i) = \sum_{i = 1}^n m_i \cdot \log(X - b_i) $$ Take the derivative: $$ \sum_{i = 1}^n \frac{1}{X - a_i} = \sum_{i = 1}^n \frac{m_i}{X - b_i} $$ &rarr; Turns a product of polynomials into a sum of fractions! --- ## LogUp - Commit to vectors $A, B$ and the multiplicities $M$ - Commit to a *helper* vector $H$ with $h_i := \frac{1}{\beta - a_i} - \frac{m_i}{\beta - b_i}$ - Prove that $H$ is formed correctly (via a polynomial identity) - $\forall i: h_i \cdot (\beta - a_i) \cdot (\beta - b_i) = (\beta - b_i) + m_i \cdot (\beta - a_i)$ - Run a *sum-check* to prove that $\sum_{i = 1}^n h_i = 0$ - Batching multiple lookups with the same right-hand side is efficient, but might require more helper vectors to keep the degree of the identity low ---- ## LogUp + GKR - **Idea**: Instead of having to commit to the helper vector $H$, compute the fractional sum directly using GKR! - Fractions are represented as tuples $(num, den)$ and updated as: $\frac{num_1}{den_1} + \frac{num_2}{den_2} = \frac{num_1 \cdot den_2 + num_2 \cdot den_1}{den_1 \cdot den_2}$ - &rarr; computing a sum of size $n$ can be implemented in a *layered* arithmetic circuit of depth $O(\log n)$ ---- ## cq (= "Cached Quotients") Main achivement: Look up $n$ elements into a table of size $N$ in $O(n \log n)$ time (requiring $O(N \log N)$ preprocessing time) - Instantiation of LogUp in the *univariate* (instead of *multivariate*) setting using KZG commitments - Multivariate sum-check &rarr; univariate sum-check - Multivariate zero-check &rarr; univariate zero-check - They use use one helper polynomial for each column ($h_A$ and $h_B$) **where the degree of $h_A$ is smaller than the degree of $h_B$** - But $h_B$ is *sparse*, so its commitment can be computed in size $O(n)$ by adding pre-computed (homomorphic) commitments to Lagrange polynomials - Also, the quotient polynomial required for the zero-check is sparse, but in a different basis that can be pre-computed! At hundreds of millions of requests on the same 200,000-point grid, distinct inputs would saturate near 200,000. But actual model activations may use different scales, ranges, or function parameters, so we cannot assume one shared cache across the whole model.

- Matching one or two bin coordinates allows reuse of partial factors. Our public tables already provide much of that reuse.
- Matching the **complete tuple** allows reuse of the entire exponential output.
- Equal exponential inputs in different softmax rows generally **do not produce equal normalized probabilities**, because their denominators differ.

**Why doesn’t that make the cached implementation win?**

Let \(W\) denote factor-selection, multiplication, and rounding work per value; \(K\) the allocated cache capacity; and \(U\le K\) the actual distinct count. The approximate constraint costs are

\[
\begin{aligned}
C_{\text{factors}}&=O(NW+\text{factor tables}),\\
C_{\text{cached}}&=O(N+KW+\text{factor tables}),\\
C_{\text{full table}}&=O(N+M).
\end{aligned}
\]

Caching removes repeated factor work. It still has to connect **every ordered request** to the correct dictionary entry.

Our current cache uses two lookup arguments: one for the dictionary input and one for its output. The full-table baseline needs one. The measured marginal costs are approximately:

- **Cached factors:** 6 constraints per additional request.
- **Full table:** 3 constraints per additional request.

Once \(N\) dominates the fixed table cost, that difference matters more than storing 180 versus 200,000 constants.

I also fixed an implementation inefficiency: cached witness construction previously recomputed factors while filling every output. It now reuses the dictionary’s computed outputs.

**There are three ways to improve scaling beyond a coefficient.**

1. **Improve scaling with precision.**  
   For a \(b\)-bit input domain, a full table has \(2^b\) entries. Splitting into \(k\) balanced factors reduces storage to roughly
   \[
   k\,2^{b/k}.
   \]
   This is a genuine improvement in dependence on precision. It does not eliminate the work of binding \(N\) requests.

2. **Change the lookup and proof backend.**  
   Our implementation expands the computation into a generic Groth16 circuit, which incurs transform costs roughly proportional to \(C\log C\). A suitable sumcheck and structured-lookup implementation offers a route toward linear or near-linear online work. Lasso and TaSSLE are relevant because they exploit structured or decomposable tables; our shallow-product GKR experiment did not implement their lookup machinery. genui{"citation":{"refs":["turn68view1","turn68view2","turn68view3"]}}

   The comparator must improve too: cq moves table-dependent work into preprocessing, with \(O(M\log M)\) preprocessing and \(O(N\log N)\) online work. Our generic full-table circuit is therefore not the strongest possible direct baseline. genui{"citation":{"ref":"turn68view0"}}

3. **Prove the activation’s consumer without materializing every intermediate.**  
   For attention,
   \[
   O_c=\sum_j\frac{P_j}{D}V_{jc}
      =\frac{\sum_jP_jV_{jc}}{D},
   \qquad D=\sum_jP_j.
   \]
   We could normalize the resulting channels rather than every attention probability. This changes normalization counts from \(O(T^2)\) to \(O(Td_v)\).

   At \(T=512,d_v=128\), choosing the cheaper approach per causal row reduces normalization operations from **131,328 to 57,408 per head**. The advantage grows with sequence length. It does not remove exponential lookups or matrix products.

   This fusion changes finite-precision rounding. I derived an error bound and checked 400 numerical output cases, but **have not implemented or timed a fused-attention proof**.

For a new, explicit vector of \(N\) inputs and outputs, the complete system still has to process those \(N\) entries somewhere. The realistic targets are to make expensive function work depend on \(U\), reduce dependence on precision, remove backend overhead, and avoid unnecessary intermediate outputs.

The useful changes were:

1. **Apply your inequality idea directly.** For exact normalization, derive and range-check
   \[
   R_i=QP_i-Y_iD,\qquad H_i=D-1-R_i.
   \]
   This removes redundant witness variables and defining equations. Multiplication constraints and componentwise range checks remain necessary. Combined with factor-table fusion, this reduced constraints by **16.7% while preserving every output**.

2. **Share one reciprocal across each softmax row.** Prove
   \[
   Z=\left\lceil\frac{2^{B+p}}D\right\rceil,\qquad
   Y_i=\left\lfloor\frac{P_iZ}{2^B}\right\rfloor.
   \]
   This replaces two wide range checks per output with one, plus checks shared across the row. The complete optimized public circuit uses **41% fewer constraints** at 16k inputs.

3. **Merge two factor axes.** This reduces factor lookups from three to two per input and removes one multiplication, using exact products of the existing constants.

4. **Offer Poseidon2 for private commitments.** This proved especially important:

   | Private configuration, 16,384 evaluations | Median proving time |
   |---|---:|
   | Original arithmetic + MiMC | 10.57 s |
   | Optimized arithmetic + MiMC | 10.42 s |
   | Optimized arithmetic + Poseidon2 | **4.26 s** |

   Arithmetic savings alone barely helped private proving. Changing the commitment hash addressed the dominant remaining cost. Poseidon2 is optional and requires a different expected commitment.

The reciprocal method has a **different rounding rule**. In an independent audit of 2,097,152 values, 43 outputs differed from exact-floor normalization, each by one output unit. Its normalization error remains below \(2^{-32}\) relative to the finite-weight probabilities; table and input quantization errors are separate. The exact-output option remains available.

**Yes—we can express the range conditions exactly as \(a\le Ab\le c\), and we can prove the whole collection with one aggregated argument.** The distinction is between making the *proof* compact and making the *prover’s computation* cheap. Matrix structure can help with both, but it does not automatically eliminate the work needed to establish each bound.

Here is how your idea applies to our normalization problem.

For one softmax row, recall that

\[
D=\sum_i P_i,\qquad
QP_i=DY_i+R_i,\qquad
0\le R_i<D.
\]

The last inequality establishes correct downward rounding.

Collect the remainders into a vector \(r\), and define

\[
b=
\begin{pmatrix}
r\\D
\end{pmatrix},
\qquad
A=
\begin{pmatrix}
I&0\\
-I&\mathbf 1
\end{pmatrix}.
\]

Then

\[
Ab=
\begin{pmatrix}
r\\
D\mathbf1-r
\end{pmatrix}.
\]

Consequently, the required inequalities are simply

\[
\boxed{
\begin{pmatrix}
\mathbf0\\
\mathbf1
\end{pmatrix}
\le
Ab.
}
\]

The first block says \(R_i\ge0\); the second says \(D-R_i\ge1\), which is precisely \(R_i<D\) for integers.

If we have a proven bound \(D\le D_{\max}\), we can give it exactly your two-sided form:

\[
\boxed{
\underbrace{\begin{pmatrix}\mathbf0\\\mathbf1\end{pmatrix}}_{a}
\le
Ab
\le
\underbrace{\begin{pmatrix}
(D_{\max}-1)\mathbf1\\
D_{\max}\mathbf1
\end{pmatrix}}_{c}.
}
\]

For many softmax rows, we repeat this structure in blocks. **The matrix is highly structured: applying it requires copying and subtracting vectors, not performing a dense matrix multiplication.**

We must still prove the quotient identities \(QP_i=DY_i+R_i\). If both \(D\) and \(Y_i\) are secret, those contain genuine multiplications; the matrix reformulation does not turn the entire computation into a fixed public linear system.

Now, how do we prove \(a\le Ab\le c\) collectively?

Define two slack vectors:

\[
u=Ab-a,\qquad v=c-Ab.
\]

Our task becomes proving

\[
u\ge0,\qquad v\ge0,
\]

together with the linear relations defining them. Assuming bounded integer representations and no modular wraparound, this is equivalent to the original inequalities.

Choose a bit length \(\ell\) sufficient for the slacks. Arrange their binary representations into a matrix \(Z\), and write

\[
\begin{pmatrix}u\\v\end{pmatrix}
=
Z
\underbrace{\begin{pmatrix}
1\\2\\4\\\vdots\\2^{\ell-1}
\end{pmatrix}}_{w},
\qquad
Z_{ij}\in\{0,1\}.
\]

This gives us exactly the kind of structure you are proposing:

- Matrix–vector equalities reconstruct every slack.
- One collection of Boolean conditions establishes that all the reconstructed quantities are nonnegative bounded integers.

The Boolean conditions themselves can be written as a Hadamard product:

\[
\boxed{Z\odot(Z-\mathbf1)=0.}
\]

So we have transformed many comparisons into **linear algebra plus a batched multiplication relation**.

That is a useful transformation.

We can then aggregate the Boolean conditions cryptographically. Flatten \(Z\) into a vector \(z\). After committing to \(z\), obtain independent random field coefficients \(\lambda_j\), and prove

\[
\boxed{
\sum_j\lambda_j z_j(z_j-1)=0.
}
\]

If any entry is not a bit, the vector of errors \(z_j(z_j-1)\) is nonzero. For a fixed committed vector, a uniformly random linear combination equals zero with probability only \(1/p\), where \(p\) is the field size.

The reconstruction equalities can also be aggregated. An inner-product or polynomial protocol can prove the resulting relations succinctly, without sending every bit to the verifier. Commitments, challenge ordering, and hiding are necessary parts of the complete zero-knowledge protocol.

**This is closely related to how aggregated range proofs already work.** Bulletproofs, for example, combines bit constraints and reconstruction constraints into an inner-product argument. Its aggregated proof size grows logarithmically with the total number of represented bits, while standard proving and verification work remains linear in that number. genui{"citation":{"refs":["turn52view0","turn52view1"]}}

There is one tempting shortcut that does **not** work: aggregating the inequalities themselves.

For example, suppose we need

\[
0\le x_1,x_2\le1.
\]

Replacing these with

\[
0\le x_1+x_2\le2
\]

accepts the invalid vector

\[
(x_1,x_2)=(-1,2).
\]

Checking an average or a small number of weighted inequalities can similarly hide individual violations. Random linear combinations are effective for **equalities that should each be zero**. To apply that technique to inequalities, we first need a sound encoding—such as bounded slacks and Boolean digits—that converts each inequality into equalities.

That encoding is where much of the work remains.

For our implementation, your proposal therefore has three different implications:

| Change | Likely consequence |
|---|---|
| Rewrite the existing constraints as \(a\le Ab\le c\) | Cleaner formulation; essentially unchanged proving cost |
| Use one specialized argument for all bounded linear relations | Potentially lower overhead and better use of shared structure |
| Replace all bounds with a few bounds on sums or projections | Does not establish every individual inequality |

Our current implementation already batches all range-check limbs into one lookup argument, and the final SNARK is already one proof. We are not paying for thousands of separate proof objects. To obtain a substantial speedup, we would need a more efficient way to prove the *contents* of that aggregated statement.

There is also a practical tradeoff: our current range checker represents a 144-bit remainder using nine 16-bit limbs. A straightforward Boolean formulation introduces 144 bits instead. An inner-product protocol can compress the proof of those bits, but the prover still processes them. It could outperform our current backend, but that requires measurement; aggregation alone does not guarantee it.

**The direction I would investigate is a single structured argument for the entire normalization batch.** It would jointly prove:

\[
\begin{aligned}
D_k&=\sum_{i\text{ in row }k}P_i,\\
T_i&=Y_iD_{\operatorname{row}(i)},\\
R_i&=QP_i-T_i,\\
H_i&=D_{\operatorname{row}(i)}-1-R_i,
\end{aligned}
\]

with all \(Y_i,R_i,H_i\) in their required ranges.

The denominator is shared within each row; the linear maps are sparse and repetitive; the products form one Hadamard relation; and the bounds form one aggregated range statement. A protocol designed around that structure could reduce overhead compared with translating everything into our current general-purpose circuit.

Your matrix formulation is therefore a sound basis for a better protocol. The remaining research question is **whether we can prove membership in that bounded region more cheaply than our already-batched limb lookups**, while binding the same values to the exponential calculation.

=====

Your intuition about multiplication is correct: **once we have the right factors, multiplying them is cheap to prove.** The more expensive work is establishing that we selected the right factors, and that the resulting integers represent correctly rounded real numbers.

There are also two different operations we have called “normalization”: rescaling a fixed-point exponential, and dividing by the sum in softmax. We can avoid the first in some cases; the second needs more care.

Let’s follow one value through the [current circuit](sandbox:/workspace/scratch/4ee9dfa745a9/expzk/softmax.go).

**First, lookup selection connects your input to the correct factors.**

Our three-dimensional example represents inputs as

\[
x=-10+\frac{n}{10{,}000},
\qquad 0\le n<200{,}000.
\]

We split the integer index into three digits:

\[
n=d_0+50d_1+2500d_2,
\]

where \(d_0,d_1<50\) and \(d_2<80\).

For your example \(x=8.8679\):

\[
n=188679=29+50(23)+2500(75).
\]

Consequently,

\[
8.8679=0.0029+0.115+8.75,
\]

and

\[
e^{8.8679}=e^{0.0029}e^{0.115}e^{8.75}.
\]

With fixed-point scale \(S=2^{40}\), we store three small tables:

\[
\begin{aligned}
A[d]&=\left\lfloor S e^{d/10{,}000}\right\rfloor,\\
B[d]&=\left\lfloor S e^{50d/10{,}000}\right\rfloor,\\
C[d]&=\left\lfloor S e^{-10+2500d/10{,}000}\right\rfloor.
\end{aligned}
\]

The prover supplies the digits and retrieves \(A[29],B[23],C[75]\). The proof must establish:

1. The digits reconstruct the original input index.
2. Each retrieved value belongs to its claimed index in the appropriate table.
3. The output weight is their product.

The third step takes just two multiplication constraints:

\[
P=A[29]B[23]C[75]\approx S^3e^{8.8679}.
\]

But those multiplications alone would also accept the product of three *incorrectly selected* factors. Lookup selection prevents that.

Importantly, we prove membership of **\((\text{index},\text{value})\) pairs**. Proving merely that a value appears somewhere in the table would not establish that it corresponds to the input.

**We already batch the lookup checks.**

The implementation does ordinary memory reads while generating the witness, then proves all the recorded reads together. It does not scan the entire table separately for each input. The lookup gadget’s work scales linearly with table size plus query count. genui{"citation":{"ref":"turn50view0"}}

Here is the central idea behind that batch proof.

Randomly compress each table pair and each claimed pair into one field element:

\[
t_j=j+\alpha T[j],
\qquad
q_i=d_i+\alpha v_i.
\]

Let \(m_j\) be the number of times table entry \(j\) was requested. Schematically, the argument checks

\[
\boxed{
\sum_i\frac{1}{\beta-q_i}
=
\sum_j\frac{m_j}{\beta-t_j}
}
\]

for unpredictable challenges \(\alpha,\beta\), after the relevant witness data has been committed.

If a table entry was requested 100 times, its 100 identical fractions on the left become one fraction multiplied by 100 on the right. An invalid query introduces a denominator that cannot generally be matched by table entries. Random challenges make an invalid batch pass only with a small soundness error, under the protocol’s assumptions. This is the logarithmic-derivative approach to lookup arguments. genui{"citation":{"ref":"turn50view1"}}

For our three tables and \(N\) exponentials, the lookup work is therefore roughly proportional to

\[
\underbrace{50+50+80}_{180\text{ table entries}}
+\underbrace{3N}_{\text{queried pairs}}.
\]

Your tensor factorization makes the table component extremely small. **The remaining query component connects every input to its selected tensor cell.** Adding tensor dimensions can shrink the tables further, but also adds another lookup and multiplication per input.

**Next, consider the two kinds of normalization.**

For a standalone exponential, we might want an output at scale \(S\), rather than the product’s scale \(S^3\):

\[
E=\left\lfloor\frac{P}{S^2}\right\rfloor.
\]

We prove that using a remainder:

\[
P=S^2E+r,\qquad 0\le r<S^2.
\]

Because \(S^2\) is a power of two, the computation is just a bit shift. However, proving correct truncation still requires establishing that the discarded remainder has the appropriate size.

For softmax, we can skip this intermediate truncation:

\[
p_i
\approx
\frac{P_i/S^3}{\sum_j P_j/S^3}
=
\frac{P_i}{\sum_jP_j}.
\]

That is our “deferred” variant. The common scale cancels.

However, the stored integers \(P_i\) are still large. Cancellation does not automatically reduce the bit widths needed to prove the subsequent division.

**Softmax normalization proves a rounded integer quotient.**

For each row, we compute the shared denominator

\[
D=\sum_jP_j.
\]

At probability scale \(Q=2^{32}\), the specified output is

\[
Y_i=\left\lfloor\frac{QP_i}{D}\right\rfloor,
\qquad
\widehat p_i=\frac{Y_i}{Q}.
\]

The sum defining \(D\) is linear arithmetic. The expensive part is establishing the quotient and its rounding.

For each output, the prover supplies a remainder \(R_i\) and a nonnegative slack \(H_i\), and proves

\[
\boxed{QP_i=Y_iD+R_i}
\]

and

\[
\boxed{D-1=R_i+H_i}.
\]

The second equation, together with nonnegative \(R_i,H_i\), establishes

\[
0\le R_i<D.
\]

That makes \(Y_i\) the correct floor quotient.

For example, take weights \([2,3,5]\), so \(D=10\), and use the small scale \(Q=16\). For the middle weight:

\[
16\cdot3=4\cdot10+8.
\]

Thus \(Y=4\), \(R=8\), and \(H=1\), because \(10-1=8+1\). Its represented probability is \(4/16\).

Across the row, the outputs are \([3,4,8]/16\). They sum to \(15/16\): independent downward rounding need not preserve an exact sum of one.

Why can’t we just multiply by \(D^{-1}\)? Because **division in the proof’s finite field does not mean rounded real division**. A modular inverse gives a field element; it does not establish that the result is a small integer encoding a probability.

Range bounds, along with bounds preventing modular wraparound, make these field equations correspond to the intended integer calculation.

**Most of the normalization overhead comes from proving those bounds—and those checks themselves use lookups.**

To prove an integer is within a range, our backend splits it into small chunks, called limbs. For example,

\[
R=r_0+2^{16}r_1+2^{32}r_2+\cdots
\]

and proves each limb belongs to

\[
\{0,\ldots,65535\}.
\]

It also proves that the limbs reconstruct \(R\). These limb lookups are batched together.

Tracing the implementation for our **16,384-input, three-factor deferred benchmark** gives:

| Quantity checked per output | Allowed bits | 16-bit limb lookup claims |
|---|---:|---:|
| Remainder \(R_i\) | 144 | 9 |
| Slack \(H_i\) | 144 | 9 |
| Output \(Y_i\) | 33 | 4 |
| **Total** | | **22** |

The 33-bit output needs three ordinary limbs plus an extra check restricting the top limb to one bit.

Compare that with just **three exponential-factor lookup claims per input**:

- Exponential selection: **49,152 pair lookups**.
- Normalization bounds: **360,448 scalar limb lookups**.

These claims have different costs, so the counts are not directly timing ratios. Nevertheless, the backend’s constraint formula attributes approximately **475,137 of 674,540 constraints—about 70%—to the normalization range-check machinery**. This is a code-derived count, not a measured runtime breakdown.

There are only 180 exponential constants, but this configuration also uses a 65,536-entry table for checking integer limbs.

That suggests several concrete optimization directions.

**A small improvement that preserves our existing outputs: tighten the probability bound.**

Our generic circuit allows 33 bits because a one-element softmax row produces \(Y=2^{32}\).

For a row containing at least two strictly positive weights,

\[
P_i<D
\quad\Longrightarrow\quad
Y_i<2^{32}.
\]

Thus our 512-element rows need only 32 bits. With the current limb layout, that reduces the output range check from four lookup claims to two.

At 16,384 inputs, the predicted saving is **32,768 constraints, about 4.9% of the current total**. This is a concrete candidate for the next test; it is not yet a measured speedup.

**A larger opportunity: normalize the attention result instead of every probability.**

If softmax immediately feeds an attention weighted sum, then over real arithmetic

\[
o_k
=\sum_i\frac{P_i}{D}v_{ik}
=\frac{\sum_iP_iv_{ik}}{D}.
\]

We could prove the numerator and normalize once per output coordinate.

For a 512-entry attention row with head dimension 128, that changes **512 rounded divisions into 128**. The weighted sums still need proving, so this does not imply a fourfold overall speedup.

There is a significant numerical distinction: rounding each probability before the weighted sum generally differs from rounding only the final ratio. This optimization needs an agreed numerical specification and error bound.

**For lookup selection itself, exploit the tensor structure inside the lookup protocol.**

Our current implementation uses your factorization with ordinary batched lookups. A more specialized argument could handle the implicit tensor table directly and reduce commitment overhead. Decomposable-table protocols such as TaSSLE specifically address avoiding construction or commitment of an entire structured table. Our multiplication-only GKR experiment does not implement that lookup optimization. genui{"citation":{"ref":"turn50view2"}}

Grouping repeated inputs can also help, but we must still prove which original inputs belong to each group. Sorting or binning moves that obligation into a mapping or permutation proof; it does not remove it.

Finally, we can reduce intermediate bit widths by allocating precision differently among factors. The present three-factor construction carries roughly 120 bits of common fixed-point scale into normalization. Lowering that precision can reduce range-check work, provided we certify the resulting approximation error.

I would prioritize the exact 32-bit bound improvement first, then investigate fused attention normalization. The latter attacks the largest source of repeated work we have identified, while a structured lookup implementation targets the remaining cost of connecting inputs to your tensor.

Your three-vector construction is mathematically sound. Write a grid index as

\[
n=i+r_1j+r_1r_2k,\qquad x=a+\Delta n.
\]

Define three vectors:

\[
A_i=e^{\Delta i},\qquad
B_j=e^{\Delta r_1j},\qquad
C_k=e^{a+\Delta r_1r_2k}.
\]

Then the exponential grid is the rank-one tensor

\[
T_{ijk}=A_iB_jC_k.
\]

It represents \(r_1r_2r_3\) grid points using only \(r_1+r_2+r_3\) constants. Balanced dimensions make this especially effective:

| Grid spacing on \([-10,10)\) | Full table | Two-factor representation | Three-factor representation |
|---|---:|---:|---:|
| \(10^{-4}\) | 200,000 entries | \(400+500=900\) | \(50+50+80=180\) |
| \(10^{-6}\) | 20 million entries | \(4000+5000=9000\) | \(200+250+400=850\) |
| \(10^{-8}\) | 2 billion entries | \(40000+50000=90000\) | \(1000+1000+2000=4000\) |

**That is a substantial precision-scaling advantage.** These are representation sizes, not measured runtimes. My earlier three-factor implementation used dimensions \(20\times100\times100\), but proved accesses through ordinary component lookups; it did not use a specialized tensor lookup protocol.

For batch size, let \(N\) be the requested evaluations and \(M\) the possible grid points. A simplified model of the lookup/arithmetic work is

\[
C_{\mathrm{direct}}\approx \alpha N+\beta M,
\]

\[
C_{\mathrm{3D}}\approx \gamma N+\delta\,3M^{1/3}.
\]

The proof backend adds further costs. Factorization dramatically reduces the grid-dependent term. Whether it wins as \(N\) increases depends on the per-request coefficients \(\alpha\) and \(\gamma\). In my implementation, \(\gamma\) was larger.

For arbitrary fresh inputs, someone still needs to bind every requested input to the correct tensor entry. Sorting into bins or proving the tensor’s outer-product structure does not by itself establish that correspondence. A sufficiently optimized product protocol could nevertheless have a better per-request constant than the baseline.

Two changes look particularly promising.

**First, make the lookup argument exploit the tensor’s structure.** For the unrounded integer tensor \(P=A\otimes B\otimes C\), its multilinear extension factors:

\[
\widetilde P(u,v,w)
=
\widetilde A(u)\widetilde B(v)\widetilde C(w).
\]

**Yes—the factorization is sound, and it can support an efficient proof strategy.** Your central observation is correct: at a fixed input range and precision, a small collection of reusable factors represents every exponential on the grid, independently of how many evaluations are requested.

The important qualification is that **proving which grid entry belongs to each input still requires processing the batch**. We can make the table construction—and potentially all exponential-specific multiplication—independent of the batch size. We cannot generally make the entire proof-generation workload independent of it.

There is also a useful refinement: preserve the outer-product structure in integer arithmetic and postpone rounding. That gives a clean connection to structured lookup proofs.

Here is how I would formalize it.

**First, make the example precise.** To obtain 20 integer bins, take \(x\in[-10,10)\), with integer parts \(-10,\ldots,9\). On a grid with four decimal places, write

\[
x=q+\frac{a}{100}+\frac{b}{10^4},
\qquad
q\in\{-10,\ldots,9\},\quad a,b\in\{0,\ldots,99\}.
\]

Then

\[
e^x=e^q\,e^{a/100}\,e^{b/10^4}.
\]

For your positive example,

\[
e^{8.8679}=e^8\,e^{0.86}\,e^{0.0079}.
\]

Define

\[
A_q=e^q,\qquad B_a=e^{a/100},\qquad C_b=e^{b/10^4}.
\]

Your coarse matrix is exactly

\[
P=A B^\top,\qquad P_{q,a}=e^{q+a/100},
\]

and an output is obtained by selecting

\[
e^x=P_{q,a}C_b.
\]

The counts are:

| Quantity | Size |
|---|---:|
| Original factor vectors \(A,B,C\) | \(20+100+100=\mathbf{220}\) |
| Stored coarse matrix \(P\), plus residual vector \(C\) | \(2{,}000+100=\mathbf{2{,}100}\) |
| Complete grid of possible outputs | \(20\cdot100\cdot100=\mathbf{200{,}000}\) |

Thus **2,100 is a valid count of stored factors in your partially expanded representation**. It is not the number of possible outputs, nor necessarily the number of calls to an exponential routine: the 2,000 coarse values can themselves be constructed from the smaller vectors.

There is one dimensional issue with the proposed Hadamard product. The inputs \(8.8601\) and \(8.8679\) share the same coarse bin but need different residual factors. A single residual value in that coarse matrix cell cannot represent both. We must either:

- select factors into vectors of length \(N\), then multiply those vectors;
- add a residual-index axis, producing the full 200,000-entry grid; or
- compute each distinct requested grid entry once and prove that all requests select the appropriate result.

That third option captures your tree-sharing idea particularly well.

**The general construction is a factorization of a finite lookup table.**

Choose an input grid

\[
x=a+\frac{n}{Q},
\qquad n\in\{0,\ldots,M-1\}.
\]

Here \(1/Q\) is the grid spacing, and approximately \(M=Q(b-a)\) points cover an interval \([a,b)\).

Choose radices \(R_0,\ldots,R_{K-1}\) whose product is \(M\), or covers \(M\) with padding. Every index has a mixed-radix decomposition

\[
n=\sum_{j=0}^{K-1}w_jd_j,
\qquad
w_j=\prod_{\ell<j}R_\ell,
\qquad
0\le d_j<R_j.
\]

Define factor tables

\[
f_j(d)=
\exp\!\left(
\frac{w_jd}{Q}+a\,\mathbf 1_{\{j=K-1\}}
\right).
\]

Then, exactly over the reals,

\[
\boxed{
e^{a+n/Q}=\prod_{j=0}^{K-1}f_j(d_j).
}
\]

The complete output tensor is therefore an outer product of \(K\) vectors. Its full size is \(M\), but its factor representation contains only

\[
\boxed{T=\sum_{j=0}^{K-1}R_j}
\]

numbers.

Your tree corresponds to deciding which factors to combine and cache. Combining two factors reduces the number of lookups and multiplications per request, while increasing the stored table size.

There is a straightforward improvement to your particular partition: **the bins need not follow familiar decimal positions**. For the same 200,000-point grid, write

\[
n=400u+v,\qquad 0\le u<500,\quad 0\le v<400.
\]

Then

\[
e^{-10+n/10^4}
=
\underbrace{e^{-10+0.04u}}_{500\text{ entries}}
\underbrace{e^{0.0001v}}_{400\text{ entries}}.
\]

This needs **900 stored factors**, with the same two lookups and one multiplication per evaluation as your 2,100-factor construction.

For a fixed number \(K\) of factors, roughly balanced radices minimize storage:

\[
\sum_jR_j\ge K M^{1/K}.
\]

The implementation trade-off looks like this:

| Representation of the 200,000-point grid | Stored factor/output values | Factor lookups per request | Factor multiplications per request |
|---|---:|---:|---:|
| Three factors: \(20\times100\times100\) | 220 | 3 | 2 |
| Your two factors: \(2{,}000\times100\) | 2,100 | 2 | 1 |
| Balanced two factors: \(500\times400\) | 900 | 2 | 1 |
| Complete output table | 200,000 | 1 | 0 |

These counts exclude range checks, rounding, commitments, and the internal work of the lookup argument.

**A workable ZK construction must prove the selections as well as the products.**

Given a sound ZK lookup argument and an arithmetic proof system, I would implement the following relation:

1. **Fix public tables and numerical rules.** Specify the input grid, domain, factor tables, output scale, and rounding rule. Generate and certify the constants once. The prover must not be allowed to choose arbitrary factor tables.
2. **Bind each input to its digits.** Prove the mixed-radix recomposition of \(n_i\), including digit bounds and the overall domain bound.
3. **Prove factor selection.** For every digit, prove that the pair \((d_{ij},F_{ij})\) belongs to the appropriate public factor table. Checking only that a factor value appears somewhere is insufficient.
4. **Prove the product and rescaling.** Connect the selected integer factors to the claimed output through exact arithmetic and a bounded rounding remainder.
5. **Bind outputs to their original positions.** If requests are sorted or grouped into bins, prove that this reorganization preserves the original input/output pairs. A lookup-based implementation can avoid explicit sorting.

Use a ZK implementation of these arguments so that private digit values and bin occupancies remain private.

For fixed \(K\), a useful design-level cost model is

\[
\begin{aligned}
C_{\text{total}}\approx{}&
C_{\text{preprocess}}(T)
+KN\,c_{\text{lookup}}\\
&+(K-1)N\,c_{\text{multiply}}
+C_{\text{range/round}}
+C_{\text{commit}}.
\end{aligned}
\]

The exact scaling depends on the backend. For example, cached-quotient lookups separate table preprocessing from online query work: their stated costs are \(O(T\log T)\) preprocessing and \(O(N\log N)\) online proving. This is precisely the distinction between reusable table work and batch-dependent work. genui{"citation":{"ref":"turn33view0"}}

**Your outer-product observation gives additional structure, but rounding must be handled carefully.**

For an exact field-valued table

\[
P_{u,v}=A_uB_v,
\]

its multilinear extension factors:

\[
\widetilde P(r,s)=\widetilde A(r)\widetilde B(s).
\]

The variables \(r\) and \(s\) address separate axes. This makes the full product table easy to describe without materializing it.

However, a rounded output table

\[
Y_{u,v}=\operatorname{round}(A_uB_v/S)
\]

generally loses that exact factorization. Also, after selecting arbitrary entries into two length-\(N\) vectors, their Hadamard product does not inherit the same simple extension identity. A sumcheck can prove that product efficiently, but its prover still processes the vectors.

The clean implementation is therefore:

\[
F_j[d]=\left\lfloor S f_j(d)\right\rfloor,
\]

followed by an **exact integer product**

\[
Z_i=\prod_jF_j[d_{ij}],
\]

and only then

\[
Y_i=\left\lfloor \frac{Z_i}{S^{K-1}}\right\rfloor.
\]

The represented real output is \(Y_i/S\). Prove the final step through

\[
\boxed{
Z_i=S^{K-1}Y_i+r_i,
\qquad
0\le r_i<S^{K-1}.
}
\]

All relevant integers must be bounded so that these equalities cannot hold merely because of finite-field wraparound. Dividing by \(S\) inside the field would not establish integer rounding.

This formulation preserves a decomposable table for the **unrounded product**. Its input-index column is a linear combination of digits, and its product column is a low-degree polynomial in the selected factors.

That connects directly to **Lasso and TaSSLE**, which exploit decomposable tables without constructing the entire table. TaSSLE explicitly generalizes this approach to other lookup arguments. Applying it to the integer-product table above is a concrete route to investigate; it does not by itself establish a speedup over ordinary digit lookups. genui{"citation":{"refs":["turn33view1","turn35view1"]}}

**The precision claim needs an explicit error target.**

Your \(20\times100\times100\) grid provides **four decimal places in the input**. That is different from five significant digits in the output.

If an original input \(x\) is rounded to \(\widehat x\) with

\[
|x-\widehat x|\le h/2,
\]

then the relative exponential error from input quantization alone satisfies

\[
\frac{|e^{\widehat x}-e^x|}{e^x}\le e^{h/2}-1.
\]

Consequently:

| Input grid spacing \(h\) | Maximum relative error from nearest-grid rounding |
|---|---:|
| \(10^{-4}\) | \(5.000125\times10^{-5}\) |
| \(10^{-5}\) | \(5.000013\times10^{-6}\) |
| \(10^{-6}\) | \(5.000001\times10^{-7}\) |

Factor approximation and output rounding add to this. A small relative error also does not guarantee the *correctly rounded* output at every rounding boundary; those are different specifications.

As a concrete workable configuration, take:

- inputs on a \(10^{-5}\) grid in \([-10,10)\);
- a 2,000-entry coarse table and a 1,000-entry residual table;
- factor and output scale \(S=2^{40}\);
- downward-rounded factor tables and one final downward rounding.

Write

\[
x=u+v,\qquad
u\in\{-10,-9.99,\ldots,9.99\},\quad
v\in\{0,0.00001,\ldots,0.00999\}.
\]

For certified table entries \(A=\lfloor Se^u\rfloor\), \(B=\lfloor Se^v\rfloor\), and \(Y=\lfloor AB/S\rfloor\), a conservative bound is

\[
\frac{|Y/S-e^x|}{e^x}
<
\frac{1+2e^{10}}{S}
\approx 4.01\times10^{-8}.
\]

If the input itself was rounded with error at most \(5\times10^{-6}\), the combined bound is approximately

\[
\boxed{5.04\times10^{-6}\text{ relative error}.}
\]

That gives an explicit numerical contract. It uses **3,000 factors for two million possible grid inputs**. If the tables are generated through rounded outer products, their additional error must also be included or removed through higher-precision certified preprocessing.

**Your proposed batch-independent multiplication bound can hold—with a separate lookup stage.**

Suppose the batch contains \(U\) distinct quantized inputs. We can:

- compute and prove the exponential for each distinct input once;
- build a verified dictionary of those \(U\) input/output pairs;
- prove that all \(N\) requested pairs belong to that dictionary.

Then the factor-combination work scales with \(U\), where

\[
U\le\min(N,M),
\]

while the request-to-dictionary proof still processes \(N\) requests.

Equivalently, precompute the entire public \(M\)-entry output table once. Then there are **no per-query factor multiplications** in the exponential relation, only lookup work.

This is particularly relevant to our earlier estimate of roughly 370 million evaluations. A two-million-entry output table is much smaller than that batch. At 32 bytes per output, the table values occupy about **64 MB**, although proof preprocessing and witnesses require additional memory. A complete table is therefore a serious candidate at this precision.

At higher precision, the balance changes. A decimal grid on a range of width 20 contains

\[
M=20\cdot10^p
\]

points for \(p\) fractional decimal places. Full tabulation becomes expensive quickly, and your factorized representation becomes increasingly valuable.

Finally, **this is promising, but its central factorization already appears in the literature**. ZKMath decomposes inputs into digits, looks up exponential factors, and combines them multiplicatively; it also discusses delaying truncations. zkLLM’s zkAttn uses segmented exponential tables and analyzes their rounding errors. genui{"citation":{"refs":["turn32view0","turn32view1"]}}

The worthwhile research question is whether your choice of cached tree levels, reuse of distinct inputs, and implicit outer-product tables can improve the actual prover cost. I would compare three implementations under exactly the same numerical contract:

1. **Complete output lookup**, where the grid fits comfortably in memory.
2. **Balanced factor tables**, with batched lookups and deferred rounding.
3. **A decomposable lookup over the implicit product table**, with rounding proved separately.

The decisive measurements are online prover time, commitment work, range/rounding costs, and peak memory. Your 2,100-factor observation establishes compact reusable structure; the potential improvement comes from using that structure to reduce those batch-dependent costs.

I found a useful way to preserve the outer-product structure in a proof: store rounded integer factors, multiply them exactly, and postpone rescaling until the end. Rounding each completed grid entry generally destroys the rank-one structure. This connects the proposal to decomposable lookup arguments such as Lasso and TaSSLE. There is also a simple improvement to the example: a 500 × 400 grid covers the same 200,000 inputs using 900 stored factors instead of 2,100.

The reasoning behind the two terms matters:

- **MLP:** Llama uses \(\operatorname{SiLU}(z)=z/(1+e^{-z})\) on one branch of its gated MLP. There is one sigmoid—and therefore one exponential in the usual decomposition—per intermediate coordinate. The other projection is multiplied by this result; it does not introduce another sigmoid. genui{"citation":{"refs":["turn27view4","turn27search0","turn27search2"]}}
- **Attention:** Position \(t\) attends to \(t\) positions, including itself. Each query head therefore needs \(1+2+\cdots+512=131{,}328\) exponential terms. Grouped-query attention shares keys and values, but still has **32 separate query-head softmax distributions**, so using eight heads here would undercount. genui{"citation":{"ref":"turn25view0"}}

Thus the general expression for this architecture is

\[
N_{\exp}(T)
=
\underbrace{LTI}_{\text{SiLU}}
+
\underbrace{LH_q\frac{T(T+1)}2}_{\text{causal attention}}.
\]

These are mathematical exponential terms before small constant-folding optimizations, not a count of GPU instructions. A proof can also establish an activation through a lookup without explicitly representing its internal exponential.

| Causal attention + SiLU + vocabulary softmax at all 512 positions | **435.03 million** |
| Dense attention + SiLU + vocabulary softmax at all positions | **568.98 million** |

The standard model forward returns **logits**; a vocabulary softmax is an additional operation. Computing it for every position adds \(512\times128{,}256=65{,}667{,}072\) exponentials. Computing it only for the final position adds just 128,256. The reference eager attention implementation applies softmax to the dense masked matrix, which explains the larger dense count. genui{"citation":{"refs":["turn26view3","turn25view1"]}}

**For aggregation, my recommendation is to preserve softmax and SiLU as separate proof operations, while allowing them to share a batched exponential backend.** Whether SiLU should actually use that backend depends on its numerical representation.

Softmax and SiLU offer different opportunities:

| Operation | Approach I would benchmark first | Reason |
|---|---|---|
| Softmax | Specialized row-wise proof using batched exponential relations | Exponentials are pointwise, but normalization couples the entries of each row. |
| Sigmoid / SiLU with a small quantized input domain | Direct lookup of the complete activation | Can eliminate explicit exponential, reciprocal, and intermediate rounding witnesses. |
| Sigmoid / SiLU with a large domain or high precision | Exponential decomposition plus fused arithmetic checks | A complete activation table may be too large; exponent identities permit smaller component tables. |

**Direct SiLU lookup is particularly important here because SiLU represents 63.6% of the exponential-equivalent workload.** For a genuinely 16-bit input domain, a complete SiLU table has only 65,536 entries. Its outputs can encode the specified rounded activation directly. This means 234.9 million activation checks need not become 234.9 million explicit exponential checks.

That is different from having *16 fractional bits*: a signed fixed-point value with additional integer bits may have a much larger domain. Range reduction or truncation before the lookup must itself be proved.

The literature supports preserving opportunities to fuse operations. ZKTorch, for example, combines the constituent operations of its GeLU approximation into a single lookup. Applying the same principle to SiLU is a design recommendation, rather than a SiLU speedup measured by that paper. genui{"citation":{"ref":"turn28view2"}}

For softmax, the conventional decomposition is

\[
e_i=\exp(x_i-m),\qquad
D=\sum_j e_j,\qquad
p_i=e_i/D.
\]

The exponentials can be batched across rows, heads, and layers. However, the proof must retain the association between each output and its row denominator. This workload contains **524,288 attention softmax rows**, with causal lengths from 1 through 512. A dedicated softmax proof can exploit that structure and fuse normalization and rounding checks. zkLLM’s zkAttn is directly relevant: it combines segmented exponential lookups with a specialized attention construction. genui{"citation":{"ref":"turn27view1"}}

There is also a useful common domain for a shared exponential backend. Shifted softmax uses nonpositive arguments. Sigmoid can likewise use only nonpositive arguments:

\[
t=e^{-|z|},\qquad
\sigma(z)=
\begin{cases}
1/(1+t),&z\ge0,\\
t/(1+t),&z<0.
\end{cases}
\]

ZKMath uses this decomposition. It enables shared negative-exponential machinery, with separate sign and arithmetic checks. genui{"citation":{"ref":"turn29view0"}}

But **combining two already enormous batches does not automatically produce a large speedup**. With a roughly linear prover, most per-element work remains. Sharing can save table preprocessing, commitments, openings, and launch overhead; decomposing a complete activation can add intermediate witnesses and constraints. Different scales, rounding rules, and input intervals also need separate treatment.

The practical comparison is therefore:

\[
\text{cost of direct SiLU proof}
\quad\text{versus}\quad
\text{cost of exp proof}+\text{remaining SiLU checks}.
\]

We should measure both under the **same accuracy and rounding contract**. At this scale, memory matters too: one column containing 369.36 million 32-byte field elements occupies about **11.8 GB**, before extra witnesses. Logical aggregation should support processing in chunks.
