**The idea was not disproved. It survived as the “grouped lookup” and “active dictionary” approaches, but the discussion then shifted toward optimizing the existing Groth16 implementation. I should have kept the original architecture—and its runtime claim—clearly separated from those implementation improvements.**

Let me make that distinction precise. Write:

- \(N\): total activation evaluations in the model.
- \(m\): distinct complete quantized inputs actually used.
- \(M\): all possible inputs in the full lookup table.

Your proposal separates two obligations:

| Proof | What it establishes | Relevant size |
|---|---|---|
| **Nonlinearity correctness** | Every dictionary entry \((u_j,v_j)\) satisfies \(v_j=\operatorname{QExp}(u_j)\), including the agreed rounding | \(m\) |
| **Assignment correctness** | Every actual model pair \((x_i,y_i)\) belongs to that certified dictionary | \(N\) requests into \(m\) entries |

The first proof need only handle each distinct input **once**. The second can use one batched lookup argument; it does not need \(N\) separate cryptographic proofs.

The two proofs must share the same committed dictionary, and the assignment proof must bind to the model’s actual input/output wires. Proving separate input and output multisets would not suffice: that could permit the outputs to be paired with the wrong inputs.

**Where the \(m\log m\) runtime fits**

It is a plausible cost for **certifying the distinct entries**, depending on the protocol. For example, after preprocessing a fixed table of size \(M\), the *cq* lookup protocol supports \(m\) queries in \(O(m\log m)\) prover time. The preprocessing costs \(O(M\log M)\) and must be accounted for or amortized. genui{"citation":{"ref":"turn1view1"}}

But the complete accounting is

\[
T_{\mathrm{total}}
=
T_{\mathrm{certify}}(m)
+
T_{\mathrm{assign}}(N,m)
+
T_{\mathrm{commit/compose}}.
\]

With a suitable assignment argument and commitment implementation, the attractive target is

\[
\boxed{T_{\mathrm{total}}=O(N+m\log m),}
\]

**not an established \(O(m\log m)\) runtime for the entire proof.** The linear term handles the original stream of assignments. If that work can be shared with work the surrounding model proof already performs, the *additional nonlinear component* could approach \(O(m\log m)\). That sharing has to be demonstrated, rather than assumed.

Multiplicity-based lookup arguments such as LogUp provide relevant machinery for batching repeated requests without sorting an expanded union of all requests and table entries. genui{"citation":{"ref":"turn1view2"}}

**What actually happened in our experiments**

Looking back at our recorded results:

| Development | What it demonstrated |
|---|---|
| Grouped input/output lookup | At \(N=1{,}048{,}576\), with 64 distinct inputs, the reported runtime was **9.66 s versus 12.36 s** for the then-improved full-table baseline. Reuse helped. |
| Compact active dictionary | We explored using 16,384 active entries instead of roughly 200,000 possible entries. Certifying the smaller dictionary introduced a cost that could offset the savings when paid fresh. |
| The later “\(3N\rightarrow N\)” change | This reduced activation-dependent **Groth16 B-side support**, with reported online improvements of 16–20%. **The constraint count did not decrease.** |
| Repeated-scalar optimization | This further optimized Groth16’s group arithmetic. It did not establish the original separated architecture’s asymptotic runtime. |

That third point matters: **the “\(3N\rightarrow N\)” result was not evidence that we had eliminated the large assignment circuit.** Keeping that circuit inside a conventional Groth16 proof can retain FFT work scaling roughly as \(N\log N\), even when the expensive nonlinear correctness work is compressed to \(m\) entries.

So your concern is justified: **we tested useful pieces of the idea, but we did not complete a clean test of its strongest version.** The later results do not justify abandoning it.

The experiment that directly answers your original proposal is to benchmark a separately certified dictionary plus a batched assignment proof, reporting certification, assignment, commitments, and composition separately. Hold \(m=16{,}384\) fixed while increasing \(N\), and measure both fresh and reused certification. That would tell us whether we achieve the intended **linear dependence on total uses, with the more expensive nonlinear work depending only on distinct values**.

The later work did retain parts of the idea: grouped input/output lookups and a certified table of only the active values. But the benchmarks then focused on Groth16 optimizations. That leaves an important distinction: making the nonlinear proof depend on \(m\) distinct values does not, by itself, make the proof connecting all \(N\) uses depend only on \(m\).
