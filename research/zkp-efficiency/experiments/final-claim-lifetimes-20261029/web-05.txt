L102: ### 2.1 Layer reduction and structured wiring
L103: Linear-time and structured GKR techniques already establish the algorithmic foundation [【43†11】, 【44†14】]. The production oracle uses a Libra-style two-phase sparse booking construction. Weighted linear and cube terms depend on the first input block. Multiplication supplies a sparse list of weighted input pairs. Summing the second block first produces a booking table; binding the first block then produces the remaining second-block coefficients.
L104: This implementation avoids materializing the full input-pair hypercube.
L105: For a layer with $n_{i}$ input wires, $n_{o}$ output wires and $m$ multiplication gates, the sparse auxiliary ownership is $O(n_{o}+n_{i}+m)$. The comparison baseline is StateSync-GKR’s own DenseLayerOracle, a test-only reference retaining the initial dense design. It constructs six $n_{i}^{2}$ factor tables and constructor temporaries. The production SparseLayerOracle implements Libra-style sparse reduction. Both use StateSync-GKR’s prove_impl driver and transcript order.
L106: Thus Dense and Sparse name two representations within this implementation.
L107: StateSync-GKR implements the sumcheck and GKR assembly from their published constructions; it uses Plonky3 0.4.3 for field arithmetic, hash and challenger primitives. The Dense reference is neither a Plonky3 GKR implementation nor the independently probed Lambdaworks GKR engine. The measured ratios isolate an internal representation change, not an external product comparison.
L108: Verification has a separate optimization. TableWiring already iterates a sparse gate list. DerivedRegularWiring evaluates regular progression families in closed form and retains an exact sparse residue. Derivation checks each member’s progression, kind and coefficient; unsupported gates stay on the sparse path. Audit tests re-expand the representation and compare weighted gate multisets. This reduces repeated wiring work without changing the proof object.
L109: It is distinct from replacing the quadratic prover oracle.
L110: Release 1.2 reorganizes the arithmetic of the production oracle inside the same two phases. Output-wire weights come from scaled equality tables built once per layer instead of a product chain per output wire. Each phase computes the node values of a round polynomial in one pass over its table, taking two nodes from the table halves and the others by difference additions.
L111: Round polynomials are interpolated with a constant inverse-Vandermonde matrix built once per layer, which removes the per-round inversions and small allocations of Lagrange interpolation.
L112: Each change computes the same field values by an algebraically equivalent route, and field arithmetic is exact, so round polynomials and proofs are byte-identical to release 1.1: the committed test vectors match, the Dense and Sparse oracles still agree, and all 6,912 reference proof hashes of the benchmark corpus match in both the native and the default build (【22†Section 5】). Additional requested allocation at width 4,096 stays at 579,584 bytes.
L113: Verification, the wiring oracles and the Dense reference are unchanged in release 1.2.
L114: ### 2.2 Cube gates and path constraints
L115: 
L116: The circuit intermediate representation supports weighted linear, product and cube gates. A Pow3 gate is an algebraic operation, not a processor instruction. The builder combines cube/linear taps and constants into one round layer. The Poseidon2 cube and matrix step are thereby represented without separate layers for every arithmetic subexpression [【59†3】]. The shipped primitives use the pinned Plonky3 0.4.3 registry dependencies [【45†8】].
L117: The witness computes authentication-path accumulators in order. Compilation checks each compression transition against those supplied intermediate values as parallel residual constraints. More tree levels therefore increase width and work while preserving the hash-template round schedule in the measured profiles. This is a structural benefit; there is no measured unfused-compiler ablation or claim of constant total cost with path depth.
L118: ### 2.3 Preparation and independent requests
L119: 
L120: PreparedSync owns the operation-kind circuit, full circuit commitment and derived wiring. Reuse requires the same kind, sparse Merkle tree (SMT) parameters, strategy/configuration and circuit. Every request keeps its own public inputs, witness, transcript and proof. Preparation reuse saves commitment work as well as compilation; it does not share challenge-dependent proof state.
L121: The indexed parallel batch API returns one proof per input job in input order. Witness construction and output encoding/verification can also be parallelized by the caller. This is independent job processing, not proof aggregation. Remote replies can complete out of order; explicit request IDs bind them to the corresponding original requests.
L122: The continuous serving mode of release 1.2 relies on this property: replies leave in completion order, and the frontend, the client process that sends requests and verifies the returned proofs, matches each reply to its original request by job identifier. Each proof transcript starts from its own job’s public inputs, so proof bytes do not depend on serving mode, thread or order.
L123: The reference server checks this at startup, before it listens: the sequential and parallel batch APIs must return the same proofs in input order, the per-job completion function must reproduce their encoded bytes, and a tampered control proof must be rejected.
L124: ### 2.4 Semantics, transport and reuse
L125: 
L126: 【58†Figure 2】 shows what preparation reuse shares and what remains private, including the original request checked at acceptance.
L127: The SMT frontend distinguishes Empty, Occupied(payload) and Tombstone. A never-used and a deleted slot remain semantically different, while either can satisfy non-membership. The general single-leaf update accepts old and new leaf states under the same sibling path and respective root conditions. Insertion, replacement, deletion and restoration are application uses of that operation, rather than an exclusive four-transition policy.
L128: The earlier input-variant study exercises eight lifecycle and payload/key cases.
L129: The encoded verifier consumes the complete received inner-proof encoding, checks circuit/configuration identity and verifies against the original request. Roots, value digest and input claims remain required. Malformed trailing bytes and mismatched requests reject. The current SMT verifier also recomputes native leaf/path hashes from the private witness; faster wiring evaluation does not offload that hashing.
L130: Release 1.2 enforces in every build two misuse checks that release 1.1 performed only in debug builds: a request whose operation kind differs from the prepared circuit returns an error, and a leaf-hash input of the wrong width stops execution.
L131: The sumcheck/protocol crates have no dependency on the SMT compiler. Another arithmetic frontend supplies its own circuit, witness, output claim and transcript conventions and must consume both residual input multilinear-extension (MLE) claims. The shipped entry points use KoalaBear values, a degree-four extension and the fixed hash primitives. Arbitrary Rust-program compilation and runtime field/hash selection are not bundled services.
L132: The current official distribution is release 1.2.0, source-available under BSL 1.1, which permits non-production research and reproduction. Previously granted MIT or Apache-2.0 rights and required third-party notices remain valid; they do not provide an alternative current official distribution. Data and figure rights are recorded separately. A separate serving crate (【12†Section 2.7】) builds its service components on the public prover API alone, which exercises the reuse boundary from outside the core.

L411: ## 9 Conclusion
L412: StateSync-GKR connects a reusable GKR/sumcheck core to an authenticated-state frontend with explicit preparation, independent job and encoded-acceptance boundaries.
L413: Its nine mechanisms address different application costs: sparse reduction lowers prover ownership; regular wiring reduces repeated verification; fused cube/affine circuits and parallel path constraints keep the schedule and proof growth compact; preparation reuse and indexed jobs lower repeated work and expose CPU parallelism; three-state semantics and original-request binding preserve the meaning of each result; and the separate core/model interfaces support reuse with an inspectable assurance boundary.
L414: Release 1.2 shows that the serving path and the arithmetic inside the prover’s rounds can change latency and capacity while proof bytes and verifier acceptance stay fixed.
L415: The controlled evidence gives these mechanisms concrete scope. The largest internal memory contrast is a 3,242-fold requested-allocation and about 89-fold process-RSS reduction at mixed width 4,096, retained in release 1.2. Direct fresh/prepared request measurements show 7.19 to 10.13-fold lower proving-path latency in release 1.2, and 3.46 to 4.45-fold in release 1.1; prepared verification calls and complete local batches with parallel output handling show their own substantial reductions.
L416: Release 1.2 proves 2.4 to 2.7 times faster than same-day release 1.1 on the same bare-metal workers. On a 192-core VM it keeps p99 at 34 ms at 1,000 offered requests/s, against 440 ms for same-day release 1.1, and meets a one-second budget for every request at 3,300 requests/s on one connection, including a 30-minute run of 5.94 million requests; two connections pass 5,000 requests/s in short screens, where the frontend becomes the bound.
L417: On 48 cores, in single 15-second screens, the highest rate meeting that budget rises from 500 to 2,000 requests/s. These are measured offered loads under stated budgets, which differ from both a proving-only kernel rate and an indefinitely stable capacity.
L418: The artifact therefore supplies a memory-efficient and reusable implementation, measured choices for repeated proof work, service components that kept worker memory bounded in the overload runs while the return budget was full, and explicit application acceptance semantics. Full conditions and outcomes preserve the limits of those results.
L419: The 15- and 30-minute confirmations are finite observations; larger-scale external ranking and the remaining cryptographic and code-correspondence arguments stay outside the established claims.

L16: > Abstract:Recently, researchers have been working toward the development of practical general-purpose protocols for verifiable computation. These protocols enable a computationally weak verifier to offload computations to a powerful but untrusted prover, while providing the verifier with a guarantee that the prover performed the computations correctly. Despite substantial progress, existing implementations are not yet practical.
L17: The main bottleneck is typically the extra effort required by the prover to return an answer with a guarantee of correctness, compared to returning an answer with no guarantee.
L18: > We describe a refinement of a powerful interactive proof protocol originally due to Goldwasser, Kalai, and Rothblum. Cormode, Mitzenmacher, and Thaler show how to implement the prover in this protocol in time O(S log S), where S is the size of an arithmetic circuit computing the function of interest. Our refinements apply to circuits whose wiring pattern is sufficiently "regular"; for these circuits, we bring the runtime of the prover down to O(S).
L19: That is, our prover can evaluate the circuit with a guarantee of correctness, with only a constant-factor blowup in work compared to evaluating the circuit with no guarantee.
L20: > We argue that our refinements capture a large class of circuits, and prove some theorems formalizing this. Experimentally, our refinements yield a 200x speedup for the prover over the implementation of Cormode et al., and our prover is less than 10x slower than a C++ program that simply evaluates the circuit. Along the way, we describe a special-purpose protocol for matrix multiplication that is of interest in its own right.
L21: > Our final contribution is a protocol targeted at general data parallel computation. Compared to prior work, this protocol can more efficiently verify complicated computations as long as that computation is applied independently to many pieces of data.
