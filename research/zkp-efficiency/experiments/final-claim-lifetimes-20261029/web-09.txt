L231: # StateSync-GKR
L232: 
L233: A Rust GKR and sumcheck engine for sparse-Merkle state transitions, with its protocol and compiler models machine-checked in Isabelle/HOL.
L234: 
L235: 【55†Website†oraclizer.io】 · 【112†Documentation†oraclizer.io】 · 【113†Quick start】 · 【114†API guide】 · 【115†Measured profiles】 · 【100†Formal verification】 · 【116†Refinement evidence】
L236: Its SMT frontend proves membership, non-membership and single-leaf updates. Models of the SMT circuit compiler and of the GKR and sumcheck protocol, and their composition, are machine-checked in Isabelle/HOL, building on the Archive of Formal Proofs `Sumcheck_Protocol` entry and including the exact degree-four KoalaBear extension field that the implementation uses.
L237: A conditional, mechanized forward acceptance theorem and recorded proofs for selected Rust contracts relate the model to the shipped verifier: the checks that turn a request into an acceptance verdict (public-input binding, sumcheck rounds, carry construction and final input evaluations) can be traced across model and code; see 【116†Refinement evidence and reuse】.
L238: Prepare a circuit once, reuse its proving and verification material, and run independent CPU proving jobs in parallel. The protocol and sumcheck crates have no dependency on the SMT compiler, so other arithmetic-circuit frontends can build on the same engine and use its 【116†acceptance-check review map】 when reviewing an integration.
L239: ## Implementation benefits
L240: 【117†Image: StateSync-GKR v1.2.0 in four measured cells, each with its own baseline: 89-fold less peak memory than the engine's own dense baseline on a width-4,096 test circuit (89.46-fold on v1.1.0, 88.87-fold on v1.2.0); 6,470-fold faster proving than that baseline on the same circuit, against 2,507-fold with v1.1.0; 3,300 requests a second on one 192-core server with every request accepted within one second, against 1,150 for v1.1.0 measured the same day; and a 99th-percentile latency of 34 ms at 1,000 requests a second on the same server, against 440 ms for v1.1.0 the same day.】
L241: 【118†Image: StateSync-GKR v1.2.0 serving results against v1.1.0 measured the same day on the same VM types. On one 192-core VM at 1,000 requests per second, p99 latency from scheduled arrival to verified acceptance fell from 440 ms to 34 ms, medians of three 60-second runs. The highest offered rate with every timed request accepted within one second rose from 500 to 2,000 requests per second on 48 cores and from 500 to 3,000 on 96 cores, in short screens with one run per rate.
L242: On 192 cores it reached 3,300 requests per second on one connection in three 60-second runs and a 30-minute run, against 1,000 for v1.1.0 in the earlier campaign and 1,150, the highest rate tried for it, on the same day. With two connections, 15-second screens passed every rate up to 5,000 requests per second, where the verifying frontend reached its own limit, so 5,000 is a lower bound.】
L243: Version 1.2.0 keeps every proof byte and changes how proofs are computed and served. On one 192-core VM, the reference proof server in continuous mode had a p99 latency of 34 ms at 1,000 requests/s, against 440 ms for v1.1.0 measured the same day (medians of three 60-second runs), and accepted every request within one second at 3,300 requests/s on one connection in three 60-second confirmation runs.
L244: In 15-second screens on 48-core and 96-core VMs, the highest offered rate with every request accepted within one second rose from 500 to 2,000 and to 3,000 requests/s. 【119†Performance and operating profiles】 gives each value with its server mode, host, offered rate, run length and connection count.
L245: 【120†Image: Nine benefits in three groups. Use resources well: sparse reduction, cube and affine fusion, parallel Merkle constraints. Repeat efficiently: derived wiring, prepared reuse, independent jobs. Keep the meaning: three-state lifecycle, strict codec and request binding, reusable sumcheck/GKR core, selected Rust contracts and a conditional forward acceptance theorem.】
L246:   * Use resources well: sparse reduction, cube/affine fusion and parallel Merkle constraints.
L247:   * Repeat efficiently: derived wiring, prepared reuse and independent proof jobs.
L248:   * Keep the meaning: three-state lifecycle, strict codec/request binding and a reusable core with traceable acceptance evidence.

L253: Measurement conditions and the full implementation map
L254: The engine combines sparse proving, a compact circuit schedule and reusable preparation. In separate controlled comparisons against its own references, StateSync-GKR used about 89 times less peak process RAM and achieved up to 23.68 times faster prepared verification.
L255: Mechanism  | Application benefit
L256: --- | ---
L257: Two-phase sparse proving  | More circuit or independent-job capacity within a RAM budget
L258: Derived wiring  | Less repeated work in the prepared verifier
L259: Cube gates and affine fusion  | A compact representation of Poseidon2 rounds
L260: Parallel Merkle constraints  | Modest proof-size growth across measured tree depths
L261: Circuit, commitment and wiring reuse  | Lower cost for repeated requests of the same kind and configuration
L262: Independent proof jobs  | Parallel CPU work with one result per original request
L263: Empty, occupied and tombstone leaves  | Distinct absence, insertion, update, deletion and restoration semantics
L264: Strict encoding and request binding  | Rejection of malformed or mismatched proof material
L265: Reusable core and refinement evidence  | Build another arithmetic frontend on the same engine and use the model and the acceptance-check review map

The verification result times the complete prepared typed verifier call on the same proof and request, changing only Table/Derived wiring; preparation is excluded.
L267: Table is already sparse and is not the Dense prover reference.
L268: Direct depth-24 fresh/prepared measurements of v1.2.0 show 7.19–10.13 times lower per-request proving-path latency, against 3.46–4.45 times in the earlier v1.1.0 campaign; the ratio grew because v1.2.0 proves a prepared request faster. Preparation reuses the circuit commitment as well as compilation: one membership profile spends 105.03 ms on commitment and 7.90 ms on compilation.
L269: The compact schedule has 118 layers across the nine measured depth-24/28/32 profiles; membership proof bytes grow about 2.93% from depth 24 to 32. Cube/affine fusion is a structural benefit without a separately measured speed multiplier, and a cube gate is an IR operation, not a CPU instruction.
L270: These mechanisms draw on measurements, source structure, rejection controls and formal models, rather than nine independently isolated causal experiments. The compiler-to-protocol model is mechanized. Selected Rust contract proofs and a conditional forward acceptance theorem provide a review map for the actual verifier checks; the Rust/model value relation remains a premise. 【116†Refinement evidence】 describes the reusable checks and remaining obligations.

L273: ## What you can use
L274:   * SMT operation: use `StateSyncProver` with `SyncRequest` for membership, absence or a single-leaf transition (【127†guide†oraclizer.io】).
L275:   * Prepared requests: call `prepare` once for a kind and configuration, then `prove_sync_op_prepared` and `verify_sync_op_prepared` per request (【128†guide†oraclizer.io】).
L276:   * CPU jobs: construct each witness with `make_job_prepared`, then run independent jobs through `prove_batch_parallel` (【129†guide†oraclizer.io】).
L277:   * Encoded proof: use `encode_sync_result` and `verify_encoded_sync_op` (【130†guide†oraclizer.io】).
L278:   * Proof service: use the serving components in 【131†`benches/serving`】 for bounded admission, framed replies bound to job identifiers, a return budget and continuous workers, or run their reference proof server.
L279:   * Another circuit frontend: use the `sumcheck` and `gkr` modules and supply the frontend's statement and input binding (【132†guide†oraclizer.io】).
L280:   * Model and implementation boundary: read 【100†Formal verification】 and the 【133†formal study†arxiv.org】.
L281: For direct SMT checks and the GKR boundary, see 【134†Choosing a path】.

L304: ## Minimal Rust integration
L305: The facade consumes an operation, its private Merkle witness and the public inputs that the caller expects. A checked call handles both construction errors and a rejected verifier result:
L306: 
L307:     use statesync_gkr::{StateSyncProver, SyncRequest, SyncResult};
L308: 
L309:     pub fn prove_checked(
L310:         prover: &StateSyncProver,
L311:         request: &SyncRequest,
L312:     ) -> Result<SyncResult, String> {
L313:         let result = prover
L314:             .prove_sync_op(request)
L315:             .map_err(|error| format!("proving failed: {error:?}"))?;
L316:         if !prover.verify_sync_op(request, &result) {
L317:             return Err("the proof or its request binding was rejected".to_owned());
L318:         }
L319:         Ok(result)
L320:     }
L321: 【114†Usage and API boundary】 contains a complete application, dependency pin, supported input format, prepared execution and error handling. The 【138†API reference†oraclizer.io】 lists every public module. The caller obtains trusted roots and witnesses from its own state store; the library does not authenticate an external database or establish consensus. 【139†Trust boundaries†oraclizer.io】 separates what a successful verification establishes from the application's responsibilities.
L322: The current verifier reconstructs the circuit input from that witness, including the leaf hash and the complete old/new Merkle paths.

L350: ## Measured serving and memory profiles
L351: 
L352: The serving experiments send complete encoded proofs over private TCP to a separate generator/verifier frontend. Their endpoint is cryptographic acceptance of the original request, including queueing and transport. The v1.2.0 runs use the reference proof server from `benches/serving` in continuous mode, with v1.1.0 run on the same day and VM types as the reference:
L353:   * 192 cores / 384 GiB, one connection: every timed request was accepted within one second at 3,300 requests/s in three 60-second runs (p99 35.4–38.5 ms) and in a 30-minute run of 5,940,000 requests (p99 35.3 ms). v1.1.0 met one second at 1,000 requests/s in the earlier campaign and at 1,150 requests/s, the highest rate tried for it, on the same day.
L354:   * Two connections to the same 192-core server: 15-second screens met one second at every rate from 3,400 to 5,000 requests/s. At 5,000/s the 48-core frontend reached its own limit, so 5,000/s is a lower bound for the server.
L355:   * 192 cores, 1,000 requests/s: p99 33.7–33.9 ms in three 60-second runs, against 433.8–475.1 ms for v1.1.0 on the same day.
L356:   * 48 and 96 cores: in screens with one 15-second run per rate, the highest offered rate with every timed request accepted within one second was 2,000 and 3,000 requests/s; these were not confirmed by longer runs. In same-day screens of 15 and 20 seconds, v1.1.0 passed 500/s and failed at its next measured rate of 1,000/s.
L357:   * Above capacity: offered 5,100 requests/s under a 2,760-MiB memory limit, the 192-core server's sampled peak RSS was 548,064 KiB (535.2 MiB, about 19% of the limit; 402,948 KiB or 393.5 MiB by GNU time) and it exited normally; its return budget filled while the excess requests waited at the frontend.
L358:   * Compute cost: about USD 0.87 per million requests at 3,300/s on the 192-core VM. For v1.1.0 it was USD 2.87 at 1,000/s in the earlier campaign and at most USD 2.50 at 1,150/s on the same day, the highest rate tried for it. The estimate divides the VM's on-demand hourly price by the measured rate for continuous operation and leaves out the frontend, storage and network.
L359: Every compared v1.2.0 proof matched the v1.1.0 proof bytes. The earlier v1.1.0 batch caller results remain their own series:
L360:   * 48 cores / 96 GiB, 500 requests/s: 450,000 timed requests over 15 minutes; every request accepted within 500 ms. p99 267.025 ms; maximum 307.096 ms.
L361:   * Two 48-core / 96-GiB workers, 1,000 requests/s total: each receives 500/s. Three 20-second process runs accepted every timed request within 500 ms; process p99 282.108–329.785 ms.
L362:   * 192 cores / 384 GiB, 1,000 requests/s: three 60-second process runs accepted every timed request within one second; process p99 426.032–443.471 ms and 99.62–99.92% within 500 ms.
L363:   * 192 cores / 384 GiB, 1,150 requests/s: one 60-second run accepted all 69,000 timed requests within two seconds, with maximum latency 1,598.489 ms. Of those requests, 48,553 (70.3667%) met one second. Including the drain to final acceptance at 61.394 s, the finite-window rate was 1,123.89 accepted requests/s. The growing queue prevents a sustained 1,150/s capacity claim.
L364: Both series use the membership/non-membership/update 1:1:1 mix at depth 24. In the v1.1.0 batch caller, worker count, batch cap and maximum wait are 48/48/5 ms per 48-core worker, and 192/192/5 ms on the 192-core VM. Repetitions use the same fixed corpus on each named host; different hosts, periods and profiles are kept separate. The two-worker result is a resource-equivalent deployment comparison against one 96-core worker with batch cap 96, not a topology-only causal experiment.
L365: At 1,150/s, the one-second budget met in short screens did not hold for all requests in the 60-second confirmation; the two-second budget held for every request. Sixty seconds is the offered-load window, not a prover lifetime limit. Queues, late acceptances and explicit overload outcomes remain in the data.
L366: Memory is measured independently on generic circuits. The same-driver Sparse path succeeded through tested width 65,536 under a 3-GiB cgroup with swap disabled, while the internal Dense reference reached a native OOM at width 8,192. This is a bounded tested scale, not the largest supported circuit. A v1.2.0 rerun of the same 17 limit attempts gave the same outcome for each. Requested allocation, owned Vec capacity and whole-process RSS have separate plots and definitions.
