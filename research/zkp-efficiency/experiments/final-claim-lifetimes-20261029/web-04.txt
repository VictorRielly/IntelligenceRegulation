L61: Authenticated state transitions need proof engines that conserve memory, avoid repeated setup, keep every result bound to its request under parallel execution and return complete proofs at service rates. We present StateSync-GKR, a reusable Rust sumcheck/GKR core with a sparse-Merkle frontend, and evaluate release 1.2.0 against release 1.1 measured on the same day on the same instance types, request corpus and latency budgets.
L233: At mixed width 4,096, the median of three process medians for additional requested allocation is 1,879,247,872 bytes in Dense and 579,584 bytes in Sparse, a ratio of 3,242.41, in both releases. Exposed oracle Vec capacity is 1,610,612,736 versus 508,096 bytes, also in both releases. Whole-process GNU-time RSS has a separate ratio: 89.46 in the release 1.1 record (1,811.54 versus 20.25 MiB) and 88.87 in release 1.2 (1,811.76 versus 20.39 MiB, with the Dense reference measured again on the same day).
L234: The observed prover intervals are 11,610,216,436 versus 4,630,590 ns in the release 1.1 record and 11,631,531,215 versus 1,797,814 ns in release 1.2, so the sparse prover is about 2,507 times faster than the dense reference in the release 1.1 record and about 6,470 times faster in release 1.2.
L235: Release 1.2 makes 85 allocation calls per Sparse proof at this width, against 1,282 for the same-day release 1.1 prover, while its total requested bytes per proof rise from 1,571,688 to 1,710,696: fewer and larger requests replace many small ones, and the requested peak is the same. The three ownership/timing boundaries must not be substituted for one another.
L236: Figure 3: SS-GKR (Sparse) versus its internal Dense reference on mixed two-layer circuits. At width 4,096, additional requested allocation is 3,242.41-fold lower in both releases, and process RSS is 88.87-fold lower in release 1.2 (89.46-fold in release 1.1).
L237: 【50†Figure 3】 connects the quadratic table construction to the observed growth. This is a controlled internal contrast, with common circuits, field and proof-result checks. It supports avoiding quadratic auxiliary tables when the circuit has a sparse multiplication list. The reduction comes from the sparse representation of release 1.1; release 1.2 retains it and does not claim it anew.
L238: It does not measure a production SMT memory reduction of 3,242 times or establish a ranking against every external engine. In the same-day contrast of the two provers, release 1.2 proves in 0.387 times the release 1.1 time at width 4,096 and 0.364 times at width 65,536, with 101 instead of 1,698 allocation calls at the larger width and process RSS within 0.4%.
L239: At width 2,048, Sparse completes one, two, four and eight concurrent jobs under the 4-GiB AS guard. Dense completes one, two and four, then aborts allocation at eight. Under the distinct 3-GiB cgroup, Sparse four/eight and Dense four succeed; Dense eight is OOM-killed. With active-cap entry records confirming 3 GiB and swap 0, Dense width 8,192 is OOM-killed before returning a proof. Sparse widths 8,192, 16,384, 32,768 and 65,536 each return one warmup and three timed proofs.
L240: Release 1.2 repeats all 17 attempts with the same outcome classes. Its eight-job Sparse allocation peak is higher, 2,120,976 bytes under the AS guard and 2,318,912 bytes under the cgroup against 1,481,936 and 1,273,640 bytes in the release 1.1 record.
L241: Per-job start and end times point to overlap: in release 1.2 all eight jobs started within 11.5 $\mu$s (5.0 $\mu$s under the cgroup) and ran together, whereas in the release 1.1 record the starts spread over 4.6 ms and at most six jobs overlapped (five under the cgroup).
L242: This repeat ran on the 48-core VM, whereas the release 1.1 record used a four-vCPU development host on which the eight jobs shared four cores; the difference in overlap, and with it the higher eight-job peak, is confounded with the host and is not attributed to release 1.2. The one-, two- and four-job peaks are equal or lower. Width 65,536 is the largest tested point, not an established global supported maximum.
L243: The application benefit is additional circuit or independent-job capacity within a memory budget. The comparison preserves unsuccessful attempts and their native dispositions. It does not turn missing failure telemetry into a manufactured peak or interpret a controller’s later default limit as the cap active during execution.

L248: On the bare-metal host at depth 24, batch 768 and 192 workers, release 1.2 proves 7,713.71, 7,220.36 and 5,390.07 inner proofs/s for membership, non-membership and update, against 3,195.50, 2,947.08 and 2,102.02/s for same-day release 1.1 and 3,207.74, 2,930.85 and 2,092.03/s in the 6 October record.
L249: Relative to same-day release 1.1, the release 1.2 proving rate at 1, 48, 96 and 192 workers is 2.53, 2.48, 2.43 and 2.41 times higher for membership, 2.56, 2.52, 2.47 and 2.45 times for non-membership, and 2.71, 2.68, 2.63 and 2.56 times for update. Parallel witness plus proving yields 6,323.95, 5,899.04 and 4,782.21/s, against 2,881.55, 2,654.03 and 1,984.00/s in the record.
L251: The release 1.2 gain is smaller at 192 workers than on one worker. A probe that keeps every thread proving shows why. With one pinned thread as the reference, per-thread proof time at 192 threads is 1.19 times longer for the release 1.1 prover and 1.21 to 1.22 times longer for release 1.2, while the effective clock at 192 threads falls from 4.54 GHz to 3.83 to 3.85 GHz in the release 1.1 runs and 3.75 to 3.77 GHz in the release 1.2 runs.
L252: The time ratio divided by the clock ratio is 1.00 to 1.01; five tested thread placements differ by about one percentage point, and the serving VM shows the same shape. A prototype that replaces only the per-round interpolation, removing its small allocations and inversions, recovers 1.6 to 4.2% of the 192-thread slowdown. The batch driver adds a further 1.20 to 1.25-fold per-thread time over the probe, and its parallel efficiency at 192 workers is 69 to 70% for release 1.1 and 66 to 67% for release 1.2.

L397: #### Reproducibility.
L398: Current source and bounded Linux replay are identified by the BSL 1.1 distribution at 【76†https://github.com/Oraclizer/statesync-gkr†github.com】 and the release 1.2.0 software coordinate 【77†doi:10.5281/zenodo.23643505†doi.org】. The replay builds separate callers, tests an isolated memory child, checks honest/tampered proofs and CLI rejection, and performs a small local complete-proof transfer.
L399: Its source/binary/environment identities are separate from the historical measured binary; REPRODUCING.md separates source-level reproduction from release-asset verification. The serving crate builds with cargo build --release --locked --manifest-path benches/serving/Cargo.toml, and its service-checks.py runs real-TCP functional suites, including byte equality across serving modes; these checks are not capacity evidence. Measurements use native builds (-C target-cpu=native).
L400: In one process per build, the default release build took 1.66 to 1.71 times the native latency of a prepared request and an x86-64-v3 build 0.90 times; these build comparisons were not repeated. The repository’s capacity reproduction job remains pinned to the release 1.1 measured source, because the archived memory observer accepts only that sparse oracle; the release 1.2 measurement harness, frozen cell plans and raw records are kept in the same companion package (Data availability).
L401: The v1.1.0 DOI cited in this paper preserves historical provenance with source files now restricted. Replaying a tiny functional test does not reproduce an archived performance rate.
L402: The RISC Zero [【78†9】] integration of release 1.2 has its own program identity, image ID beginning 1a8b55f4; a proof of that program’s fixed depth-24 membership relation was verified through the zkVerify [【79†16】] RISC0 verifier on the public Volta testnet, in submission block 7,775,413 with its aggregation receipt in block 7,775,436. This proof is not attached to the 1.2.0 release, whose attached proof belongs to the release 1.1 program; its bytes are the call argument of that public submission.
L403: It adds no measurement to this report. Appendix A displays all 43 detailed scientific figure families with release 1.2 overlays and four new families on uniform A4 portrait pages, in addition to twelve main-text figures. Wide panels are reformatted or divided without dropping values, conditions or not-applicable cells; original exports remain in the archive.
