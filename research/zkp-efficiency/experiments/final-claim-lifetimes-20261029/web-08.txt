L372: ## 8 Implications and validity
L373: The nine mechanisms have related but separate payoffs. Sparse reduction gives circuit/job capacity within RAM. Derived wiring lowers prepared verification-call time. Cube/affine fusion and parallel path residuals give a compact schedule. Prepared material removes repeated setup. Independent jobs exploit workers and deployment choices while retaining result identity. Three-state leaves encode application lifecycle. Strict codec/request binding gives a meaningful delivery endpoint.
L374: The generic core and formal model provide reusable interfaces and an inspectable assurance boundary. Release 1.2 builds service parts on these mechanisms. In the overload and slow-reader runs, worker memory stayed bounded while the return budget was full and producers waited for it; the frontend’s pending limit, equal to the server’s queue cap, also bounded outstanding requests, and no run without a return budget was made, so the budget’s share of the bound is not isolated.
L375: Misuse checks hold in release builds, and the reorganized prover arithmetic lowers the cost of each proof while its bytes stay fixed. These benefits extend independent jobs, request binding and sparse reduction; they add no new mechanism.
L376: The strongest memory claim is the same-driver Dense/Sparse ownership contrast, not the global superiority of this engine. The strongest serving claims name an actual host, mix, batch/wait policy, period and budget. Scale-limit results give tested support points and native failure dispositions. The fixed corpus, common host repeats, frequency/background placement, observation overhead and confirmation lengths restrict generalization.
L377: Retaining full data prevents those limitations from being concealed by a representative median.
L378: Release 1.2 ran on Amazon Linux 2023 with kernel 6.18, whereas the release 1.1 records used Ubuntu 22.04 with kernel 6.8; same-day release 1.1 runs on the new image separate the software change from the image change, and they reproduced the records within 1.1% for serving computation at 1,000/s and within 0.4% for proving; at 1,150/s same-day release 1.1 met one second, which the 60-second run of the record did not.
L379: Measurement groups ran in parallel on separate instances, while the earlier campaign ran them in sequence. Network-bound and frontend-bound points describe this measurement topology, and the 15- and 30-minute runs are finite observations.
L380: Cryptographic acceptance here is an inner-proof endpoint. Persistent database writes, sequential adoption of roots, consensus and settlement are not part of this profile. The companion formal composition and preservation results supply the semantic basis for these implementation choices; the Rust connection remains partial under explicit assumptions [【48†4】].
L381: Neither differential observations nor successful encoded acceptance discharge the online challenge-distribution or multi-round Fiat–Shamir obligations. Release 1.2 leaves this boundary as it was, because its proof bytes and verifier are those of release 1.1.

L411: ## 9 Conclusion
L412: StateSync-GKR connects a reusable GKR/sumcheck core to an authenticated-state frontend with explicit preparation, independent job and encoded-acceptance boundaries.
L413: Its nine mechanisms address different application costs: sparse reduction lowers prover ownership; regular wiring reduces repeated verification; fused cube/affine circuits and parallel path constraints keep the schedule and proof growth compact; preparation reuse and indexed jobs lower repeated work and expose CPU parallelism; three-state semantics and original-request binding preserve the meaning of each result; and the separate core/model interfaces support reuse with an inspectable assurance boundary.
L414: Release 1.2 shows that the serving path and the arithmetic inside the prover’s rounds can change latency and capacity while proof bytes and verifier acceptance stay fixed.
L415: The controlled evidence gives these mechanisms concrete scope. The largest internal memory contrast is a 3,242-fold requested-allocation and about 89-fold process-RSS reduction at mixed width 4,096, retained in release 1.2. Direct fresh/prepared request measurements show 7.19 to 10.13-fold lower proving-path latency in release 1.2, and 3.46 to 4.45-fold in release 1.1; prepared verification calls and complete local batches with parallel output handling show their own substantial reductions.
L416: Release 1.2 proves 2.4 to 2.7 times faster than same-day release 1.1 on the same bare-metal workers. On a 192-core VM it keeps p99 at 34 ms at 1,000 offered requests/s, against 440 ms for same-day release 1.1, and meets a one-second budget for every request at 3,300 requests/s on one connection, including a 30-minute run of 5.94 million requests; two connections pass 5,000 requests/s in short screens, where the frontend becomes the bound.
L417: On 48 cores, in single 15-second screens, the highest rate meeting that budget rises from 500 to 2,000 requests/s. These are measured offered loads under stated budgets, which differ from both a proving-only kernel rate and an indefinitely stable capacity.
L418: The artifact therefore supplies a memory-efficient and reusable implementation, measured choices for repeated proof work, service components that kept worker memory bounded in the overload runs while the return budget was full, and explicit application acceptance semantics. Full conditions and outcomes preserve the limits of those results.
L419: The 15- and 30-minute confirmations are finite observations; larger-scale external ranking and the remaining cryptographic and code-correspondence arguments stay outside the established claims.
