## 2. How the rounds are encoded (COUNTED, metal.rs at the current head)

- **Production = batched.** `batched_round_count` (4111-4129) takes every round until the host cost `half x points x per_eval` falls to 25 microseconds (`BATCH_TAIL_BUDGET_S`, 3872); `HL_METAL_BATCH_TAIL_US` overrides it (3874-3877). `batched_rounds` (3943-4104) puts the table-build prelude (its own **concurrent** encoder, `TabBuild::encode` 3190-3223, line 3192) and then ALL device rounds of one slot into one command buffer with ONE **serial** compute encoder (`new_compute_command_encoder`, 3242). One command buffer, committed and spin-waited (`wait_done`, 1193), per slot: 12 per block.
- **Per round, in order** (4033-4083): fold of the previous round by the device's challenge (`fold_kernels().1`, k tables), `encode_xfold` (a second fold dispatch for the m materialized tables, only when m > 0: slots 18, 14, 17, 19, 3), the round kernel (`np = de+1 or de` points x pairs threads), `k_sc_part_reduce` only when `nthreads > 4096` (`PART_RED_MIN`, 3892; so absent in the tail), then `k_sc_fs_step` as ONE threadgroup (`dispatch_thread_groups(1,1,1)`, 4081). So a tail round is 3 dispatches (4 with xtabs), all serialized by the serial encoder; each is a true dependency (fold needs the challenge, the round needs the fold, the step needs the partials), except fold and xfold, which write different buffers.
- **Host finish exists and is the knob.** `with_host_tail` (3694) / `TailedRounds::host_round` (3775) finish the sumcheck on one host thread from the first round whose measured host cost is under the budget. Production budget 25 microseconds; the unbatched budget is 250 (3676). `HL_METAL_BATCH_TAIL_US` = 0 keeps all rounds on the device. Raising it is the "finish on the CPU" idea already implemented.
- **No split kernels in production.** Tick 15's K6 (concurrent split kernels) addresses the bench's G-way split, which does not ship (H162 gets no lane); the production tail round is one round kernel plus the step. K6 does not apply as written.

## 3. What each option would save

| option | basis | tail effect, solo | stream (two lanes) |
|---|---|---|---|
| CPU finish at a larger budget | measured knob | 250 us: -7.1 ms all slots (6.1% of block GPU); 500 us: further -1.3 ms [MEASURED] | forks -52 to -82 ms per request, prove call -49 to -51 ms, but overlapped seal +47 to +180 ms; cadence 3.7455 vs 3.7576 s, no gain [MEASURED, README 3.2]. the seal rise is 1.5 to 5.6 ms per block (47 to 180 ms / 32), the same order as 36 moved rounds at 25 to 250 us of host time each (up to 9 ms, about 3.6 ms at a 100 us mean) [DERIVED; that the extra time lands on the seal pass's cores is the README's reading, not verified] |
| Persistent single-threadgroup tail kernel (README's H135b) | arithmetic | Fits threadgroup memory (32 KB) only at about 28 pairs for 36 tables x 16 B (36 x 32 x 16 B = 18 KB at 16 pairs), i.e. only the rounds the host already takes at 25 microseconds. Above that the single core's rate (1/40 of the whole-GPU 2.08 ns per pair-point at 8B slot 14, ASSUMED: one core of 40 at equal rate) makes a round of 1,024 pairs x 4 points about 0.34 ms, longer than the 0.24 ms it replaces; break-even near 700 pairs, i.e. the last 3 device rounds | Ceiling is the 3 trailing rounds per slot already priced by the 250 microsecond knob: at most 7.1 ms solo and 52 to 82 ms per request on the stream (1.4 to 2.2% of the 3.7455 s cadence), less the kernel's own time |
| Concurrent encoding of fold and xfold | count | One dispatch gap fewer per round, only at slots with m > 0, about 38 rounds past the fifth in 5 slots. If a dispatch costs about 0.02 ms (ASSUMED: a quarter of the 0.09 ms per-round marginal at tail 500) that is under 1 ms per block (<0.7%) | not measured, below noise |
| Fuse the fold into the next round kernel (fold on load) | count | 3 to 2 dispatches per round; the same idea as H133's fused fold-eval, whose bound ticks 13 and 14 already gave; at the tail the saving is a dispatch gap, not bytes | unmeasured |

**What the stream does with the tail.** The removed 3 rounds are worth 7.119 ms x 32 = 228 ms per request solo and only 52 to 82 ms in the two-lane stream: 64 to 77% of the tail's solo cost is already hidden by the other lane's full-occupancy kernels filling idle cores [DERIVED from README 3.1 and 3.2]. Applying the same hiding ratio to the whole central tail (12.66 ms solo), if it were free: 92 to 146 ms per request, **2.5 to 3.9% of cadence**; to the 24.1 ms upper end: 4.7 to 7.4% [DERIVED]. A real fix removes only part of it. These are ceilings on the assumption that cadence tracks GPU forks one for one (the 3.8 s prove call is 68 to 72% GPU-busy and 29 to 32% host-only, STREAM_GPU_PHASES.md section 0, so a GPU gain moves cadence less than one for one).

## 4. Falsifiable tests (for the coordinator to schedule; I run nothing)

- **T1, the per-round floor of a batched round, no code change.** Solo W16R2_8B, guarded, same digest: sweep `HL_METAL_BATCH_TAIL_US` over {25, 50, 100, 250, 500, 1000, 2500}; each step moves a known set of rounds to the host. Fit slot GPU time against round count per slot. Pass for any device-side tail project: marginal cost of a round beyond j = 10 is >= 0.09 ms at every step (a floor of dispatches, not of body work). Fail: it falls below 0.04 ms, in which case the 0.198 ms average of the first three is body latency and tick 15's K7 is the test to run, not an encoder change. Six more solo runs of about 6 seconds each; the same sweep at Shieldstral removes the extrapolation in section 1.
- **T2, the unexplained 0.8 ms per batch.** Arm A against Arm B differs by about 1 ms at slots whose rounds cost 0.02 ms. If the table-build prelude and the first round kernel are the cause, a per-dispatch timestamp (counter sample buffers, where the M3 Ultra supports them) separates it. Pass: the fixed part is <= 0.3 ms (the batch gap was the tail after all); fail: >= 0.7 ms, so about 9 to 10 ms per block is a batching cost outside this item.

## 5. Honest expected effect

- **Committed words per request: none.** Scheduling only; same field elements and transcript; the device transcript is replayed through the host (4156-4171) either way.
- **Proved tokens per second:** the tail is 4.7 to 20.5% (central 10.8%) of solo block GPU at W16R2_8B and 2.8 to 11.3% (central about 6.1%, extrapolated) at Shieldstral, **but the stream already hides about two thirds of it**, and the one lever tried (host finish) is flat because it costs the sealing pass what it saves. Realistic gain of a tail-only project: x1.01 to x1.02 on cadence, ceiling x1.03 to x1.04 at the central estimate. This corrects tick 15's "about 1% of block GPU" upward for the solo block (it counted slot 18 alone) and corrects the README's expectation of -0.20 to -0.30 s per request for H135b downward on the stream (its own measurement, 52 to 82 ms for the same three rounds, bounds it).

## 6. Risks and what was not verified

- Arm B per-round medians are per command buffer GPU time with the host spin-wait and submission outside; Arm A's in-batch round times are not separable (no per-dispatch counters), so section 1's central figure assumes the extra rounds cost 0.198 ms each from the knob difference, which also contains any change to the batch's fixed costs. The two arms differ in table build too (Arm B builds tables synchronously: `tables_sync_ms`, counted in its total).
- The Shieldstral central and upper figures use the 8B extra-round cost; the Shieldstral Arm A/B sums are over 11 and 12 slots with slot 19 and 20 missing from Arm B.
- The "seal pass loses what the GPU gains" reading is the README's, with no per-core attribution behind it.
- I have not read the Metal kernel text of `k_sc_fs_step` or an ISA dump; the single-core rate in section 3 is a scaling guess.
- Any change that moves rounds across devices changes no byte (M4k, `with_host_tail` comment) but is a prover change; the coordinator decides. No effect on the protocol, the verifier or Lean.
