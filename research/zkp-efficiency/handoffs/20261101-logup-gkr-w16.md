## 1. LogUp-GKR: the measurement (the kill rule's experiment)

**What was built.** A streamed Goldilocks/Fp2 LogUp-GKR prover and verifier for W16 tagged range lookups, on zkp-core's
field.
- Leaves: `(1, α − γw − v)` with `v < 2^16`, the 9 W16 widths, a 111,028-entry table, and two blinding leaves.
- Streaming: no pair table; layer n−1 is virtual; 16.1 B/leaf of heap.
- Baseline: the native-equivalent helper path on the same leaves (gather, write, zkp-core `commit_zk_owned`).
- Tests: 112 checks pass, covering equality with an independent reference prover, fast path equal to slow path,
  direct-sum oracles, and 9 negative controls (README table).
  - **The out-of-table leaf breaks the identity**, and the verifier refuses it.
  - A `(0,0)` leaf is refused only by the root-denominator check.
  - A cancelled matched pair is refused only by the leaf claim. So the leaf-claim binding is load-bearing.

**Measured** (shared M3 Ultra, medians, n = 5 at 32 threads):

| Leaves | GKR prove | ns/leaf | Helper commit | ns/word | Helper gather + write |
|---|---:|---:|---:|---:|---:|
| 2^20 | 0.0234 s | 22.3 | 0.0421 s | 40.2 | 0.0010 s |
| 2^22 | 0.0472 s | 11.2 | 0.0542 s | 12.9 | 0.0014 s |
| 2^24 | 0.1044 s | 6.2 | 0.1006 s | 6.0 | 0.0025 s |
| 2^25 | 0.160 s | 4.77 | 0.180 s | 5.38 | 0.0031 s |

- **Counted per leaf:** 10.4 Fp2-mult equivalents, and 116 B read + 64 B written.
- **Proof:** 20.8 KB unmasked, 300 rounds, of which 66 are GPU-scale (≥ 2^13 pairs).
- **Single thread:** GKR 54 ns/leaf against 99 ns/word for the commit. GKR scales poorly: ×8.7 at 32 threads,
  against ×16.5 for the commit.

**Kill rule.** It kills only if GKR ≥ 0.7× the helper path per lookup on the CPU **and** GKR's counted bytes ≥ the
helper path's.
- **Ratio clause fails.** Under the full accounting the ratio is **0.32–0.60** (ESTIMATE: the helper share of the
  domain zero-checks is attributed by table count from the native CPU pass).
- On measured parts only (GKR against gather + commit), the ratio is 0.91.
- **Bytes clause holds:** GKR 187 B/lookup against the helper path's 132.
- **NOT KILLED, and marginal.**

**Metal per block** (ESTIMATE; `projection.py`):
- Helper path today: 0.110 s.
- GKR: 0.040–0.105 s. Compute is 1.74 G base products. The 66 rounds cost 0.30–0.35 ms each against today's
  per-round floor.
- **Range lookups only:** saves −0.004 to +0.061 s, so **×1.00–1.15**.
- **Every lookup, with `H` retired** (exp/act in the tree, `ZS` gone): **×1.07–1.25**.
- This is below the coordinator's ×1.1–1.2 for the range-only variant, and similar for the all-lookups variant.

**Recommendation.**
- Rank it below the byte-identical levers below.
- Pursue it only as **all lookups → retire `H`**, with these first:
  1. a **fan-in-4 bottom layer**. The virtual layer 23 is 26% of GKR time, and the change also removes 12 GPU rounds;
  2. a **low-latency round driver** (H113);
  3. a minimal Metal kernel for the two bottom layers, measured under the owner's locks.
- **Implementation seam:** `protocol.rs::prove_core` (helpers, `write_helpers_w16`, `logup_sum_claim`), the
  `HIds`/`Layout::for_shape` schedule, and the domain zero-checks in `argument.rs`. The leaf claim is designed to
  enter them as one linear term per domain (`ZK_DESIGN_NOTE.md` §3).

**Main ZK risks** (from the note, all unreviewed):
- **Joint-view simulation** across 25 masked layers is unproven.
- **The fix for the Boolean child-bit leak.** Libra's `Z` vanishes at the child bit, so `Z` must run over the
  parent coordinates only. Layer 1 then needs the two independent-scale blinding leaves. An independent project hit
  the same two leaks: [tessera PR #325](https://github.com/AbdelStark/tessera/pull/325).
- **Masked per-domain shares** of the leaf claim must not reveal a domain's sums.
- **Committed blinding scalars** enter a public-coefficient final check.
- **Schedule.** A new slot order needs a new profile string (D17), and the DD variants need the same work.
- **Budget:** +48 to +144 `M` rows; receipt about **−5.1 MB per block** (COUNTED).

## 2. The gap after W16 (AGENDA standing question of 2026-10-30)

**Target.** At T128, a 32-layer 8B is `4 / t_block` tokens/s. 50 tok/s needs `t_block ≤ 0.080 s`. Today it is
0.47 s (warm Metal), so the gap is **×5.9**.

**Decomposition of the instrumented 0.578 s** (QUOTED from `results/zk60_limb16_20261031/logs/g_phases2.log`):
- **Host-side by phase name: about 0.21 s (36%).** ESTIMATE: some of it may already touch the GPU.
  - witness planes, lookup values and histograms, mask rows: 0.047;
  - `M` commit: 0.010;
  - helper writes: 0.008;
  - exp/act inverses: 0.020;
  - table helpers and mask rows: 0.009;
  - matmul slots, mostly CPU i8 weight folds: 0.054;
  - openings: 0.044;
  - limb slot 03 on 2^14: 0.017.
- **Device-side: about 0.37 s.**
  - commits `A` + `H`: 0.096;
  - five domain zero-checks: 0.193 (table builds 0.085, masked rounds 0.095);
  - the other large slots (SS, row sums, IO, `TAB`, `ZS`): about 0.08.

**Ranked hypotheses** (new numbers continue STATE's 110):

1. **H112: cross-block host/device pipelining.**
   - **Lever.** Each block proof is unchanged. Run block i+1's host phases (witness, helpers, exp/act, weight folds,
     openings) while block i's device phases run.
   - **Ceiling.** Throughput becomes `max(host, device)` instead of the sum. About 0.37 s against 0.578 s
     instrumented, so **×1.3–1.6** (ESTIMATE). No protocol change, no ruling.
   - **Prerequisites.**
     - Check the chain order: block i+1's IO-in needs only block i's output commitment, early in its proof.
     - Memory for two blocks in flight; trivial at 256 GB.
     - Rayon table builds inside the device phases compete for the CPU.
   - **Falsifier.** Two concurrent W16 block proofs on Metal reach < 1.15× sequential throughput.
   - The speed plan's S3 ("whole prover resident") is the alternative. Pipelining is cheaper, and it stays useful on
     the 5090, where host residue would otherwise cap the rate near 25–30 tok/s.
   - Native owner; GPU run.
2. **H113: device round-latency floor.**
   - **Evidence.** Three-table 2^19 slots (00, 01, 21) take 6–7 ms over 19 rounds, while their traffic is about
     0.1–0.2 ms. So about 0.3 ms per round is overhead. Over about 190 large-slot rounds that is about 0.057 s.
   - **Lever.** One command buffer per round, with no per-kernel waits, or a persistent kernel with on-device sums
     and an immediate host hash. On the 5090 design: CUDA graphs. Byte-identical. Saving **−0.03 to −0.05 s**.
   - **Falsifier.** Metal GPU timestamps show the device busy > 70% of each round's wall in those slots.
3. **H114: exp/act helper inverses by public-table gather.**
   - **Evidence.** `protocol.rs:1611–1618` builds 2.62 M tuple denominators. `accuracy_act::query_values` (line 74)
     is a sequential iterator, followed by chunked batch inversion. The phase measures 0.020–0.026 s.
   - **Lever.**
     - A valid query `(group, key, output)` or `(delta, E)` is a table entry. Invert each entry's denominator once
       (about groups × 4,096 for act, plus the exp table).
     - Gather and check equality.
     - Fall back to direct inversion otherwise, which gives the same word and the same refusal.
     - Use an indexed parallel iterator for the build.
   - Byte-identical, like Stage 28. Saving **−0.015 to −0.02 s** (×1.03–1.04).
   - **Falsifier.** A microbenchmark shows < 5 ms of the phase in query build plus inversion.
4. **H115: small-value first rounds in the domain zero-checks**, after coordinator item 1. Saving −0.01 to −0.035 s;
   it overlaps H113's latency share. Supported by this prototype's 2.4× per-entry measurement.
5. **H111: LogUp-GKR, all lookups, retiring `H`** (§1). ×1.07–1.25. Needs the ZK review and a ruling.
6. **H116: small-field rebase.** ×1.2–1.5. Parked.

**What reaching 50 tok/s needs** (ESTIMATE):
- The byte-identical levers (items 1 and 2, H113, H114, H115) bring the warm block to about **0.32–0.37 s**.
- H112's overlap brings throughput to about **0.22 s** per block on Metal, about 18 tok/s.
- H111 brings it to about **0.15–0.20 s**, about 20–27 tok/s on Metal.
- A 5090 port at ×2.2–3.5 on the device side brings it to **0.05–0.09 s**, about 44–80 tok/s. That holds **only if**
  the roughly 0.13–0.16 s of host residue is overlapped (H112) or moved onto the device. Otherwise the host alone
  caps the rate at about 25–30 tok/s.
- The hardware factors are spec-derived: bandwidth 1.79 against 0.8 TB/s, and lanes × clock. Not measured.
