## 0. Headline

1. **The six lanes are host-bound as much as device-bound.** On a request thread a block takes 611 ms (24 requests, 600 blocks, DERIVED from the trace): 307 ms waiting for command buffers (committed to done, queueing behind other lanes included) and 303 ms with no buffer outstanding on that thread. One request is 19.405 s per lane (MEASURED, `CADENCE.json`) = 26 blocks 15.96 s + 3.44 s outside, of which the sealing window is 2.88 s (median, range 2.60 to 3.59).
2. **The app has no A33, no A35 and no seal-ahead.** `seal_chain_keeping` still calls the repeating `check_lookup_misses` (`classify_cli.rs:591`); A33's dedup lives in `trained_block::seal_chain` only. A35 cannot apply (tick 29/Astra: fork format refused for classifier profiles). The harness finding "sealing-side savings do not reach the stream" is a two-lane, prove-paced result; the app runs six lanes with the device 72.7% busy (MEASURED), where a lane's serial path is its throughput.
3. **Candidate host work that needs neither block k's device results nor the transcript is about 59 to 101 ms of the 303 ms per block** (section 2). A closed-queue MODEL passes it through at x1.03 to x1.11 on the lane period; seal-ahead at W16R2 is bounded x1.04 (R13 pass-through) to x1.18 (ceiling).

## 2. (b) What is left to move

`prove_core_before_with` takes no transcript (doc comment: it "reads no transcript, so it can run before the transcript it will continue on exists"), but `prove_classify_run_with` calls before and after back to back for each block (`classify_run.rs:293`); the forks' ahead-of-turn use (A13, A35) is not in this path. The lane's request thread waits on the device for 307 ms a block while four of its five rayon workers are idle (the request body runs on one worker; waiting spins 200 microseconds, then blocks, `metal.rs:1180-1212`). So block k+1's before-part (48.6 ms gap, plus its A commit's device work) and boundary prepare could run on idle workers during block k's slots, and **all 26 boundary planes exist when sealing ends** (`CliSource::boundary_plane` reads the same planes sealing computed; tick 25 / A35's observation). Bound DERIVED: independent host work per block is **59 ms (A rows plus M) to 101 ms (adding all of the 38-row gap)**, 10 to 17% of 611 ms.
Costs and constraints: (i) one `ZkRng` is shared by `boundary::prepare`, the A and M masks and the openings, so running ahead changes draw order; it is seeded from the OS (`classify_run.rs:236`) so no byte is fixed, but whether a test pins the order was not checked; (ii) memory: A rows 2,504 x 8,192 x 8 B = 164 MB host and 657 MB encoded per lane ahead (DERIVED, row width ASSUMED 8,192 from the census); (iii) the openings' folds, matmul slots and helper inverses wait for challenges: no.
**Also left (harness work missing in the app):** A33's dedup at `classify_cli.rs:591` holds on the same precondition (build just ran `check_accuracy_for_shape` on the same `&blk`, `&ssh`, `witness.rs:83`; W16R2 is non-Legacy was not verified): 12.6% of the sealing window = 0.36 s, **at most x1.019** on the lane period (DERIVED; ASSUMED proportional); needs A33's pinned test and the H-1 refusal text unchanged.
**Closed-queue MODEL** (script; device as one first-come server, demand 74.4 ms a block from the 72.7% busy share, think time 455 ms fitted to the 614 ms period): cutting 30, 59, 101, 150 ms of host gap a block gives x1.039, x1.078, x1.137, x1.204 at block level, **x1.032, x1.063, x1.110, x1.162 on the lane period** (26 blocks are 82% of it), device busy 76 to 88%. The model has no memory contention (hosts stretch x1.4 to x3.7 at six lanes, A28 3.3), so these are ceilings. Falsifiable test: bench one lane with the before-part for k+1 spawned on a pool worker, same binary otherwise; pass is a lanes-full gain of at least 3% with unchanged receipts; not scheduled.

## 3. (c) `HL_A28_SEAL_AHEAD=1` at this profile (CODE-READ, `classify_serve.rs:249-271, 280-290, 517-540`)

Two request threads a lane, each with its own 5-thread pool (12 pools, 60 threads); the lane's second request seals while the first runs and waits at the lane's run gate (`classify_cli.rs:781`). It moves the **2.93 s** (window plus hand-over) off the critical path. Ceiling if fully hidden and free: 19.405 to 16.48 s, **x1.178**. At R13, A28 realised 1.4 of 5.7 s (25%: cycle 39.0 to 37.6 s, stream +1.3%); the sealing share of a request is the same at both profiles (14.6% there, 15.1% here, DERIVED), so the pass-through is a fair first prior, giving **x1.039 on the lane period (stream-level +1.3% if the R13 ramp effect carries)**. What is not like for like: the device was 80% (utilisation counter) there against 72.7% (union of buffer intervals) here, different meters; the product buffers are 18.5% of the sealing window, so the move adds device work to the busiest phases. Memory: 7.168 GiB a request is charged (`WITNESS_CACHE.json`), so up to +43.0 GiB at six lanes; the guarded W16R2 stream peaked at 113.81 GiB RSS, so about 157 GiB against the app's 196 GiB need and 220 GiB cap (DERIVED, an upper bound: the first request's kept witnesses are freed as the run consumes them). The 300 ms stagger starts every request, so the 12 initial sealing passes begin within 3.6 s of each other. It adds R13's 11 CPU-s a proof (not re-measured).

## 4. (d) Oversubscription

Cores: batch 2 arm B (A30/A31, 24 proofs, 104.8 s) used 940.6 prover and 539.4 checker CPU-s, **9.0 plus 5.1 = 14.1 cores of 32** on average (DERIVED); R13 A28 showed 12.8 to 15.2. Mean occupancy is not saturation: 30 pool threads plus checker and writer threads fit 24 performance cores on average, but hot sections are memory-bound (A28 3.3, memory-bandwidth probe inconclusive) and bursts coincide (Astra: 302 of 333 near-simultaneous A commits began together). No per-thread CPU-share record exists at W16R2; the CPU-s totals cannot separate stalls from work.
