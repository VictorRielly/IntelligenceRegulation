# Who can prove a check for a holder with a small machine?

The installed text prover reads the content. A receipt lets a guest check which pinned model and policy produced the stated result. The party that prepared the witness can still read it. For the current public-text pilot, a holder can delegate to an operator who may see the post. A confidential VM or multiple independently operated provers would address a different need, keeping sensitive input from that operator. Neither route has been qualified here. The service decision reserves hosted sensitive content for a named customer need. A classification receipt establishes an execution result and gives no guarantee of human authorship. [Service decisions and trust boundaries](../../../docs/zkmatrix-poc/ZK60_PROVING_SERVICE_SPEC.md) · [Privacy requirements](../../../docs/zkmatrix-poc/ZK60_PRIVACY_REQUIREMENTS.md)

### Trust the host by contract

The client sends plaintext over an authenticated connection. The operator and anyone with its privileges can see the text, intermediate values and private opening. Access controls, deletion terms and incident procedures limit who may handle those data. A public verifier can check the resulting receipt independently. This is the smallest implementation change. Keep the private opening available only to the author, bind it to the submitted item and verify the receipt in a fresh process. The installed W16R2 profile is qualified for public pilot content only. [Installed pilot and profile limits](../../../results/zk60_astra_20261026/app_composed_native_20261122/PILOT.md)

MEASURED on the installed Mac over loopback, one 14-token public item and three policies took 152.88 seconds from submission to publication, including 81.5 seconds waiting for the guard. DERIVED, 152.88 − 81.5 = 71.38 seconds for all other work in that interval. On identical hardware, contractual delegation adds no proof operations. A remote client also incurs the upload, service queue and response time. An internet deployment has no measurement here. The installed author/guest workflow is the closest existing implementation. [Pilot run](../../../results/zk60_astra_20261026/app_composed_native_20261122/PILOT.md)

### Send plaintext only to an attested confidential VM

The holder checks a fresh attestation against an approved guest image, security configuration and device measurements, then encrypts to a session key bound to that instance. In this design the approved guest sees the text. The infrastructure operator is outside the plaintext trust boundary under the hardware vendor's threat model. The holder still trusts the guest software, whoever can administer it, and the CPU and accelerator trust roots. Job timing and sizes can remain observable. GPU debug mode, stale measurements or an unauthenticated key exchange defeat the intended claim. NVIDIA documents attested key release and the limits of the isolation. [NVIDIA key release](https://docs.nvidia.com/enterprise-reference-architectures/deploying-proprietary-models-confidential-compute-self-hosted-vms/latest/attestation-and-key-release-flow.html) · [NVIDIA threat model](https://docs.nvidia.com/confidential-computing/virtual-machines/threat-model)

[Source's number] Wang and colleagues compared confidential and ordinary inference on an H100 with Intel TDX. With Mistral-7B at fixed request rates the confidential run lost 17.7% of global token throughput and took 21.8% longer to produce the first token. Those measurements cover inference. Proof generation also moves commitments, witnesses and large receipts, so its overhead requires a paired test. The installed arm64 Metal prover would need a qualified CPU or accelerator port. Protect tokenization, inference, proof generation, temporary files, crash handling and opening delivery within the measured guest. Bind the attestation and session key to the job and approved code, and verify the mathematical receipt separately. [Authors' benchmark](https://arxiv.org/abs/2607.19353)

### Split the witness across independent provers

The holder can distribute random shares and keep the decommitment, with each server learning only its share and authorized outputs under the chosen protocol's corruption assumptions. Two-party malicious-secure proving can tolerate one corrupt party for privacy, with abort possible. A three-party honest-majority protocol needs at least two honest parties. Two services under the same administrator offer little practical separation. Input decoding and witness construction must also run locally or on shares. Sending the whole document to a tokenizer or a witness service would disclose it before proving began. [Ozdemir and Boneh, USENIX Security](https://www.usenix.org/system/files/sec22-ozdemir.pdf)

[Source's number] On their large arithmetic circuits, Ozdemir and Boneh reported online proving latency near the single-prover baseline for the three-party honest-majority construction and around twice the baseline with dishonest-majority security. The experiment used single-threaded provers on a fast network and excluded preprocessing. It gives no end-to-end rate for this classifier. TACEO's coNoir example demonstrates shared witness generation, collaborative proving and ordinary public verification for a different proof system. Porting this project's witness construction, sumchecks, commitments, random masks and openings would be protocol work. [Experiment, §7 and Figure 8](https://www.usenix.org/system/files/sec22-ozdemir.pdf) · [coNoir implementation walkthrough](https://docs.taceo.io/docs/getting-started/quick-start-co-noir/)

### A deciding test

Use one synthetic document with a distinctive private marker. For each route, measure submission through owner acceptance, split queueing from computation, count transferred bytes and include preprocessing. Require the same model and policy, a matching owner opening and a separately verified receipt. Inspect host-visible logs, databases and scratch for the marker and opening. For the VM, substitute a new image, replay an old quote and swap the session key. Each must prevent input release. For collaborative proving, isolate each server's view, corrupt one share and stop one server. Require privacy under the declared threshold and correct verification or explicit failure. Start with one small relation before estimating a full-model port. No confidential-hardware or collaborative classifier run was performed for this study.
