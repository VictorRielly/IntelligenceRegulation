# Where a kilobyte inference proof would fit

**A12, 25 November 2026.** A 1 KiB proof fits comfortably in the example Ethereum transaction below. Browser and phone feasibility depends on the verification key, implementation, memory and time as well as the transferred proof. Counting one actual classifier receipt puts the present gap at **at least 1,594 Ethereum transactions** to carry its segment bytes under the specified gas rules. That would still leave verification to implement. ## Transport and checking budgets

| Destination | Budget, assumptions and implication |
|---|---|
| Ethereum L1 calldata, Fusaka rules | **Source numbers.** EIP-7825 caps a transaction at 16,777,216 gas. EIP-7623 sets a floor of 21,000 plus 10 per zero byte and 40 per nonzero byte for an ordinary transaction. **Derived.** With 1,024 proof bytes alone the floor is 31,240–61,960 gas. A data-only all-nonzero payload tops out at ⌊(16,777,216 − 21,000)/40⌋ = 418,905 bytes. Method selectors, public inputs and contract execution also need room. Gas charged follows the greater of the floor and the ordinary calculation. This is a named fork calculation. Base and later Ethereum revisions need their own accounting. [Calldata floor](https://eips.ethereum.org/EIPS/eip-7623) · [Transaction cap](https://eips.ethereum.org/EIPS/eip-7825) |
| Ethereum blobs | **Source numbers.** A blob has 4,096 field elements of 32 bytes, or 131,072 serialized bytes. The EVM can access the versioned hash and check an opening. A contract cannot read arbitrary blob bytes to run an inference verifier. Posting an anchor or blob and checking the inference on-chain are separate operations. [EIP-4844](https://eips.ethereum.org/EIPS/eip-4844) |
| Desktop browser | **Source number.** A single wasm32 linear memory has a 4 GiB addressing ceiling. Streams can process files larger than one allocation. **Measured locally.** The current native guest needs an 11,950,596,915-byte verification kit on disk and replays a 2,008,826,368-byte three-category download. Its Apple Silicon binary is a different executable format. A browser needs a verifier build and a measured working set, including its verification key and temporary allocations. [V8 memory explanation](https://v8.dev/blog/4gb-wasm-memory) · [Guest replay and kit](../../../results/zk60_astra_20261026/app_composed_native_20261122/guest-20261125T073308.630547Z/RESULT.json) |
| Phone | Android documents a **16 ms** frame target for UI responsiveness. Checking can run on a worker. Apple documents that under memory pressure the system can terminate an app. Neither gives a universal maximum proof size or verification time. The **measured** Mac maximum of 2.47 GiB sampled process RSS for one category leaves the phone's memory and time open. [Android memory guide](https://developer.android.com/topic/performance/memory-overview) · [Apple jetsam reports](https://developer.apple.com/documentation/xcode/identifying-high-memory-use-with-jetsam-event-reports) · [Native guest measurements](../../../results/zk60_astra_20261026/app_composed_native_20261122/guest-20261125T073308.630547Z/RESULT.json) |

**Counted and derived.** I streamed the 28 public files listed in the sexual-content inventory, checked every length and SHA-256, and counted zero bytes. The 669,561,472 bytes contain 2,796,475 zeros and 666,764,997 nonzeros. The data term alone is 26,698,564,630 gas. Dividing by the 16,756,216 usable gas per transaction and rounding up gives 1,594. This excludes the other two categories, calldata framing, public inputs and any verifier code. [Counted files and digests](../../../results/zk60_astra_20261026/app_composed_native_20261122/qualification-20261125T070919.014403Z/sexual.publication.json)

## What other inference systems report

| Primary source | Proof and checking cost reported by the source |
|---|---|
| Aethelred verification framework | Its service matrix gives EZKL a **256-byte minimum** for ML inference and a **2×** gas multiplier in its own pricing formula. Those are protocol parameters. A named hosted inference, observed proof length and absolute checking cost were unavailable in that record. [Provider's proof matrix](https://aethelred.io/zk-proofs.html) |
| AERE deployment report | Its SP1 Groth16 table cites a **326,492-gas** zkML check from its deployment artifacts and a **roughly 260–356-byte** proof range for the SP1 route. The range covers several applications. The row does not pair an exact MNIST proof length with that gas observation. [Operator's report, part B.1](https://git.aere.network/aere-network/aere-docs/src/branch/main/AERE-BENCHMARK-REPORT.md?display=source) |
| ZKML research implementation | The authors report KZG proofs of **6,560 bytes / 6.69 ms** for MNIST, **17,664 bytes / 17.67 ms** for MobileNet, and **28,128 bytes / 18.70 s** for GPT-2. Timings are from EC2 machines. Even in one implementation, similar byte counts can have very different checking times. [EuroSys paper, §9.2 and Table 6](https://ddkang.github.io/papers/2024/zkml-eurosys.pdf) |

**Deciding product test.** Produce a compact proof that binds the installed model, policy, input commitment, post coverage and verdict. Count the complete encoded call and measure a deployed verifier's gas on the target fork. On a named browser and physical phone, record cold download bytes including the verification key, warm verification time and peak memory. Both should reject a changed verdict or model identity. A hash-only anchor can exercise the transport path but leaves the inference test open. The companion study identified public-weight authentication as a major unresolved cost of wrapping the current verifier. [Wrapper study, item 90](../../zkp-efficiency/handoffs/20261125-claude-tick55-recursive-wrapper-cost.md)

The count used retained public receipts. I did not call a proving service, submit a transaction or benchmark a phone. The Aethelred figures and Apple's platform text came from indexed first-party content. A direct Aethelred page read failed and Apple's direct HTML required JavaScript.
