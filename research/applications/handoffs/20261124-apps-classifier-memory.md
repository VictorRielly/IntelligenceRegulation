# How small a Mac can run the installed classifier?

**The installed app requires more memory than any of the proposed 36, 48, 64, 96 or 128 GB machines can offer.** A version that runs its activation writer, prover and verifier one after another has a plausible one-lane test target at 48 GiB and a two-lane target at 64 GiB. Only the 256 GB M3 Ultra has been tested here. The W16R2 profile proves the pinned classifier's verdict on public content. Use with private content also depends on a reviewed privacy profile. ## What occupies memory

- **Installed app, counted and measured.** Six prover lanes, a separate three-lane verifier and two concurrent activation writers reserve 196 GiB with a 220 GiB cap. The guard also reserves 3.5 GiB for the system. The November 24 post peaked at 93.53 GiB sampled process-tree RSS. It submitted three category jobs. A fully occupied service would have a different workload. - **Weights and witness cache, counted.** Each W16R2 Python writer counted 28,879,688,704 bytes (26.90 GiB) of resident arrays. Two copies account for 53.79 GiB before native prover work. The public model export occupies 4,249,132,083 bytes on disk. The native server shares loaded blocks between its own lanes. Each active proof request receives its own 16 GiB limit for retaining witnesses from the sealing pass. This is a ceiling, and the guard peak already includes the cache that was actually used. - **Sequential stages, measured.** The public-fixture harness finished one writer before proving and ran its checker separately. One proving lane with five threads recorded **27.45 GiB RSS and 5,811 MiB GPU allocation** for the entire guarded run. ## Capacity and rate estimates

For a **planning estimate**, allow 8 GiB for macOS and other processes. Apple GPU allocations can overlap RSS in unified memory. Counting zero or all of the sampled GPU figure as additional gives a one-lane range of 35.45–41.12 GiB. For two lanes, linear interpolation of the one- and six-lane observations gives 27.45 + (65.02 − 27.45)/5 = 34.96 GiB RSS, and 10.36 GiB GPU allocation. The same calculation gives 42.96–53.32 GiB including headroom. Phase overlap, model data already in RAM, and missed peaks can move those estimates. **Speed at M3 Ultra compute capacity.** From two untraced switch-off legs at one lane, 128 padded tokens divided by the median whole native request time gives **11.38 and 11.45 padded tokens/s**. A two-lane estimate uses the matched one- and six-lane trace legs alone. Their completion windows give 11.383 and 44.047 padded tokens/s. Fitting the simple shared-work model `R(n) = R(1) × n / (1 + (n − 1) × s)` gives `s = 0.110` and **20.5 padded tokens/s at two lanes**. This interpolation is a hypothesis. It excludes writing activations, independent verification, and the other two categories of a post. The traces used an earlier binary at the same statement profile. Memory capacity alone gives no device-specific multiplier for a smaller chip. None of these rates has been measured on a smaller Mac. **Confirmation test, proposed only.** On the M3 Ultra, stage the current writer, prover and verifier sequentially under the normal lock and watchdog. Start with one prover lane, five threads, the existing 16 GiB cache, and a 40 GiB process-tree cap for the 48 GiB case. Use the pinned public fixture, all three policies and the existing verifier and input check. Record per-phase process RSS, GPU allocation, system memory pressure, swap growth and elapsed time. Require all three receipts to verify and no guard kill or swap growth. If this passes, test two lanes with two simultaneous requests and a 56 GiB cap for the 64 GiB case. A watchdog cap on a 256 GB host cannot reproduce a smaller chip's bandwidth, compression or shared GPU budget. A physical target is needed to establish capacity and rate. A shipping app would also need a separately selected and qualified sequential worker profile.
