## 3. Pooling, reuse and draw order

The commit message says "private host reuse", so this was read as a
privacy question and not as a performance detail.

### 3.1 What the pool is

`mod zkhostbuf` (`zk.rs:2315-2461`) is a process-global
`static POOL: Mutex<[Vec<Vec<Fp>>; 2]>` with two slots, `W` and `A`, and
`KEEP = 1` retired buffer per slot.

* `take(slot, len, tiled)` returns a buffer of exactly `len` elements in
  which `[tiled, len)` has been zeroed and **`[0, tiled)` holds whatever
  the previous holder left there**. With `HL_FSP_POOL=0` it returns a
  fresh `vec![Fp::ZERO; len]`.
* `give(slot, v)` parks `v` with its contents intact; a `Vec` with zero
  capacity (one emptied by `std::mem::take`) is dropped instead.

So a pooled buffer **does** carry one proof's numbers into the next
caller's hands. Everything therefore turns on who the callers are.

### 3.2 The callers, and why none is on this profile's path

`take` has exactly two call sites, `zk.rs:2680` (`w_data`) and `:2746`
(`a_data`), both inside `prepare_layer_zk_v3_inner`. `give` has exactly
three, `zk.rs:2572` and `:2582` inside `PendingV3::finish` and `:3225`
inside `prepare_layer_zk_v3_inner`. All five are in the **v3 FFN layer
prover**.

The toy private block's prover is `private_block/protocol.rs::prove`. It
builds its own `a_data` / `h_data`, commits them with
`pcs::commit_zk_owned` (`protocol.rs:316`, `:373`), and calls
`zk::mask_commit` / `mask_open` / `mask_verify` (`:324`, `:392`, `:453`).
It never calls `prove_layer_zk_v3`, `prove_layer_zk_v3_inner`,
`prepare_layer_zk_v3_inner` or `PendingV3::finish` — none of those names
appears in any file of `private_block/`, `private_attention/` or
`private_seam.rs`, and the first is the only public one of the four.
**No pooled buffer is on this profile's path, in either direction**: the
block never takes one, and nothing of the block's is ever given to the
pool. Its pads, masks and salts are drawn by `rng.fp_vec` / `rng.bytes32`
straight into freshly allocated `Vec`s inside `mask_commit`
(`zk.rs:436-462`), which is byte-identical.

### 3.3 The v3 FFN path, for the integrator, out of D22's scope

Not this profile, so not a finding against D22 — recorded because the
question was asked and because that profile is the MVP's main line.

* Under P1, `take(W, lay.w_len, lay.w_len)` zeroes nothing, so the whole
  buffer is stale until written. The block loop at `zk.rs:2681-2696`
  writes all three block families (`wg`, `wu`, `wd`) for every
  `(c, b)`, and `Layout::new` (`zkp-core/src/ffn_v3/statement.rs:148-170`,
  untouched) lays exactly those `3·nb_d·nb_f` blocks of `wb` contiguously
  from 0 with `w_len = woff`. The tiling is exact, so every element is
  written before any is read.
* `take(A, zl.a_len, lay.a_len)` zeroes `[lay.a_len, zl.a_len)` — the CFS
  mask rows, the table rows, the predicate row, the endpoint rows — which
  is what the two PARTIAL writes into that tail (multiplicities
  `0..t.size`, predicate bits `0..16`) require. The prefix is written by
  the loops at `:2746-2765`: `7·nb_f` blocks of `tfb` and `3·nb_d` blocks
  of `tdb`, and `Layout::new` allocates exactly those with `a_len = off`.
  Again exact.
* `give(W, std::mem::take(&mut cm.data))` at `:2572` retires a buffer that
  under P3 contains the W **mask rows**. It is only ever handed back by
  `take`, whose caller overwrites the whole prefix and zeroes the rest, so
  that randomness cannot reach a later commitment; it does linger in
  process memory, which §6 of the statement puts out of scope by ruling
  (D20/D21: timing, memory and power).
* The pool's own test spawns a child process and sets `HL_FSP_POOL` on
  that child's `Command`, not on the parent's environment, so it cannot
  perturb a concurrent proof in the same test binary.

### 8.7 The manifest cross-check's silent skip, fixed — 2026-09-22 (round 9e)
