## 1. In plain words, for Victor

**The free data is gone where it mattered first.** The top theorem talked about "the kinds data `D`": for every check
of the run, what claims it checks and what data the prover was committed to. Until now `D` was anything that had the
right sizes, so nobody could prove the checks are sound OF THE REAL RUN. This lane builds `D` from the verifier's own
readers: an opening's claims are the claims the verifier's accumulator holds at that point of the transcript, an
opening's data is the matrix extracted from the prover's log for the root the transcript absorbed, `M`'s data likewise.
For the 26 blocks it is PROVED that on an accepted run these readers return exactly what the run verifier checked.

**Three of the nine "alive" assumptions are discharged.** The top theorem assumes, kind by kind, that on an accepted
run every check of that kind is "alive" at the end (it has not been fooled yet). For the openings' second halves
(`opB`) and for `M`, this lane proves it from the verifier's own acceptance, for every opening of every part, directly
on the run's transcript (including the openings that close a boundary, which the per-block results did not reach).
What is still assumed there is one bookkeeping fact per opening: the opened Merkle columns are the extracted ones (the
audit's GA-8). For the openings' first halves (`opA`) the assumption is now simply gone from the theorem: it follows
from the layout of any accepted run, for any `D`.

**The app's own theorem.** Because the app's model has 26 different block calibrations, only the "one shape per block"
gates apply to it (finding L40-1). This lane restated L39's gates at that model and wrote the app's top theorem in
the approved form with all of the above plugged in.

**What is not done.** The slots, the draws and LogUp (six of the nine alive assumptions), the stages' readers, the
closing openings' claims link, the doom covers and the endpoint links.

## 6. Findings

**L43-1 (Medium; for the coordinator and the owner of L34's `RtOpen`): every opening of the run is modelled with
`2^14` message columns.** `RtOpen`'s encoder is `encG h Q` on `Fin (2^14 + Q)`, and `pcs_subSt_of_acc` / `opening_alt`
need `PcsOk … rows 14`. The boundary, input-endpoint, `B_out` and stage openings have their own `log_n` (`bLogN`,
`epLogN`, `lt`). If any of them is not `14` at the app's profile, `RtKData.Valid` cannot hold for it at the real
objects and its `RhOpW.hlc` cannot be met: `RtOpen` would need the message width as a field. The stage and boundary
widths at Shieldstral are not a Lean value yet (GA-4). ARGUED.

**L43-2 (Medium; for the doom-cover lane and the coordinator): the extraction is the one fact left in `hopW` and `hMW`
at the blocks.** `RhXOk` / `RhXMOk` follow from `¬ EvXR` by L27's `opened_eq_extracted_run` and L28's `colX_root`
only when the top theorem's free `C`, `coreOf`, `Vx`, `rx` are the run's own: `C = chainEncB …`, `coreOf o k` block
`k`'s core, `Vx` containing the stage and boundary openings' Merkle checks and `rx` their roots, plus the root positions
in the frame. With them free, it is GA-8's bookkeeping premise. ARGUED.

**L43-3 (Medium; for the next cover lane): the closing opening's claims need the carry's content.** At part `i` the
verifier opens the commitment it closes on `cr.pending ++ acc_i.claims.inp`; `rkData` reads `cr.pending` as the
previous part's `acc_{i-1}.claims.out`. `RtRun.accept_part` exposes only the carry's invariant (its count), not its
content, so the X openings' `RhOpW.hrd` is not derivable from it. A version of `accept_part` that exposes the carry
handed on by part `i - 1` closes it. ARGUED.

**L43-4 (Low; for the coordinator): two ordered premises are stronger than needed.** `hal_M` is PROVED without its
hypothesis "no `opB` doomed", and `hal_opA` needs only "no `opB` doomed" (not "no `M` doomed") and no part's
semantics: only the run's layout. The order stays as L30 set it (the theorem is unchanged); this only tells the next
lanes what they may assume.

**L43-5 (Info; for the coordinator): the brief's file pattern `RunCoverP*.lean` also matches L39's
`RunCoverParse.lean`.** This lane's name-clash scan uses the explicit prefixes `RunKindsData`, `RunHal`,
`RunCoverPAlive`, `RunCoverPSomeL`, `RunCoverPRk`.

**L43-6 (Medium; for the next lane): the stages have no accumulator reader.** L31's `tAccRd` reads `Block.slotsLoop`;
stage OUT-C's slot loop is `slotsLoop` under a head of `2` challenges (`StageFS.stageSlots`), stage IN-C's is
